# 테스트 케이스 확장 실험 결과 - 2026-06-20

## 1. 실험 개요

DDL별 사전 판단과 실제 실행 결과 비교를 확장하기 위해 DDL 6개와 부하 3단계를 조합한 18개 조건을 실행하였다. 각 DDL 실행 전에는 benchmark DB를 초기화했으며, `orders` 테이블은 초기 100,000건에 900,000건을 추가하여 약 1,000,000행 규모로 구성하였다.

| 항목 | 값 |
|---|---|
| workload | `orders_mixed` |
| 대상 테이블 | `orders` |
| 부하 단계 | 100 TPS, 1000 TPS, 5000 TPS |
| 실행 시간 | 30초 |
| DDL 실행 시점 | warmup 8초 이후 |
| 결과 CSV | `experiments/benchmark/results/expand_20260620_summary.csv` |

|---:|---:|---:|---:|---:|
| 100 | 101.1 | 1.8ms | 2.8ms | 0 |
| 1000 | 1000.1 | 1.6ms | 3.0ms | 0 |

100 TPS와 1000 TPS에서는 기준선 P99가 낮게 유지되었다. 5000 TPS에서는 DDL이 없는 상태에서도 P99가 51.7ms로 상승하였으므로, 해당 조건은 DB가 이미 높은 부하를 받는 상태로 해석하였다.

## 3. 실측 판정 기준

실측 판정은 본 실험을 위한 임시 기준이다.

| 실측 판정 | 기준 |

| Safe | DDL 성공, 실패 트랜잭션 없음, P99 Ratio 2 미만 |
| Warning | DDL 성공, 실패 트랜잭션 없음, P99 Ratio 2 이상 10 미만 |

## 5. DDL별 요약

| DDL | 유형 | 실측 결과 요약 |
|---|---|---|
| DDL-1 | nullable 컬럼 추가 | 3개 부하 모두 Safe. MigraGuard는 1000 TPS 이상에서 Danger로 판단하여 보수적 오탐이 발생하였다. |
| DDL-2 | 동시 인덱스 생성 | 3개 부하 모두 Safe. MigraGuard는 1000 TPS 이상에서 Danger로 판단하여 인덱스 구축 비용을 과대평가하였다. |
| DDL-3 | 일반 인덱스 생성 | 100 TPS와 1000 TPS에서 Danger, 5000 TPS에서 Warning. 실제 P99가 크게 증가하여 위험 DDL로 확인되었다. |
| DDL-4 | 컬럼 타입 변경 | 3개 부하 모두 Safe. PostgreSQL에서 `VARCHAR(50)`에서 `TEXT`로의 변경은 이번 조건에서 큰 P99 증가를 만들지 않았다. |
| DDL-5 | NOT NULL 직접 설정 | 3개 부하 모두 Danger. `shipping_address`에 NULL 값이 있어 DDL 자체가 실패하였다. |
| DDL-6 | CHECK 제약조건 즉시 검증 | 3개 부하 모두 Safe. 제약 검증은 성공했고 P99 증가도 크지 않았다. |

## 6. 해석

이번 확장 실험에서 실제 위험이 명확했던 케이스는 DDL-3과 DDL-5였다. DDL-3은 일반 인덱스 생성으로 인해 P99 응답 지연이 크게 증가하였다. 특히 1000 TPS 조건에서는 기준선 P99 3.0ms 대비 DDL 실행 중 P99가 226.5ms로 증가하여 P99 Ratio가 75.63으로 나타났다. DDL-5는 기존 데이터에 NULL 값이 존재하여 `ALTER COLUMN ... SET NOT NULL` 실행 자체가 실패하였다. 이는 NOT NULL 직접 설정이 단순 성능 문제가 아니라 기존 데이터 상태에 따라 배포 실패로 이어질 수 있음을 보여준다.

반면 DDL-1, DDL-2, DDL-4, DDL-6은 이번 실측 기준에서는 Safe로 분류되었다. 특히 DDL-4와 DDL-6은 Squawk에서 경고하고 MigraGuard도 Danger로 판단했지만 실제 P99 증가는 크지 않았다. 이는 정적 경고가 항상 운영 장애를 의미하지 않으며, MigraGuard의 현재 계산식도 일부 DDL 유형에 대해 보수적으로 동작한다는 점을 보여준다.

결과적으로 MigraGuard는 위험 DDL을 놓치지 않는 방향으로 동작했지만, 안전한 조건까지 Danger로 분류하는 false positive가 많이 발생하였다. 이번 18개 조건에서 MigraGuard가 Danger로 판단한 조건은 16개였고, 이 중 실측 Safe는 10개였다. 따라서 현재 모델은 실서비스 적용 전 `C_max`, `MuMax`, 잠금 영향도, 인덱스 구축 비용 및 DDL 유형별 기본 위험도를 실측 데이터에 맞게 보정해야 한다.

## 7. 보고서 반영 방향

보고서에는 이 결과를 “정확도 검증 완료”가 아니라 “대표 DDL 확장 실험을 통한 한계 확인”으로 반영한다. 특히 다음 주장을 중심으로 정리하는 것이 적절하다.

- 일반 인덱스 생성과 NOT NULL 직접 설정처럼 실제 지연 또는 실행 실패가 발생한 DDL은 MigraGuard가 Danger로 판단하였다.
- 그러나 동시 인덱스 생성, 일부 타입 변경, CHECK 검증에서는 실제 영향이 낮았음에도 MigraGuard가 Danger로 판단하는 보수적 오탐이 발생하였다.
- Squawk의 정적 경고는 DDL 자체의 잠재 위험을 알려주지만, 실제 운영 영향은 PostgreSQL의 세부 동작과 현재 작업 부하에 따라 달라질 수 있다.
- MigraGuard는 배포 전 동적 지표를 반영한다는 방향성은 보였지만, 실사용 도구가 되려면 DDL 유형별 계산식과 임계값 보정이 필요하다.
