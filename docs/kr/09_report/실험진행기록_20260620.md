# 실측 비교 실험 진행 기록

이 문서는 실험이 중단되더라도 같은 지점부터 재개할 수 있도록 결정 사항, 실행 결과, 발견된 문제를 순서대로 기록한다.

## 1. 실험 목표

우선 수행하는 실험은 배포 전 도구의 위험 판정과 실제 PostgreSQL 작업 부하에서 관찰된 운영 영향을 비교하는 예비 실험이다.

- Squawk: DDL의 정적 규칙 위반 여부
- MigraGuard: DDL과 실행 직전 작업 부하를 결합한 Safe, Warning, Danger 판정
- 실측 결과: DDL 실행 중 트랜잭션 실패, P99 지연 증가, 잠금 대기, 커넥션 압력 및 회복 여부

핵심 평가는 실제 위험 조건을 Safe로 판단한 False Safe 여부이다. 파일명의 Safe, Warning, Danger는 정답으로 사용하지 않는다.

## 2. 구축 완료 사항

- Docker Compose의 PostgreSQL 15 실험 DB
- 별도 PostgreSQL 15 `benchmark` 컨테이너와 pgbench
- 매 실행 전 `benchmark_run` 데이터베이스 재생성
- `orders`, `order_event_logs`, `inventory_stocks`, `account_balances` 대상 작업 부하
- 1초 간격 커넥션 수, 활성 커넥션 수, 잠금 대기 수, 트랜잭션 수 수집
- 개별 트랜잭션 지연 로그로 P50, P95, P99 및 최대 지연 계산
- Squawk 2.58.0 실행, 부하 중 DDL 실행 및 DDL 수행 시간 기록

## 4. 본 실험 전 발견한 통제 문제

현재 `migraguard.yaml`의 `C_max`는 500이지만 실험용 PostgreSQL의 기본 `max_connections`는 100이다. 이 상태에서는 실제 DB가 연결 한계에 도달해도 MigraGuard는 500을 기준으로 위험도를 계산하므로 예측과 실측을 같은 기준으로 비교할 수 없다.

따라서 다음 순서로 실험값을 고정한다.

1. PostgreSQL의 실제 `max_connections`를 조회한다.
2. `orders_mixed`의 최대 지속 처리량을 pgbench로 측정한다.
3. 실험용 MigraGuard 설정의 `C_max`는 실제 DB 연결 한계와 일치시킨다.
4. `MuMax`는 무제한 pgbench 실행에서 관찰된 처리량보다 낮은 보수적 지속 처리량으로 고정한다.
5. 임계값과 잠금 영향 계수는 모든 실험 조건에서 동일하게 유지한다.

## 5. 예비 실험 범위

먼저 동일한 `orders` 작업 부하에 적용할 대표 DDL을 사용하여 도구와 측정 파이프라인을 검증한다.

| DDL | 선정 이유 |
|---|---|
| `022_safe_add_orders_note.sql` | 메타데이터 중심 컬럼 추가 |
| `026_safe_concurrent_orders_composite_index.sql` | 동시 인덱스 생성 |
| `037_linter_warning_standard_orders_index.sql` | 쓰기를 차단하는 일반 인덱스 생성 |
| `038_linter_warning_change_order_number_type.sql` | 타입 변경에 대한 분석기 판정과 PostgreSQL 실제 동작 비교 |
| `040_linter_warning_add_valid_order_check.sql` | 기존 데이터 즉시 검증 |

작업 부하는 저부하, 중간 부하, 한계 근접 부하로 구분한다. 각 조건은 동일한 초기 DB에서 최소 3회 반복하는 것을 최종 목표로 하되, 먼저 1회씩 실행하여 자동화와 판정 기준을 검증한다.

## 7. 처리 한계 측정 결과

실험 DB의 `max_connections`는 100으로 확인되었다. `orders_mixed`를 목표 TPS 제한 없이 10초간 실행한 결과는 다음과 같다.

| 클라이언트 수 | 실제 TPS | 평균 지연 | 실패 |
|---:|---:|---:|---:|
| 4 | 2,325.06 | 1.72ms | 0 |
| 16 | 7,992.58 | 2.00ms | 0 |
| 32 | 12,760.05 | 2.49ms | 0 |
| 64 | 13,330.57 | 4.76ms | 0 |

32개 이후에는 클라이언트 수를 두 배로 늘려도 TPS 증가는 약 4.5%에 그치고 평균 지연은 약 91% 증가하였다. 따라서 이 환경의 포화 처리량은 약 13,000 TPS 부근으로 관찰되었다. 예비 실험에서는 일시적인 최고값을 그대로 사용하지 않고 `MuMax=12,000 TPS`를 보수적인 지속 처리 한계로 고정한다. `C_max`는 실제 연결 한계와 같은 100으로 설정한다.

이 값은 보편적인 PostgreSQL 기준이 아니라 현재 Docker Desktop, 데이터 크기 및 `orders_mixed` 작업 부하에만 적용되는 실험 환경값이다.

## 8. 예비 실행 1차 시도

`022_safe_add_orders_note.sql`과 100 TPS 조건에서 전체 파이프라인을 실행하였다. pgbench는 실제 101.46 TPS, 실패 0건, P99 2.41ms를 기록했고 DDL은 235.26ms에 성공하였다. 그러나 MigraGuard가 `localhost`를 IPv6 주소 `::1`로 해석하여 Docker가 아닌 다른 PostgreSQL 연결 경로에서 인증에 실패하였다.

따라서 이 실행은 위험 판정 정확도 표본에서 제외한다. 실험 스크립트와 설정의 접속 주소를 `127.0.0.1`로 고정하고 같은 조건을 다시 실행한다.

IPv4 주소로 고정한 뒤에도 같은 인증 실패가 발생하였다. 기존 Docker 볼륨을 처음 생성했을 때의 역할 비밀번호와 현재 Compose 환경 변수의 비밀번호가 일치하지 않는 것으로 확인하였다. 컨테이너 내부 접속은 로컬 인증을 사용하므로 기존 pgbench와 DDL 실행에서는 이 문제가 드러나지 않았다. DB 초기화 스크립트에 역할 비밀번호 동기화를 추가하고 두 실패 실행은 모두 정확도 표본에서 제외한다.

역할 비밀번호를 동기화한 뒤에도 호스트 접속만 동일하게 실패하여 `127.0.0.1:5432`에 로컬 PostgreSQL과 Docker 포트가 충돌하는 것으로 판단하였다. 컨테이너 내부 부하 생성기는 `db:5432`를 사용하므로 영향을 받지 않았다. 호스트에서 실행하는 MigraGuard는 충돌하지 않는 Docker 공개 포트 `55432`를 사용하도록 변경하였다.

## 9. 첫 유효 표본

Docker 공개 포트를 55432로 분리한 뒤 MigraGuard 에이전트와 분석기가 정상적으로 실험 DB에 연결되었다.

- DDL: `022_safe_add_orders_note.sql`
- 목표 작업 부하: 100 TPS
- MigraGuard: Safe, RiskScore 30.00
- MigraGuard 입력 TPS: 124.51 TPS (`24h-Peak x0.8` 선택)
- 예상 쿼리 영향 시간: 101.03ms
- 예상 최대 커넥션 수요: 12
- 실제 처리량: 103.62 TPS
- 실패 트랜잭션: 0
- 실제 P99: 2.72ms
- DDL 실행: 성공

이 표본은 저부하에서 메타데이터 중심 컬럼 추가를 Safe로 판정했고 실제 작업 부하에서도 뚜렷한 장애 조건이 관찰되지 않은 사례이다. 다만 DDL 수행 시간 242.53ms에는 `docker exec`와 `psql` 프로세스 시작 시간이 포함되므로 PostgreSQL 서버 내부 순수 DDL 시간으로 해석하지 않는다.

## 10. 예비 행렬 실행 조건

| 부하 단계 | 목표 TPS | 클라이언트 | 처리 한계 대비 목적 |
|---|---:|---:|---|
| 저부하 | 100 | 4 | 충분한 처리 여유 |
| 중간 부하 | 5,000 | 16 | 처리 한계의 약 42% |
| 한계 근접 | 11,000 | 32 | 보수적 `MuMax`의 약 92% |

각 부하에서 DDL이 없는 기준선을 먼저 측정하고 대표 DDL 5개를 실행한다. 이번 단계는 자동화와 결과 방향을 확인하는 1회 예비 행렬이며, 최종 수치로 사용할 조건은 이후 3회 이상 반복한다.
