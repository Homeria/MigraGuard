# 보고서 참고자료

이 문서는 보고서 본문에서 인용하거나 판단 근거로 사용한 논문, 공식 문서, 기술 회고 및 도구 문서를 정리한 것이다. 본문에서는 가독성을 위해 자료명만 표기하고, URL과 인용·활용한 내용은 이 문서에서 관리한다.

- 최종 정리일: 2026-06-22
- URL 접속일: 2026-06-20 ~ 2026-06-21
- PostgreSQL 공식 문서는 실험 환경과 맞추기 위해 PostgreSQL 15 문서를 기준 URL로 정리하였다.
- 원문을 긴 문단 단위로 그대로 붙여 넣는 대신, 각 자료마다 원문 확인 위치, 페이지 내 검색어, 짧은 직접 인용 구절과 상세 한국어 정리를 함께 남겼다.
- 교수 또는 심사자가 “어디에 그런 내용이 있는가”를 물을 경우, 각 항목의 URL을 열고 `Ctrl+F` 검색어로 원문 위치를 확인하면 된다.

## R1. Online migrations at scale

- 발행 주체: Stripe
- 자료 유형: 기술 회고
- 사용 위치: 추진배경 및 목표
- URL: https://stripe.com/blog/online-migrations
- 원문 확인 위치:
  - 문서 제목: `Online migrations at scale`
  - 페이지 내 검색어: `Businesses are constantly transacting on Stripe`, `online migrations`, `Backfill`, `Dual writing`, `all infrastructure upgrades online`
  - 검증할 내용: Stripe는 지속적으로 거래가 발생하는 서비스에서 전체 서비스를 멈추지 않고 데이터 모델 변경을 수행해야 했으며, 이를 위해 이중 쓰기, 백필, 읽기·쓰기 경로 전환을 단계적으로 수행했다.
- 원문 직접 인용(English): "Businesses are constantly transacting on Stripe." / "all infrastructure upgrades online"
- 직접 인용 의미(한국어): Stripe에서는 사용자의 거래가 계속 발생하므로, 인프라 변경을 온라인 상태에서 수행해야 한다는 의미이다.
- 원문 내용 상세 정리:
  - Stripe는 수억 개의 Subscriptions 객체를 다루는 상황에서 데이터 모델을 변경해야 했다.
  - 객체 하나를 순차적으로 처리하는 데 1초가 걸린다고 가정하면 1억 개 객체 처리에 3년 이상이 걸린다는 예를 제시한다.
  - 사용자의 거래가 계속 발생하므로 Subscriptions 서비스를 멈출 수 없었고, 모든 서비스를 운영한 상태에서 마이그레이션을 수행해야 했다.
  - 이를 위해 기존 구조와 신규 구조에 동시에 쓰기, 기존 데이터 백필, 읽기 경로 전환, 쓰기 경로 전환, 기존 구조 제거의 단계적 방식을 사용했다.
  - 추가 쓰기 부하가 운영 DB에 영향을 줄 수 있으므로 적용 비율을 천천히 높이고 운영 지표를 관찰했다.
- 보고서 반영 내용:
  - 허용 가능한 중단 시간보다 작업 시간이 길고 사용자 요청을 멈출 수 없는 환경에서는 무중단 마이그레이션이 기술적 선호가 아니라 운영 요구사항이 될 수 있다는 근거로 사용하였다.
  - 무중단 마이그레이션은 단순히 DDL을 실행하는 문제가 아니라 이중 쓰기, 백필, 읽기·쓰기 경로 전환, 지표 관찰을 포함하는 복잡한 운영 절차라는 근거로 사용하였다.

## R2. GitLab Post Deployment Migrations

- 발행 주체: GitLab
- 자료 유형: 공식 개발 문서
- 사용 위치: 추진배경 및 목표
- URL: https://docs.gitlab.com/development/database/post_deployment_migrations/
- 원문 확인 위치:
  - 문서 제목: `Post Deployment Migrations`
  - 페이지 내 검색어: `Post deployment migrations`, `requires downtime`, `Deploy a new version`, `Here we don’t need any downtime`
  - 검증할 내용: 기존 애플리케이션 버전이 의존하는 상태에서 컬럼 제거와 같은 변경을 수행하면 중단이 필요할 수 있지만, 먼저 새 버전을 배포하고 이후 배포 후 마이그레이션을 수행하면 다운타임 없이 처리할 수 있음을 설명한다.
- 원문 직접 인용(English): "requires downtime" / "Deploy a new version" / "we don’t need any downtime"
- 직접 인용 의미(한국어): 애플리케이션 코드가 의존하던 DB 구조를 바로 제거하면 중단이 필요할 수 있지만, 먼저 새 애플리케이션 버전을 배포하여 의존성을 제거한 뒤 DB 변경을 수행하면 다운타임을 피할 수 있다는 의미이다.
- 원문 내용 상세 정리:
  - GitLab의 Post Deployment Migrations 문서는 기존 애플리케이션 버전이 특정 컬럼에 의존하는 상태에서 해당 컬럼을 제거하면 일반적으로 인스턴스를 중단해야 한다고 설명한다.
  - 대신 먼저 새 애플리케이션 버전을 배포하여 해당 컬럼 의존성을 제거하고, 이후 배포 후 마이그레이션으로 컬럼 제거 등의 작업을 수행하면 다운타임을 피할 수 있다고 설명한다.
  - 이는 데이터베이스 변경을 애플리케이션 배포와 같은 시점에 한 번에 수행하지 않고, 배포 순서를 나누어 위험을 줄이는 방식이다.
- 보고서 반영 내용:
  - 제한적·단계적 무중단 패턴을 전체 서비스를 멈추지 않되 애플리케이션 배포와 DB 변경 시점을 나누어 호환성 위험을 줄이는 전략으로 설명하는 근거로 사용하였다.
  - 제한적·단계적 방식이 모든 DDL을 자동으로 안전하게 만드는 것이 아니라, 변경 종류와 배포 순서를 함께 관리해야 하는 운영 패턴이라는 설명에 사용하였다.

## R3. PostgreSQL CREATE INDEX

- 발행 주체: PostgreSQL Global Development Group
- 자료 유형: 공식 문서
- 사용 위치: 추진배경 및 목표, 과제 추진 경과
- URL: https://www.postgresql.org/docs/15/sql-createindex.html
- 원문 확인 위치:
  - 문서 제목: `CREATE INDEX`
  - 섹션: `Parameters`의 `CONCURRENTLY`, `Building Indexes Concurrently`
  - 페이지 내 검색어: `standard index build locks out writes`, `Building Indexes Concurrently`, `two scans of the table`, `extra CPU and I/O load`, `live production database`
  - 검증할 내용: 일반 인덱스 생성은 쓰기 작업을 차단할 수 있고, `CONCURRENTLY`는 쓰기 차단을 줄이지만 두 번의 테이블 스캔과 추가 CPU·디스크 입출력 부하를 발생시킬 수 있다.
- 원문 직접 인용(English): "locks out writes" / "two scans of the table" / "extra CPU and I/O load"
- 직접 인용 의미(한국어): 일반 인덱스 생성은 쓰기를 막을 수 있고, 동시 인덱스 생성은 두 번의 테이블 스캔과 추가 CPU·디스크 부하를 발생시킨다는 의미이다.
- 원문 내용 상세 정리:
  - 일반 `CREATE INDEX`는 인덱스 생성 중 대상 테이블의 쓰기 작업을 차단하지만 읽기는 허용할 수 있다.
  - 대용량 테이블의 인덱스 생성은 오래 걸릴 수 있으며, 이 동안 쓰기 차단이 운영 환경에 심각한 영향을 줄 수 있다.
  - `CREATE INDEX CONCURRENTLY`는 쓰기 차단을 줄이기 위해 제공되는 옵션이다.
  - 하지만 `CONCURRENTLY` 방식은 테이블을 두 번 스캔하고, 기존 트랜잭션 종료를 기다려야 하므로 일반 인덱스 생성보다 전체 작업량과 시간이 증가할 수 있다.
  - 동시 인덱스 생성 중에도 추가 CPU와 디스크 입출력 부하가 다른 쿼리를 느리게 만들 수 있다.
- 보고서 반영 내용:
  - 온라인 변경 기능도 위험을 제거하는 것이 아니라, 짧고 강한 쓰기 차단을 더 긴 실행 시간과 추가 자원 사용으로 전환할 수 있다는 근거로 사용하였다.
  - MigraGuard에서 인덱스 여부, 동시 생성 여부, 테이블 크기, 디스크 입출력 처리량을 반영해야 하는 근거로 사용하였다.

## R4. gh-ost: GitHub's online schema migration for MySQL

- 발행 주체: GitHub
- 자료 유형: 공식 저장소 및 도구 문서
- 사용 위치: 추진배경 및 목표, 과제 추진 경과
- URL: https://github.com/github/gh-ost
- 원문 확인 위치:
  - 문서 제목: `gh-ost: GitHub's online schema migration for MySQL`
  - 섹션: `How?`, `Highlights`, `Usage`
  - 페이지 내 검색어: `triggerless online schema migration solution`, `binary log stream`, `pausability`, `dynamic control`, `testing it on replicas`, `throttles`, `postpone`
  - 검증할 내용: gh-ost는 MySQL용 온라인 스키마 변경 도구이며, 트리거 대신 바이너리 로그를 사용하고, 실행 중 일시 중지와 동적 제어를 지원한다. 또한 replica에서 테스트하고 결과를 비교할 수 있으며, 부하가 높을 때 작업을 제한하거나 최종 전환 시점을 연기할 수 있다.
- 원문 직접 인용(English): "triggerless online schema migration solution" / "pausability, dynamic control/reconfiguration"
- 직접 인용 의미(한국어): `gh-ost`는 트리거 없는 온라인 스키마 변경 도구이며, 일시 중지와 동적 제어를 제공한다는 의미이다.
- 원문 내용 상세 정리:
  - `gh-ost`는 MySQL용 온라인 스키마 마이그레이션 도구이다.
  - 기존 온라인 스키마 변경 도구처럼 원본 테이블과 유사한 Ghost Table을 만들고 데이터를 점진적으로 복사한다.
  - 일반적인 트리거 기반 방식과 달리 MySQL 바이너리 로그 스트림을 읽어 변경분을 새 테이블에 비동기적으로 반영한다.
  - 마이그레이션 중 작업을 일시 중지하거나 동적으로 설정을 바꿀 수 있고, 최종 테이블 전환 시점도 제어할 수 있다.
  - 실행 중 부하가 높으면 작업을 제한하거나 멈추어 운영 DB의 원래 작업 부하를 회복시킬 수 있다.
- 보고서 반영 내용:
  - OSC 도구가 동적 지표를 활용하더라도, 그 목적은 배포 전 위험 예측이 아니라 실행 중인 마이그레이션의 속도 제한과 영향 완화에 가깝다는 근거로 사용하였다.
  - MigraGuard는 OSC를 대체하는 도구가 아니라, OSC 시작 전 실행 시점과 위험도를 판단하는 보조 단계라는 설명에 사용하였다.

## R5. pt-online-schema-change

- 발행 주체: Percona
- 자료 유형: 공식 도구 문서
- 사용 위치: 검토 자료(최종 본문 직접 근거에서는 제외)
- URL: https://docs.percona.com/percona-toolkit/pt-online-schema-change.html
- 원문 확인 위치:
  - 문서 제목: `pt-online-schema-change`
  - 섹션: `RISKS`, `DESCRIPTION`, `--max-lag`, `--max-load`, `--alter-foreign-keys-method`
  - 페이지 내 검색어: `without blocking reads or writes`, `copying rows from the original table`, `creates triggers`, `pauses the data copy operation`, `too much load on the server`, `Foreign keys complicate`, `Test the tool on a non-production server`, `Backup your production server`
  - 검증할 내용: pt-online-schema-change는 원본 테이블을 직접 변경하기보다 새 테이블을 만들고 데이터를 청크 단위로 복사하며, 트리거로 변경분을 반영한다. 복제 지연이나 서버 부하가 커지면 작업을 일시 중지하거나 중단할 수 있고, 외래 키는 추가 위험을 만들며, 공식 문서는 비운영 환경 테스트와 백업 확인을 요구한다.
- 원문 직접 인용(English): "without blocking reads or writes" / "pauses the data copy operation"
- 직접 인용 의미(한국어): `pt-online-schema-change`는 읽기·쓰기를 막지 않고 스키마를 변경하려 하며, 복제 지연 등이 있으면 데이터 복사를 일시 중지한다는 의미이다.
- 원문 내용 상세 정리:
  - 이 도구는 변경 대상 테이블의 구조를 직접 바꾸는 대신, 변경된 스키마를 가진 새 테이블을 만든다.
  - 원본 테이블의 데이터를 새 테이블로 작은 청크 단위로 복사한다.
  - 복사 중 원본 테이블에서 발생하는 변경은 트리거를 통해 새 테이블에 반영한다.
  - 복사가 끝나면 원본 테이블과 새 테이블의 이름을 전환하여 변경을 완료한다.
  - 복제 지연이 발생하면 데이터 복사를 일시 중지하고, 서버 부하가 한계를 넘으면 작업을 중지하거나 중단할 수 있다.
  - 트리거가 이미 존재하거나 외래 키가 관련된 경우 적용 제약과 추가 위험이 있다.
- 보고서 반영 내용:
  - MySQL 계열 OSC 도구의 일반적인 동작 후보로 검토하였으나, 최종 본문에서는 gh-ost를 대표 사례로 사용하고 이 자료는 직접 근거에서 제외하였다.
  - 추후 OSC 도구와의 확장 비교를 설계할 때 참고할 수 있는 후보 자료로 유지하였다.

## R6. PostgreSQL ALTER TABLE

- 발행 주체: PostgreSQL Global Development Group
- 자료 유형: 공식 문서
- 사용 위치: 과제 추진 경과
- URL: https://www.postgresql.org/docs/15/sql-altertable.html
- 원문 확인 위치:
  - 문서 제목: `ALTER TABLE`
  - 섹션: `Description`, 하단 `Notes`
  - 페이지 내 검색어: `SET NOT NULL`, `scanning the entire table`, `rewrite the entire table`, `Changing the type of an existing column`, `NOT VALID`, `Scanning a large table`
  - 검증할 내용: `SET NOT NULL`과 제약조건 추가는 기존 행 검사를 요구할 수 있고, 컬럼 타입 변경이나 특정 컬럼 추가는 테이블 전체 재작성을 유발할 수 있다. 또한 `CHECK` 또는 외래 키 제약조건은 `NOT VALID`와 별도 `VALIDATE CONSTRAINT`를 통해 즉시 전체 검증의 영향을 줄일 수 있다.
- 원문 직접 인용(English): "rewrite the entire table" / "scan the table" / "adding a constraint"
- 직접 인용 의미(한국어): 일부 `ALTER TABLE` 작업은 테이블 전체 재작성이나 기존 행 검사를 요구할 수 있다는 의미이다.
- 원문 내용 상세 정리:
  - 컬럼 타입 변경은 기존 데이터가 새 타입과 물리적으로 호환되지 않으면 테이블 전체를 다시 작성해야 할 수 있다.
  - 일부 컬럼 추가나 기본값 변경도 기존 행에 값을 반영하거나 검증하는 작업을 요구할 수 있다.
  - `CHECK`, `NOT NULL`, 외래 키와 같은 제약조건을 추가할 때는 기존 행이 해당 조건을 만족하는지 확인하기 위해 테이블을 스캔할 수 있다.
  - `CHECK` 또는 외래 키 제약조건은 `NOT VALID`로 먼저 추가하고 이후 `VALIDATE CONSTRAINT`로 검증하여 동시 업데이트에 미치는 영향을 줄일 수 있다.
  - 이러한 작업은 데이터 규모가 클수록 오래 걸리며, 잠금과 자원 사용이 운영 쿼리에 영향을 줄 수 있다.
- 보고서 반영 내용:
  - DDL의 작업 유형, 테이블 재작성 가능성, 기존 데이터 검증 여부를 정적 지표로 선정한 근거로 사용하였다.
  - `T_ddl` 계산에서 테이블 크기와 디스크 입출력 처리량을 고려해야 하는 근거로 사용하였다.

  - 섹션: `13.3.1. Table-Level Locks`
  - 페이지 내 검색어: `conflicting lock modes`, `ACCESS EXCLUSIVE`, `CREATE INDEX`, `CREATE INDEX CONCURRENTLY`, `Only an ACCESS EXCLUSIVE lock blocks a SELECT`
  - 검증할 내용: PostgreSQL의 테이블 잠금 모드는 서로 다른 충돌 관계를 가지며, 일반 `CREATE INDEX`와 `CREATE INDEX CONCURRENTLY`, 여러 `ALTER TABLE` 작업이 서로 다른 잠금을 획득한다.
- 원문 직접 인용(English): "table-level locks" / "conflicting lock modes" / "ACCESS EXCLUSIVE"
- 직접 인용 의미(한국어): PostgreSQL에는 여러 테이블 잠금 모드가 있으며, 충돌하는 잠금 모드는 동시에 유지될 수 없다는 의미이다.
- 원문 내용 상세 정리:
  - PostgreSQL은 테이블 수준 잠금 모드를 여러 단계로 구분한다.
  - 각 잠금 모드는 서로 다른 충돌 관계를 가지며, 충돌하는 잠금이 있으면 한 작업은 다른 작업이 끝날 때까지 대기해야 한다.
  - `ACCESS EXCLUSIVE`는 강한 잠금이며 많은 작업과 충돌한다.
  - DDL이 어떤 잠금을 요구하는지에 따라 읽기·쓰기 쿼리가 받는 영향이 달라진다.
- 보고서 반영 내용:
  - DDL마다 다른 잠금 수준을 가지며, 잠금 수준에 따라 쿼리 영향 시간이 달라진다는 `T_block` 계산의 근거로 사용하였다.
  - 잠금 영향도를 계산 계수로 둔 이유를 설명하는 근거로 사용하였다.

## R17. Mathematical Model for the Optimal Utilization Percentile in M/M/1 Systems

- 저자: Francisco A. González-Horta 외
- 자료 유형: 연구 논문
- 사용 위치: 과제 추진 경과
- URL: https://arxiv.org/pdf/1106.2380
- 원문 확인 위치:
  - 문서 제목: `Mathematical Model for the Optimal Utilization Percentile in M/M/1 Systems`
  - 페이지 내 검색어: `knee`, `optimal utilization percentiles`, `70% utilization level`, `70-90%`, `M/M/1`, `utilization`
  - 검증할 내용: M/M/1 시스템의 성능 곡선에서 무릎 또는 최적 활용률 지점을 찾으려는 관점을 제시하지만, 특정 활용률을 모든 시스템에 적용 가능한 보편 기준으로 제시하지 않는다.
- 원문 직접 인용(English): "knees, or optimal utilization percentiles" / "traditional 70-90% for the optimal utilization range is a myth" / "depends on the service capacity"
- 직접 인용 의미(한국어): M/M/1 성능 곡선에서 무릎 또는 최적 활용률 지점을 찾는 관점은 있지만, 전통적으로 언급되는 70~90% 범위가 보편 상수는 아니며 시스템 처리 능력에 따라 달라질 수 있다는 의미이다.
- 원문 내용 상세 정리:
  - M/M/1 시스템에서는 활용률이 높아질수록 응답 시간이 비선형적으로 증가한다.
  - 논문은 응답 시간과 활용률 사이의 성능 곡선에서 무릎 지점을 찾는 수학적 접근을 제시한다.
  - 동시에 전통적으로 언급되는 70~90% 활용률 범위가 보편 상수가 아니며, 무릎 위치는 시스템 조건에 따라 달라진다고 설명한다.
  - 따라서 이 논문은 80%라는 특정 값을 정답으로 제공하는 자료가 아니라, 포화도 기반 정책값을 설정할 때 “처리 한계에 가까워질수록 지연 위험이 커진다”는 관점을 제공하는 자료로 사용한다.
- 보고서 반영 내용:
  - Danger 임계값 80%를 논문에서 제시한 보편 정답으로 사용하지 않고, 처리 한계 도달 전에 실행을 보류하기 위한 프로토타입의 보수적 정책값으로 설명하는 데 사용하였다.
  - Safe/Warning/Danger 임계값이 실측 데이터로 보정되어야 한다는 한계 설명과 함께 사용하였다.
