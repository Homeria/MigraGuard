# MigraGuard 핵심 비교 실험 계획

구체적인 설치 프로그램, PostgreSQL 구성, 트래픽 발생 도구 및 지표 수집 방법은 `실험환경_구축과_벤치마크_실행계획.md`에서 관리한다.

## 1. 실험의 전체 목적

본 실험은 MigraGuard에 사용된 모든 지표와 수식을 각각 증명하는 데 목적이 있지 않다. PostgreSQL 공식 문서, Google SRE, Little’s Law 및 온라인 스키마 변경 도구에서 확인한 정적·동적 지표를 결합했을 때, 실제 운영 장애를 일으키는 DDL 실행 조건을 배포 전에 얼마나 잘 구별하고 상대적으로 안전한 실행 시간을 제시할 수 있는지 확인하는 데 목적이 있다.

본 프로젝트의 전제는 동일한 DDL도 실행 시점의 작업 부하에 따라 결과가 달라질 수 있다는 것이다. 따라서 실험의 판정 단위는 DDL 파일 하나가 아니라 다음 조합으로 정의한다.

> 실험 조건 1개 = DDL 1개 × 작업 부하 조건 1개

핵심 실험은 다음 두 가지로 구성한다.

1. Squawk와 MigraGuard의 배포 전 위험 조건 판별 능력 비교
2. MigraGuard의 실행 시간대 추천 정확도 검증

첫 번째 실험은 “어떤 실행 조건이 위험한가를 배포 전에 얼마나 잘 구별하는가”를 다룬다. 두 번째 실험은 “추천 시간이 실제로도 안전한 시간이며, 위험한 시간을 잘못 추천하지 않는가”를 다룬다. Linter 비교는 배포 전 판별력을 확인하는 기준선으로 사용하고, 온라인 변경은 시간 추천의 정확도를 확인한 이후 대표 사례에서 실행 방식의 차이를 설명하는 보조 비교로 사용한다.

## 2. 공통 판정 기준

### 2.1 실제 위험 조건의 정의

DDL 파일명에 포함된 Safe, Warning, Danger는 실험 정답으로 사용하지 않는다. 해당 명칭은 DDL 제작 당시의 의도일 뿐 실제 장애 여부를 나타내지 않기 때문이다. 실제 PostgreSQL에서 DDL과 작업 부하를 동시에 실행하고 관측한 결과를 정답으로 사용한다.

주요 평가는 다음과 같이 안전과 위험의 이진 분류로 수행한다.

- 실제 안전: 사전에 정한 서비스 운영 기준을 모두 유지하고 정상적으로 회복함
- 실제 위험: DDL 실행 중 또는 실행 직후 하나 이상의 운영 기준을 위반함

운영 기준 위반에는 다음 현상을 포함한다.

- 애플리케이션 요청 타임아웃 또는 오류 발생
- P99 응답 지연의 서비스 기준 초과
- 커넥션 획득 실패 또는 커넥션 사용량의 위험 한계 초과
- 처리량의 허용 범위 이하 감소
- 사전에 정한 시간 안에 기준 상태로 회복하지 못함
- 복제 환경을 구성한 경우 복제 지연의 허용 범위 초과

Safe, Warning, Danger의 3등급 비교는 부가 결과로 사용한다. 핵심 결과는 실제 위험 조건을 안전하다고 판단한 False Safe 비율이다.

### 2.2 운영 기준을 정하는 방법

운영 기준은 실험 결과를 확인하기 전에 고정한다. 결과를 본 뒤 기준을 변경하면 원하는 결과에 맞춰 정답을 바꾸는 문제가 발생한다.

가능하면 프로젝트가 가정한 서비스 수준 목표를 사용한다. 별도의 목표가 없다면 DDL을 실행하지 않은 기준 상태를 먼저 측정하고, 기준 상태 대비 허용 가능한 P99 증가율, 오류율, 커넥션 사용률, 처리량 감소율 및 회복 제한 시간을 실험 정책으로 선언한다. 이 값은 모든 서비스에 적용되는 보편 기준이 아니라 해당 실험 환경의 판정 기준으로 명시한다.

### 2.3 공통 관측값

두 실험 모두 다음 값을 수집한다.

- DDL 실제 수행 시간
- 잠금 대기 시간과 대기 쿼리 수
- 요청 TPS와 처리 성공 TPS
- P99 응답 지연
- 요청 오류와 타임아웃 수
- 최대 활성 커넥션 수
- 기준 상태로 돌아오는 데 걸린 시간
- 복제 환경이 있는 경우 최대 복제 지연

PostgreSQL에서는 `pg_stat_activity`, `pg_locks`, `pg_stat_database`를 사용하고, 애플리케이션 또는 부하 발생기에서 요청 성공 여부와 응답 시간을 기록한다. 복제 환경을 구성하면 `pg_stat_replication`을 추가로 사용한다.

## 3. 실험 1: 배포 전 위험 조건 판별 능력 비교

### 3.1 실험 질문

> 실제 작업 부하에서 장애성 영향을 일으키는 DDL 실행 조건을 Squawk와 MigraGuard가 각각 얼마나 잘 배포 전에 구별하는가?

### 3.2 실험을 수행하는 이유

Squawk는 배포 전에 DDL의 정적 위험을 검사하지만 실행 시점의 TPS, P99 응답 지연, 활성 커넥션 및 복제 지연은 반영하지 않는다. MigraGuard는 같은 배포 전 단계에서 DDL의 정적 특성과 실행 시점의 동적 상태를 결합한다.

따라서 이 실험은 Squawk가 부족하거나 잘못되었다는 사실을 증명하기 위한 것이 아니다. 동일한 배포 전 판단 단계에서 동적 상태를 추가로 반영했을 때 실제 위험 조건을 구별하는 능력이 향상되는지 확인하기 위한 것이다.

### 3.3 사용할 대상과 도구

- DDL: `experiments/ddl/022~041`
- 정적 비교 도구: Squawk
- 비교 대상: MigraGuard
- 데이터베이스: PostgreSQL
- 작업 부하 발생기: `pgbench` 또는 대상 테이블에 맞춘 요청 발생 스크립트
- DB 관측: `pg_stat_activity`, `pg_locks`, `pg_stat_database`
- 요청 관측: 부하 발생기의 TPS, 응답 시간, 오류 및 타임아웃 로그
- 결과 저장: 실행 조건별 CSV

DDL 20개 중 15개는 Squawk 통과를 의도한 DDL이고, 5개는 Squawk 경고를 의도한 DDL이다. 실험 전에 현재 Squawk 버전으로 다시 검사하여 실제 통과·경고 결과를 확정한다.

### 3.4 작업 부하 조건

최소한 다음 세 수준을 구성한다.

- 저부하: 커넥션과 처리량에 충분한 여유가 있는 상태
- 정상 부하: 평상시 서비스를 가정한 상태
- 한계 근접 부하: TPS와 커넥션 사용량이 처리 한계에 가까운 상태

초과 부하는 시스템 보호와 실험 시간에 여유가 있을 때 추가한다. 실험의 핵심은 장애를 크게 발생시키는 것이 아니라 안전 조건과 위험 조건이 모두 포함되도록 만드는 것이다.

### 3.5 실험 방법

각 `DDL × 작업 부하` 조합에 대해 다음 순서로 실행한다.

1. 동일한 초기 데이터베이스 상태를 준비한다.
2. 작업 부하를 시작하고 TPS, P99 응답 지연 및 활성 커넥션이 안정될 때까지 기다린다.
3. DDL을 실행하기 전에 Squawk 결과를 기록한다.
4. 동일 시점의 작업 부하 값을 MigraGuard에 입력하고 등급과 5단계 지표를 기록한다.
5. 작업 부하를 유지한 상태에서 일반 PostgreSQL DDL을 실제 실행한다.
6. DDL 수행 시간, 잠금, P99, 오류, 타임아웃, 커넥션 및 회복 시간을 기록한다.
7. 사전에 정한 운영 기준에 따라 실제 안전 또는 실제 위험으로 분류한다.
8. 데이터베이스를 초기 상태로 복원하고 같은 조건을 최소 3회 반복한다.

전체 실험은 `20개 DDL × 3개 부하 수준 × 3회 반복 = 180회`이다. 시간이 부족하면 먼저 대표 DDL 6개를 사용해 `6 × 3 × 3 = 54회`의 예비 실험을 수행한 뒤 전체 실험으로 확장한다.

### 3.6 예측 결과의 변환

두 도구의 출력을 실제 안전·위험 결과와 비교할 수 있도록 다음과 같이 이진화한다.

| 도구 | 안전 예측 | 위험 예측 |
|---|---|---|
| Squawk | 정적 검사 통과 | 하나 이상의 경고 발생 |
| MigraGuard | Safe | Warning 또는 Danger |

### 3.7 산출 결과

- Squawk 혼동행렬
- MigraGuard 혼동행렬
- 실제 위험 조건 재현율
- 실제 안전 조건 정밀도
- False Safe 비율
- 실제 안전 조건을 경고한 불필요한 차단 비율
- Squawk와 MigraGuard가 서로 다르게 판단한 사례 목록
- DDL별·부하별 예측과 실제 결과 히트맵

### 3.8 결과의 의미

| Squawk | MigraGuard | 실제 결과 | 해석 |
|---|---|---|---|
| 통과 | 위험 | 실제 위험 | 정적 검사 이후 동적 운영 위험을 추가로 발견한 사례 |
| 경고 | 안전 | 실제 안전 | 정적 위험은 존재하지만 현재 조건의 운영 영향은 낮았던 사례 |
| 통과 | 안전 | 실제 위험 | MigraGuard의 가장 치명적인 False Safe 사례 |
| 경고 | 위험 | 실제 안전 | 두 도구가 모두 보수적으로 판단한 사례 |

MigraGuard의 위험 조건 재현율이 Squawk보다 높고 False Safe가 낮다면 배포 전 동적 상태 결합의 효용을 뒷받침한다. 반대로 대부분을 Danger로 판단하여 실제 안전 조건도 차단한다면 안전성은 보수적이지만 실제 사용성은 낮다는 의미이다.

이 비교는 Squawk 자체의 품질을 평가하는 것이 아니라, 배포 전 게이트로 사용했을 때 실제 운영 위험을 구별하는 정보가 얼마나 추가되는지를 평가한다.

## 4. 실험 2: 실행 시간대 추천 정확도 검증

### 4.1 실험 질문

> MigraGuard가 추천한 실행 시간이 실제 DDL 실행에서도 안전한 시간에 포함되며, 위험한 시간대를 안전하다고 잘못 추천하지 않는가?

### 4.2 실험을 수행하는 이유

MigraGuard의 핵심 목표는 현재 위험하다는 등급만 제시하는 것이 아니라, 동일한 DDL을 상대적으로 안전하게 실행할 수 있는 시간대를 제시하는 것이다. 따라서 시간대 추천 기능을 평가하려면 추천 시간이 단순히 입력 TPS가 가장 낮은 시간인지 확인하는 데서 끝나면 안 된다. 각 시간대의 작업 부하에서 동일한 DDL을 실제로 실행하고 관측한 결과를 기준으로 추천의 정확도를 평가해야 한다.

### 4.3 시간 추천의 실제 정답 정의

실제 최적 시간을 반드시 하나의 시각으로 정의하지 않는다. 여러 시간대가 모두 운영 기준을 만족할 수 있기 때문이다. 각 시간대에서 DDL을 실제 실행한 뒤 다음과 같이 정답을 구성한다.

- 실제 안전 시간 집합: DDL 실행 중과 실행 후 모든 운영 기준을 안정적으로 만족한 시간대의 집합
- 실제 허용 가능 시간 집합: 일부 지연 증가는 있지만 사전에 정한 Warning 허용 기준 안에 들어 조건부 실행 후보로 볼 수 있는 시간대의 집합
- 실제 위험 시간 집합: 하나 이상의 운영 기준을 크게 위반하여 Danger로 보아야 하는 시간대의 집합
- 관측상 최저 영향 시간: 안전 시간 중 P99 증가, 커넥션 사용량 및 회복 시간이 가장 낮은 시간
- 추천 불가 상태: 24개 시간대 모두 Danger 기준에 해당하여 실행 후보로 제시하기 어려운 상태

추천 정확도의 핵심은 MigraGuard가 관측상 최저 영향 시간과 정확히 같은 한 시간을 선택했는지가 아니다. Safe 추천 시간이 실제 안전 시간 집합에 포함되는지, Warning 조건부 추천 시간이 실제 허용 가능 시간 집합에 포함되는지, 그리고 Danger만 존재하는 조건에서 추천 불가를 올바르게 판단하는지가 더 중요하다.

### 4.4 사용할 DDL과 시간대 작업 부하

시간대 추천 실험은 정적 특성이 다른 대표 DDL을 사용한다.

- 메타데이터 중심 변경 1개
- 동시 인덱스 생성 1개
- 일반 인덱스 또는 데이터 검증 작업 1개
- 테이블 재작성 작업 1개

각 DDL에는 동일한 24시간 작업 부하 프로필을 적용한다. 시간대별 프로필에는 최소한 TPS와 P99 응답 지연이 포함되어야 하며, 가능하면 활성 커넥션과 복제 지연도 시간대별로 구성한다. 작업 부하에는 저부하 시간, 정상 시간, 출퇴근 또는 이벤트 피크, 야간 배치와 같이 서로 다른 형태가 포함되어야 한다.

실제 24시간을 기다리지 않고 각 시간대의 작업 부하를 짧은 실험 구간으로 압축하여 재현한다. 예를 들어 01시의 작업 부하를 재현한 뒤 DB를 초기화하고, 다음에는 02시의 작업 부하를 재현하는 방식이다.

### 4.5 실험 방법

각 DDL에 대해 다음 절차를 수행한다.

1. 24개 시간대의 작업 부하 이력을 MigraGuard에 입력한다.
2. MigraGuard가 산출한 시간대별 `RiskScore`, 등급, Safe 후보 시간, Warning 조건부 후보 시간 및 최저 위험 시간을 기록한다.
3. 동일한 초기 DB 상태에서 첫 번째 시간대의 작업 부하를 재현한다.
4. 작업 부하가 안정되면 동일한 DDL을 실제 실행한다.
5. P99 응답 지연, 오류, 타임아웃, 최대 활성 커넥션, 처리량 감소 및 회복 시간을 기록한다.
6. 사전에 정한 운영 기준에 따라 해당 시간대를 실제 안전 또는 실제 위험으로 분류한다.
7. DB를 초기 상태로 복원하고 다음 시간대에서 같은 절차를 반복한다.
8. 24개 시간대의 실제 안전 시간 집합을 만든다.
9. MigraGuard 추천 시간과 실제 안전 시간 집합을 비교한다.
10. 전체 과정을 동일한 조건에서 최소 3회 반복한다.

대표 DDL 4개를 24시간대에서 3회 반복하면 `4 × 24 × 3 = 288회`이다. 먼저 3개 DDL과 저부하·정상·피크·배치 등 6개 대표 시간대를 사용하여 `3 × 6 × 3 = 54회`의 예비 실험을 수행하고, 자동화가 검증되면 24시간 전체로 확대한다.

### 4.6 추천 정확도 평가 지표

- 안전 시간 적중률: MigraGuard 추천 시간이 실제 안전 시간 집합에 포함된 비율
- 위험 시간 추천률: 추천 시간이 실제 위험 시간으로 판정된 비율
- 안전 시간 재현율: 실제 안전 시간 중 MigraGuard가 Safe 후보로 제시한 비율
- 안전 시간 정밀도: MigraGuard가 Safe 후보로 제시한 시간 중 실제 안전한 비율
- 조건부 추천 적중률: Safe 후보가 없을 때 Warning 조건부 추천 시간이 실제 허용 가능한 영향 범위에 포함된 비율
- 조건부 추천 위험률: Warning 조건부 추천 시간이 실제 위험 시간으로 판정된 비율
- Top-K 적중률: MigraGuard의 위험도 상위 K개 추천 시간이 관측상 저영향 시간에 포함된 비율
- 순위 상관관계: 시간대별 예측 위험 순위와 실제 운영 영향 순위가 얼마나 비슷한지 나타내는 값
- 추천 후회값: 추천 시간의 실제 운영 영향과 관측상 최저 영향 시간의 차이
- 추천 불가 판정률: 실제로 허용 가능한 시간이 없을 때 Danger만 존재한다고 판단하여 추천을 제공하지 않은 비율

정확히 같은 한 시간을 맞히는 비율은 부가 지표로만 사용한다. 02시와 03시가 모두 안전한데 02시 대신 03시를 추천했다고 해서 실패로 볼 필요는 없기 때문이다.

### 4.7 현재 구현에서 먼저 보완할 사항

현재 구현은 Safe 시간대가 있으면 이를 우선 추천하고, Safe 시간대가 없지만 Warning 시간대가 있으면 조건부 추천을 제시하도록 구성한다. 따라서 실험에서는 Safe 추천과 Warning 조건부 추천을 구분하여 평가해야 한다. 또한 모든 시간대가 Danger인 경우에는 최저 위험 시간을 추천처럼 제시하지 않고 추천 불가로 처리해야 한다.

- Warning 임계값 미만의 시간은 Safe 후보로 구분
- Safe 후보가 없고 Warning 후보가 있으면 조건부 추천으로 구분
- 모든 시간대가 Danger이면 추천 불가로 처리
- 이력이 없는 시간대를 0으로 채우지 않고 입력 부족으로 처리
- 최저 위험 시간, Safe 추천 시간, Warning 조건부 추천 시간을 출력에서 구분
- 가능하면 시간대별 활성 커넥션과 복제 지연도 별도로 입력

한 시간 단위 추천이 예상 `T_ddl`보다 짧을 수 있다는 문제는 본 실험의 한계로 기록한다. 후속 구현에서는 `T_ddl`과 `T_rec`을 포함할 수 있는 연속 안전 구간을 탐색해야 한다.

### 4.8 산출 결과

- DDL별 24시간 예측 등급과 실제 안전·위험 결과 히트맵
- 시간대별 예측 `RiskScore`와 실제 P99·커넥션 변화 비교 그래프
- 추천 시간, 실제 안전 시간 집합, 관측상 최저 영향 시간 비교표
- 안전 시간 적중률과 위험 시간 추천률
- 시간대 위험 순위 상관관계
- 추천 후회값
- 안전 시간이 없는 사례의 판정 결과
- 추천이 실패한 사례와 실패 원인

### 4.9 결과의 의미

- 추천 시간이 대부분 실제 안전 시간에 포함되면 시간대 추천 기능의 실용 가능성을 뒷받침한다.
- 정확한 최저 영향 시간은 자주 놓치지만 실제 안전 시간에는 포함된다면 최적화 정확도는 낮아도 안전한 후보 선택 기능은 유효하다.
- 예측 위험 순위와 실제 영향 순위가 유사하면 `RiskScore`가 시간대 간 상대 비교에 활용될 수 있다는 의미이다.
- 위험 시간 추천률이 높으면 추천 기능을 배포 의사결정에 사용하기 어렵다.
- 안전 시간이 없는 조건에서 추천을 계속 반환하면 시간대 추천 정책 자체를 수정해야 한다.
- 메타데이터 DDL만 잘 맞고 재작성 DDL에서 실패하면 시간대 예측보다 `T_ddl` 추정의 오차가 원인일 가능성이 있다.

### 4.10 OSC 비교의 위치

OSC 비교는 시간 추천 정확도의 핵심 평가에서 제외하고 대표 사례의 보조 실험으로 수행한다. 시간 추천이 실제 안전 시간을 찾는다는 결과를 먼저 확보한 뒤, 1~2개 대표 DDL에 대해 다음 네 조건을 비교한다.

1. 일반 DDL을 피크 시간에 실행
2. 일반 DDL을 MigraGuard 추천 시간에 실행
3. PostgreSQL 온라인 변경 방식을 피크 시간에 실행
4. PostgreSQL 온라인 변경 방식을 MigraGuard 추천 시간에 실행

이 보조 비교는 MigraGuard와 OSC의 정확도를 겨루는 실험이 아니다. 실행 시점 선택과 실행 방식 변경 중 어느 요소가 서비스 영향을 줄였으며 두 방법을 함께 적용할 추가 가치가 있는지를 확인한다.

## 5. 실험 진행 순서

실험은 다음 순서로 진행한다.

1. 실제 안전·위험 판정에 사용할 운영 기준 확정
2. PostgreSQL 기준 작업 부하와 처리 한계 측정
3. 대표 DDL 6개를 이용한 실험 1 예비 실행
4. 결과 수집과 판정 자동화 확인
5. 실험 1을 DDL 20개로 확대
6. 실험 2에 사용할 대표 DDL과 24시간 작업 부하 확정
7. 6개 대표 시간대를 이용한 시간 추천 예비 실험
8. 24시간 전체의 실제 안전 시간 집합 측정
9. 추천 적중률, 위험 시간 추천률 및 순위 상관관계 계산
10. 대표 DDL 1~2개를 이용한 OSC 보조 비교
11. False Safe, 추천 실패 및 실제 장애 사례의 원인 분석

## 7. 해석 범위와 한계

- 실험 결과는 사용한 PostgreSQL 버전, 하드웨어, 데이터 규모 및 작업 부하에 한정된다.
- Squawk와 MigraGuard 비교는 두 도구가 같은 기능을 수행한다는 의미가 아니라 배포 전 게이트로 제공하는 정보의 차이를 비교한 것이다.
- PostgreSQL 기본 온라인 절차나 특정 외부 도구 하나의 결과를 모든 OSC 도구의 성능으로 일반화하지 않는다.
- 실제 위험 정답은 사전에 정한 운영 기준에 따라 달라지므로 해당 기준을 결과와 함께 공개한다.
- 반복 실행과 DB 초기화가 보장되지 않으면 캐시, 데이터 상태 및 이전 DDL의 영향이 결과에 섞일 수 있다.
