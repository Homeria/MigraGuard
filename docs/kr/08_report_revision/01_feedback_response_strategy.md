# 최종보고서 피드백 대응 및 수정 기준

## 1. 문서 목적

이 문서는 2026년 6월 19일 결과보고서 피드백을 바탕으로 MigraGuard의 원래 프로젝트 목표를 복원하고, 이후 보고서와 실험 내용을 일관되게 수정하기 위한 기준을 정리한다.

앞으로 보고서 문장, 그림, 표, 실험 및 발표 자료를 수정할 때는 이 문서를 우선 기준으로 사용한다. 특히 새로운 내용을 추가할 때는 다음 질문에 답할 수 있어야 한다.

1. 왜 이 문제가 발생하는가?
2. 어떤 조건에서 문제가 커지는가?
3. 이 지표를 왜 사용했는가?
4. 계산된 값이 운영자에게 무엇을 의미하는가?
5. 결과를 바탕으로 사용자가 어떤 행동을 선택할 수 있는가?
6. 이 내용이 안전한 실행 시간대 추천이라는 프로젝트 목표에 어떻게 연결되는가?

## 2. 피드백의 핵심 진단

가장 큰 문제는 구현 자체보다 프로젝트의 최종 목적이 바뀐 것처럼 보였다는 점이다.

원래 승인받은 프로젝트의 중심 목표는 다음과 같다.

> DDL의 정적 영향과 시간대별 작업 부하를 결합하여 상대적으로 안전한 마이그레이션 실행 시간대를 추천한다.

그러나 현재 보고서에서는 다음 내용이 최종 결과처럼 강조되었다.

> DDL과 현재 작업 부하를 이용하여 5단계 지표를 계산하고 Safe, Warning, Danger로 분류한다.

이 때문에 시간대 추천을 위해 고안한 중간 지표와 위험 등급이 프로젝트의 최종 산출물로 바뀐 것처럼 보였다. 이후 수정에서는 시간대 추천을 다시 최종 결과로 두고, 위험 계산은 시간대 추천을 위한 근거로 위치시켜야 한다.

### 교수의 핵심 평가 기준

교수가 가장 중요하게 보는 기준은 구현 기능의 수가 아니라 실제 사용자가 이 도구를 사용할 이유와 신뢰할 근거가 있는가이다. 이후 보고서는 다음 네 질문에 순서대로 답해야 한다.

1. **동기:** 이 도구는 어떤 사용자의 어떤 문제를 해결하기 위해 나왔는가?
2. **과정:** 어떤 입력을 사용하고 어떤 계산 과정을 거쳐 결과를 도출하는가?
3. **의미:** 계산된 지표, 등급과 추천 시간대는 각각 무엇을 의미하며 사용자는 무엇을 해야 하는가?
4. **정확성:** 결과가 실제 운영 영향과 얼마나 일치하며, 기존 도구와 비교했을 때 어떤 판단을 더 정확하게 제공하는가?

각 장은 이 네 질문 중 어떤 질문에 답하는지 분명해야 한다. 기술 설명만 존재하고 사용자 행동으로 이어지지 않는 내용은 주요 결과가 아니라 구현 세부사항으로 취급한다.

실제 사용 가능성은 다음 조건으로 판단한다.

- 사용자가 누구인지 명확하다. 주요 사용자는 DDL 배포를 결정하는 개발자, DBA 또는 SRE이다.
- 사용자가 입력해야 하는 정보와 도구가 자동으로 수집하는 정보가 구분된다.
- 결과가 단순 수치가 아니라 실행, 연기, 추가 승인, 중단 또는 OSC 검토와 같은 행동으로 연결된다.
- 기본 설정만으로 사용할 수 있고, 환경별 설정값에는 운영 지표나 정책에 근거한 의미가 있다.
- 동일한 입력에 대해 결과가 재현 가능하며, 실제 관측 결과와 비교한 검증 근거가 존재한다.
- 도구의 적용 범위와 실패할 수 있는 조건이 명확하다.

정확성은 다른 도구와 결과가 다르다는 사실만으로 증명하지 않는다. 실제 또는 통제된 벤치마크에서 관측한 운영 영향을 정답 기준으로 두고 MigraGuard와 비교 도구의 판단을 함께 대조해야 한다. 서로 다른 목적의 도구와 비교할 경우에는 정확도와 역할 차이를 구분한다.

## 3. 복원할 프로젝트 목표

프로젝트 목표는 다음과 같이 정리한다.

> MigraGuard는 DDL의 작업 특성과 시간대별 데이터베이스 작업 부하를 결합하여 각 시간대의 마이그레이션 위험도를 계산하고, 위험이 상대적으로 낮은 연속 구간을 권장 실행 시간대로 제시하는 배포 전 의사결정 보조 도구이다.

분석 흐름은 다음과 같아야 한다.

```text
DDL 입력
  -> 정적 특성 추출
  -> 시간대별 작업 부하 결합
  -> 단계별 위험 지표 계산
  -> 각 시간대의 Safe/Warning/Danger 판정
  -> 실행 가능한 연속 시간 구간 탐색
  -> 권장 실행 시간대 및 대체 전략 제시
```

따라서 `T_ddl`, `T_block`, `C_peak`, `T_rec`, `RiskScore`는 최종 목적이 아니라 시간대별 위험을 설명하기 위한 중간 지표이다.

## 4. 용어 수정 원칙

### 4.1 5단계 모델

보고서에서는 원칙적으로 `5단계 모델` 대신 다음 표현을 사용한다.

- 5단계 위험 계산 과정
- 단계별 위험 산출 과정
- 5단계 위험 지표

전체 시스템이나 위험 판단 구조를 넓은 의미에서 모델이라고 부를 수는 있지만, 다섯 값 자체를 독립적인 예측 모델처럼 표현하지 않는다.

### 4.2 정확도와 검증

실제 장애 여부가 기록된 정답 데이터가 없는 실험에서는 다음 표현을 사용하지 않는다.

- 정확도를 증명하였다
- 올바르게 예측하였다
- 실제 장애를 탐지하였다
- 기존 도구보다 정확하다

대신 다음처럼 표현한다.

- 계산 구조가 의도한 방향으로 반응하는지 확인하였다.
- 작업 부하와 서버 처리 여력에 대한 민감도를 검토하였다.
- 실제 운영 검증에 앞서 위험 판단의 동작 방향을 확인하였다.
- 실제 관측 결과와 비교하는 후속 검증이 필요하다.

## 5. 단계별 지표의 의미와 사용

각 지표는 계산식만 설명하지 않고, 값이 운영자에게 어떤 의미를 가지는지 함께 설명해야 한다.

| 지표 | 의미 | 값이 증가할 때의 해석 | 의사결정에서의 사용 |
|---|---|---|---|
| `T_ddl` | DDL 자체의 예상 수행 시간 | 잠금 및 자원 사용이 지속될 가능성 증가 | 실행 구간이 DDL을 완료하기에 충분한지 판단 |
| `T_block` | 운영 쿼리가 영향을 받을 것으로 예상되는 시간 | 쿼리 대기와 응답 지연 가능성 증가 | 허용 가능한 대기 시간 또는 타임아웃과 비교 |
| `C_peak` | 차단 시간 동안 발생할 것으로 예상되는 최대 커넥션 수요 | 커넥션 한계 접근 또는 초과 가능성 증가 | `C_max`와 비교하여 커넥션 고갈 위험 판단 |
| `T_rec` | DDL 종료 후 누적 요청을 해소하는 데 필요한 예상 시간 | 지연이 DDL 종료 이후에도 지속될 가능성 증가 | 다음 배포나 피크 시간 전에 회복 가능한지 판단 |
| `RiskScore` | 정적 위험과 실행 시점의 자원 압력을 종합한 위험 점수 | 현재 실행 조건의 운영 여유 감소 | 시간대별 위험 등급과 후보 구간 정렬에 사용 |

`C_peak`는 실제로 연결된 커넥션 수가 아니라 제한이 없을 때 필요한 예상 커넥션 수요로 설명한다.

지표의 절대값을 모든 서비스에 동일하게 적용할 수 있다고 주장하지 않는다. 각 값은 서비스의 운영 한계, 타임아웃, 처리량 및 서비스 수준 목표와 비교할 때 의미를 가진다.

## 6. 위험 등급의 운영적 의미

등급은 단순한 색상이나 점수 구간이 아니라 권장 행동과 연결해야 한다.

| 등급 | 운영적 의미 | 기본 권장 행동 |
|---|---|---|
| Safe | 예상 자원 수요와 회복 가능성이 기본 운영 한계 안에 있음 | 일반 배포 후보 시간대로 제시 |
| Warning | 즉시 한계를 초과하지는 않지만 운영 여유가 부족하거나 불확실성이 큼 | 더 낮은 부하 시간대로 연기하거나 DBA 승인, 모니터링 강화 후 실행 |
| Danger | 커넥션 한계 초과, 회복 불가능 또는 강한 정적 위험이 예상됨 | 해당 시간대를 추천 대상에서 제외하고 중단 마이그레이션, DDL 분할 또는 OSC 검토 |

Safe는 장애가 절대로 발생하지 않는다는 보증이 아니다. 설정된 운영 한계 안에서 상대적으로 실행 가능성이 높은 후보임을 의미한다.

Warning은 애매한 중간 색상이 아니라 조건부 실행 구간이다. 승인, 추가 관찰 또는 실행 시간 변경과 연결한다.

Danger는 단순 경고가 아니라 현재 조건에서 실행을 보류하고 대체 전략을 검토해야 하는 구간이다.

## 7. 임계값과 Config의 해석

임계값을 사용자 취향에 따라 임의로 조절한다고 설명해서는 안 된다. 다음 원칙으로 설명한다.

1. Safe, Warning, Danger의 운영적 의미와 판정 구조는 고정한다.
2. `C_max`는 실제 데이터베이스 또는 커넥션 풀의 허용 한계에서 가져온다.
3. `MuMax`는 해당 환경에서 안정적으로 처리 가능한 최대 처리량을 의미한다.
4. 타임아웃과 회복 허용 시간은 서비스 수준 목표와 배포 정책에서 가져온다.
5. Config는 판정 의미를 바꾸는 기능이 아니라 서로 다른 서버의 물리적 처리 여력과 운영 정책을 반영하는 환경 프로파일이다.
6. 기본 Config는 프로젝트가 제시하는 기본 정책이며, 변경할 경우에는 실측값이나 운영 정책과 같은 근거가 필요하다.

현재 Config와 위험 임계값이 실제 운영 데이터로 보정되지 않았다는 점은 한계로 명시한다. 향후에는 벤치마크와 실제 DDL 실행 결과를 이용해 기본값을 보정해야 한다.

## 8. 시간대 추천의 일반화

시간대 추천은 단일 시점의 위험 등급을 보여주는 데서 끝나지 않아야 한다.

권장 시간대는 다음 원칙으로 도출한다.

1. 예측 또는 관측된 24시간 작업 부하의 각 시점에 동일한 DDL을 적용한다.
2. 각 시점에서 단계별 지표와 위험 등급을 계산한다.
3. Danger 시간대는 후보에서 제외한다.
4. Safe가 연속되는 구간을 우선 탐색한다.
5. 연속 Safe 구간이 없으면 Warning 구간 중 위험 점수가 낮은 구간을 조건부 후보로 제시한다.
6. 후보 구간의 길이가 예상 `T_ddl`과 필요한 안전 여유보다 긴지 확인한다.
7. 조건을 만족하는 구간 중 위험 점수가 가장 낮고 회복 여유가 충분한 구간을 권장한다.
8. 적합한 구간이 없으면 중단 마이그레이션, DDL 분할 또는 OSC 검토를 제안한다.

보고서의 핵심 그림은 단일 Danger 결과보다 다음 내용을 우선해야 한다.

- 시간대별 작업 부하 그래프
- 시간대별 Safe, Warning, Danger 구간
- 최종 권장 실행 시간대
- 해당 시간대를 추천한 지표 근거
- 서버 설정이나 DDL이 바뀌었을 때 권장 시간대가 어떻게 변하는지 보여주는 비교

## 9. 중단 마이그레이션과 OSC의 선택 근거

대부분의 환경에서는 점검 시간을 확보할 수 있다면 중단 마이그레이션이 기술적으로 단순하고 통제하기 쉽다. OSC는 무조건 우수한 방식이 아니라 중단 비용이 온라인 실행의 복잡성과 위험보다 클 때 선택할 수 있는 전략이다.

개념적인 의사결정 구조는 다음과 같다.

```text
중단 마이그레이션 비용
  = 예상 중단 시간에 따른 서비스 손실
  + SLA 및 사용자 영향
  + 중단 후 복구 비용

온라인 마이그레이션 비용
  = 구현 및 운영 복잡도
  + 추가 인프라와 장시간 자원 사용
  + 데이터 정합성, 전환 및 롤백 위험
```

다음 조건에서는 OSC 또는 제한적 무중단 방식의 필요성이 커진다.

- 주문, 결제, 예약처럼 중단 비용이 큰 핵심 서비스
- 24시간 작업 부하가 유지되어 충분한 Safe 구간이 없는 경우
- 일반 DDL의 예상 잠금 또는 수행 시간이 허용 가능한 점검 시간을 초과하는 경우
- 대용량 테이블로 인해 중단 시간이 과도하게 길어지는 경우
- 지역별 서비스로 인해 모든 사용자가 적은 공통 저부하 구간을 찾기 어려운 경우

다음 조건에서는 중단 마이그레이션이 더 합리적일 수 있다.

- 사내 또는 비핵심 시스템
- 대상 테이블이 작고 예상 작업 시간이 짧은 경우
- 명확한 점검 시간을 확보할 수 있는 경우
- OSC 도입과 운영의 복잡도가 중단 비용보다 큰 경우

MigraGuard는 OSC를 직접 수행하는 도구가 아니라, 일반 배포가 가능한 시간대가 존재하는지 확인하고 적합한 구간이 없을 때 OSC 검토의 근거를 제공하는 도구로 위치시킨다.

## 10. 기존 도구와의 비교 원칙

### 10.1 DDL 린터

Squawk와 MigraGuard는 동일한 정답을 맞히는 경쟁 도구로 비교하지 않는다.

- Squawk: DDL 자체의 정적 규칙 위반 탐지
- MigraGuard: DDL과 시간대별 작업 부하를 결합하여 실행 시점과 권장 시간대 판단

Squawk 비교 실험은 정적 검사를 통과한 DDL에도 실행 시점에 따른 차이가 존재한다는 보조 근거로 사용한다. 프로젝트의 정확도를 증명하는 핵심 실험으로 사용하지 않는다.

### 10.2 OSC

OSC와 MigraGuard를 단순히 같은 입력에 대한 결과값으로 비교하지 않는다.

- OSC: 마이그레이션 실행 중 복제 지연과 부하를 관찰하면서 작업을 제한하거나 중지하는 실행 전략 또는 도구
- MigraGuard: 실행 전에 작업 부하를 분석하여 일반 실행 시간대를 추천하고, 적합한 시간대가 없을 때 OSC 필요성을 검토하도록 돕는 의사결정 도구

정확성을 검토하려면 실제 또는 통제된 벤치마크 환경에서 관측된 DDL 영향과 MigraGuard의 사전 판정을 비교해야 한다.

## 11. 실험 우선순위

주요 실험은 다음 순서로 구성한다.

1. 동일 DDL의 시간대별 위험도 변화
2. Safe 구간 탐색과 권장 실행 시간대 제시
3. Low, Default, High Capacity 환경에서 권장 시간대 변화
4. 저부하와 고부하 환경에서 실제 DDL 실행 결과와 사전 판정 비교
5. Squawk 통과 및 경고 DDL에 대한 보조 비교

최소 벤치마크를 추가한다면 다음 정도로 제한한다.

- 대표 DDL 1개
- 저부하와 고부하 2개 조건
- 실제 DDL 수행 시간
- P99 응답 지연 변화
- 잠금 대기 또는 쿼리 대기
- 활성 커넥션 변화
- MigraGuard의 추천 시간대와 실제 영향이 작은 조건의 일치 여부

이 실험은 대규모 정확도 검증이 아니라, 시간대 추천의 방향이 실제 관측과 일치하는지 확인하는 최소 사례로 해석한다.

## 13. 수정 우선순위

마감 전 작업은 다음 순서로 수행한다.

### 최우선

1. 프로젝트 목표를 안전한 실행 시간대 추천으로 복원한다.
2. forecast 분석 결과와 권장 시간대를 주요 결과로 복원한다.
3. 5단계 모델을 단계별 위험 계산 과정 또는 지표로 수정한다.
4. Safe, Warning, Danger의 운영 의미와 권장 행동을 추가한다.

### 그다음

5. Config를 임의 튜닝이 아닌 환경 프로파일로 설명한다.
6. OSC가 필요한 조건과 중단 방식과의 비용 비교를 추가한다.
7. Squawk 비교를 핵심 검증에서 보조 실험으로 조정한다.

### 가능하면 수행

8. 대표 DDL에 대한 저부하 및 고부하 최소 벤치마크를 수행한다.
9. 권장 시간대와 실제 관측 영향의 방향이 일치하는지 확인한다.
10. 참고문헌과 공식 문서 출처를 보강한다.

## 14. 이후 답변 및 수정 시 준수사항

이후 MigraGuard 보고서 관련 요청에서는 다음 원칙을 계속 반영한다.

- 시간대 추천을 프로젝트의 최종 목적으로 유지한다.
- 단계별 지표와 위험 등급을 최종 결과처럼 독립시키지 않는다.
- 모든 지표 설명 뒤에 운영적 의미와 후속 행동을 연결한다.
- 임계값을 개인 취향에 따른 설정으로 설명하지 않는다.
- Squawk 또는 OSC와 단순한 등급 일치율로 정확성을 주장하지 않는다.
- 실제 장애 정답 데이터가 없는 결과는 동작 방향과 민감도 검토로 표현한다.
- 모든 주요 주장에 왜 그런지와 어떤 조건에서 그런지를 포함한다.
- 새로운 그림과 표는 시간대 추천 또는 의사결정에 어떤 정보를 제공하는지 설명한다.
- 기존 구현과 다른 기능을 보고서에 있는 것처럼 작성하지 않는다.
- 구현 한계는 숨기지 않되, 원래 목표와 연결되는 구현 및 실험 결과를 먼저 제시한다.
