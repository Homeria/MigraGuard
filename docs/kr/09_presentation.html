Research Background

1. DDL 마이그레이션이 유발하는 장애 실태

Slide 02
📌 Target Lock Mechanism: AccessExclusiveLock (8단계)
  • 정적 문법 검사의 한계: 기존 린터(Linter) 도구들은 쿼리의 구문적 무결성만 판단할 뿐, "현재 가동 중인 데이터베이스의 실시간 부하"를 인지하지 못해 배포 차단 결정을 내릴 수 없습니다.
  • 독점 락(Exclusive Lock)의 블로킹 병목: ALTER TABLE 타입 변경 시 획득하는 `AccessExclusiveLock`은 트래픽이 높은 서비스에서 조회를 포함한 모든 후속 트랜잭션을 무기한 대기 큐에 쌓이게 만듭니다.
  • 애플리케이션 커넥션 풀 고갈: 단 몇 초간의 락 점유로도 대기 세션이 폭증하여 WAS 커넥션 풀이 즉각 고갈되고, 결국 시스템 전체 타임아웃 장애로 전파됩니다.
Proposed Framework

2. 정적-동적 데이터 결합형 분석 모델

Slide 03

MigraGuard는 스키마 구조 변경의 정적 메타데이터(Lock Level, Table Rewrite 여부)와 운영 중인 DB의 동적 성능 지표(실시간 TPS, P99 Latency, 커넥션 가동률)를 실시간 결합하여 배포 승인 여부를 선제 결정합니다.

비교 차원 정적 SQL 린터 (sqlfluff 등) APM 모니터링 (Datadog) MigraGuard (제안 시스템)
핵심 데이터원 SQL 텍스트, 정적 DDL 문법 규칙 사후 서버 CPU 사용량, 활성 세션 개수 AST 구문 분석 + 실시간 TPS, P99, 인프라 사양
분석/작동 타이밍 개발 단계 (배포 전 코드 작성 시) 실제 DDL 실행 중 혹은 장애 진행 중 **배포 게이트웨이 (PR 머지 직전 실시간 검증)**
차단 능력 (Control) 단순 구문 스타일 수정 권고 (차단 불가) 알림 발송 후 DBA 수동 수습 대기 **자동 서킷 브레이킹 (CI/CD 종료 코드 제어)**
최적 배포 대안 제시 없음 없음 **24시간 예측치 분석 후 골든 윈도우 시간 추천**

Mathematical Modeling

4. 5단계 정량적 리스크 예측 모델

Slide 05
📂 Strategy Pattern: pkg/migraguard/internal/analyzer/risk_evaluator.go
🔬 물리 소요시간 & 차단 윈도우

Step 1: DDL 소요시간 예측 ($T_{ddl}$)

T_{ddl} = \left(\frac{TableSize}{DiskIO}\right) \times 1000 \quad (ms)

Step 2: 가상 서비스 차단 시간 계산 ($T_{block}$)

T_{block} = (P99 + T_{ddl} + Lag_{repl}) \times LockImpact
🔮 연결 수 폭증 및 복구력

Step 3: 커넥션 풀 폭증 예측 ($C_{peak}$)

C_{peak} = ActiveConns + \left(\frac{TPS}{1000} \times T_{block}\right)

Step 4: 벡로그 해소 시스템 회복 시간 ($T_{rec}$)

T_{rec} = \frac{C_{peak} - C_{max}}{(\mu_{max} - TPS) / 1000} \quad (ms)
Step 5: 리스크 수치화 (RiskScore) = \max\left(BaseRisk, \frac{C_{peak}}{C_{max}} \times 100\right) Danger > 80%
Infrastructure Awareness

5. 하드웨어 스펙 연동 환경 적응력

Slide 06

정적 린터와 다르게 MigraGuard는 대상 데이터베이스 장비의 하드웨어 스펙 한계점($\mu_{max}$, 디스크 I/O 속도)과 유기적으로 연동하여 차단 위험도를 평가합니다.

  • 동일 DDL 배포의 가변 의사결정: 데이터 재작성을 동반하는 ALTER TABLE 배포 시, 하드웨어 수용 한계량에 따라 서킷 브레이크 동작이 달라집니다.
  • Low-Spec (Low Capacity) 환경: 디스크 속도 저하로 $T_{ddl}$이 길어지고 최대 커넥션 수 $C_{max}$가 낮아 리스크가 임계치(80%)를 초과해 차단(Danger)됩니다.
  • High-Spec (High Capacity) 환경: 우수한 물리 성능으로 리스크 스코어가 낮아 주의(Warning)를 거쳐 배포가 허용됩니다.
High-Spec Instance Profile Warning

Disk IO: 100MB/s | Max Conns: 500
Peak Conns: 312.5 | Risk Score: 62.5%

Low-Spec Instance Profile Danger (Block)

Disk IO: 20MB/s | Max Conns: 100
Peak Conns: 312.5 | Risk Score: 312.5%

6. 예측 엔진 및 Tie-Breaker 알고리즘

Slide 07

안전 구간 내 트래픽 최소점 선별 로직

  • 기존 모델의 한계점: 과거 트래픽 분석을 거쳐 리스크가 가장 낮은 'Safe' 구간이 복수 검출될 경우, 단순히 가장 이른 시간대(예: 밤 12시 00:00)를 일률 추천하는 한계가 발생했습니다.
  • 트래픽 기반 최저점 선별 (Tie-Breaker): 동점 리스크 영역 중에서 물리적인 예상 트랜잭션 빈도(Expected TPS)가 가장 낮아, 최악의 경우에도 장애 반경(Blast Radius)을 최소화할 수 있는 골든 배포 윈도우를 탐색합니다.
💡 최적 윈도우 판정 수식

1. 미래 24시간 동안의 리스크 스코어 시계열 계산

2. $RiskScore_h < ThresholdWarning$ 만족 시간대 후보군 필터링

3. 통계적 예상 트래픽(Expected TPS) 최소화 시간대 탐색

BestHour = \arg\min_{h \in SafeHours} (ExpectedTPS_h)

7. 예측 리스크 히트맵 시각화 결과

Slide 08

8. 다차원 시나리오 배치 시뮬레이션 결과

Slide 09
📂 Verification: pkg/migraguard/internal/infra/sqlite/sqlite_sandbox.go
  • 600회 배치 실험 매트릭스: Sine 패턴, Spike 트래픽 패턴 등 10개 시나리오 ✚ 20개 DDL 문 ✚ 3개 인프라 사양 조합의 다차원 검증을 수행했습니다.
  • 트래픽 스파이크(Flash Sale) 검증: 평시 300 TPS 수준에서 3,500 TPS로 솟구치는 인위적 트래픽 주입 시, 기존 패스되던 DDL 위험 스코어가 즉각 280%로 치솟아 배포 차단이 정상 작동함을 입증했습니다.
  • 정밀한 DDL 오판율 0%: PostgreSQL의 정형 파서 엔진을 네이티브 코드로 호출하여 문법 해석 오탐률 0건을 기록하였습니다.

DevSecOps Pipeline

9. CI/CD 파이프라인 통합 워크플로우

Slide 10
📂 Pipeline Gate: Github Actions Integration
  • 자동화 배포 게이트 키퍼: 개발자가 DDL 마이그레이션 파일이 포함된 Pull Request를 오픈하면, GitHub Actions 러너가 CLI를 호출해 리스크 지수를 체크합니다.
  • 피드백 루프 단축: `Danger` 등급으로 분석될 시 파이프라인이 즉각 종료 코드 1로 실패하여 병합을 차단하며, 골든 배포 윈도우 분석 리포트가 PR 코멘트로 자동 출력됩니다.
  • 최소 권한 가이드 및 감사(Audit): 분석 및 락 조회 권한을 제한한 전용 DB 계정을 가이드하고 모든 분석 이력을 감사 로그로 남겨 내부 통제를 충족합니다.

10. 한계점 및 향후 고도화 연구 계획

Slide 11
HTTP API 원격 아키텍처

현 SQLite 로컬 지표 캐시 구조의 망 격리 문제를 해결하고자, 원격 Prometheus/TSDB 환경에서 직접 지표를 조회하는 **HTTP API 아키텍처**로 진화 예정.

기계학습 모델 보정

Online DDL 처방 연동
