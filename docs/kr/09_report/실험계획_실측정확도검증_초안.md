# 실측 정확도 검증 실험 계획 초안

이 문서는 MigraGuard의 중간 지표, 최종 위험 등급 및 시간대 추천을 실제 PostgreSQL 실행 결과와 비교하기 위한 후속 실험 계획을 보관한다. 현재 보고서의 핵심 실험 목적을 다시 정의하는 동안 별도 초안으로 유지하며, 실제 장애 예측 정확도를 검증할 필요가 있을 때 활용한다.

## 1. 실험 목적

다음 질문에 답하는 것을 목적으로 한다.

- `T_ddl`, `T_block`, `C_peak`, `T_rec`은 실제 관측값과 얼마나 가까운가?
- MigraGuard가 Safe로 판단한 조건은 실제 실행에서도 운영 기준을 지키는가?
- Warning과 Danger는 실제 지연, 타임아웃 및 커넥션 고갈을 구분하는가?
- 추천 시간에 실행하면 즉시 실행할 때보다 운영 영향이 감소하는가?
- Squawk를 통과했지만 실제로 위험한 조건을 MigraGuard가 추가로 발견하는가?
- PostgreSQL의 저잠금 변경 방식과 MigraGuard의 시간대 선택은 상호 보완적인가?

## 2. 사전 환경 보정

본 실험 전 대상 환경의 기준값을 측정한다.

- 부하를 단계적으로 증가시키며 TPS, P99 응답 지연 및 오류율을 기록한다.
- 운영 기준을 유지할 수 있는 최대 처리량을 `MuMax`로 정한다.
- PostgreSQL의 `max_connections`와 애플리케이션 커넥션 풀 크기를 기준으로 `C_max`를 정한다.
- DDL이 없는 상태의 TPS, P99 응답 지연 및 활성 커넥션을 기준선으로 기록한다.
- 디스크 입출력 처리량을 실제 환경에서 측정한다.

`MuMax`는 보편적인 상수가 아니라 실험 작업 부하와 대상 환경에 대한 처리 한계로 해석한다.

## 3. 대표 DDL

최소한 다음 유형을 포함한다.

- 메타데이터 중심 변경: nullable 컬럼 추가
- 동시 인덱스 생성: `CREATE INDEX CONCURRENTLY`
- 일반 인덱스 생성: `CREATE INDEX`
- 테이블 재작성: 컬럼 타입 변경
- 기존 데이터 검증: `SET NOT NULL`
- 제약조건 검증: `CHECK` 또는 외래 키 추가

각 DDL은 저부하, 정상 부하, 한계 근접 부하에서 실행한다. 데이터 크기도 소형과 대형으로 나누며, 각 조건을 최소 3회 반복한다. 실행 순서를 무작위로 섞고 매 실행 후 동일한 DB 상태를 복원한다.

## 4. 예측값과 실제 관측값

| MigraGuard 예측값 | 실제 관측값 |
|---|---|
| `T_ddl` | DDL 시작부터 종료까지의 실제 시간 |
| `T_block` | 잠금 때문에 운영 쿼리가 대기한 시간 |
| `C_peak` | 실행 중 관측된 최대 활성 커넥션 수 |
| `T_rec` | P99·TPS·커넥션이 기준 상태로 돌아오는 시간 |
| `RiskScore` | 운영 기준 위반, 타임아웃, 커넥션 포화 등 실제 영향 |

관측에는 `pg_stat_activity`, `pg_locks`, `pg_stat_database` 및 애플리케이션 요청 로그를 사용한다. 복제 지연을 검증하려면 Primary와 Replica 환경 및 `pg_stat_replication`이 필요하다.

## 5. 실제 결과 등급 정의

DDL 파일명의 의도 등급은 정답으로 사용하지 않는다. 실제 실행 결과를 기준으로 다음과 같이 독립적인 정답을 구성한다.

- Safe: P99, 오류율 및 커넥션 사용량이 사전에 정의한 운영 기준 안에 있고 정상적으로 회복함
- Warning: 지연 또는 커넥션 주의 기준을 초과했지만 요청 실패나 커넥션 고갈은 발생하지 않음
- Danger: 타임아웃, 요청 실패, 커넥션 고갈, 처리량 붕괴 또는 회복 실패가 발생함

운영 기준은 결과를 확인하기 전에 확정한다.

## 6. 정확도 평가

- `T_ddl`, `C_peak`, `T_rec`: 평균 절대 오차, 상대 오차, 예측값과 관측값 산점도
- `T_block`: 0에 가까운 값이 존재할 수 있으므로 절대 오차 중심
- `RiskScore`: 실제 커넥션 사용률 및 운영 기준 위반 정도와의 상관관계
- 최종 등급: 혼동행렬, 정밀도, 재현율, F1 점수
- 핵심 안전 지표: 실제 Danger를 Safe로 판단한 False Safe 비율

## 7. 시간대 추천 검증

시간대별 작업 부하를 짧은 구간으로 압축하여 재현한다.

1. 시간대별 TPS와 P99 응답 지연을 가진 작업 부하를 준비한다.
2. MigraGuard가 시간대별 위험도와 최저 위험 시간을 계산한다.
3. 동일한 DDL을 저부하, 중간 부하 및 고부하 시간 조건에서 각각 실행한다.
4. 각 조건의 실제 P99 응답 지연, 오류율, 커넥션 수와 회복 시간을 비교한다.

다음 결과를 산출한다.

- 추천 시간 적중률: 추천 시간이 실제 Safe였는가?
- 잘못된 추천률: 모든 시간이 위험한데도 안전 시간처럼 제시했는가?
- 위험 감소율: 즉시 실행보다 추천 시간 실행에서 운영 영향이 얼마나 감소했는가?
- 후회값: 추천 시간의 실제 영향이 관측상 최적 시간보다 얼마나 큰가?

## 8. 기존 도구 및 실행 방식 비교

다음 배포 정책을 비교한다.

- 별도 검사 없이 즉시 실행
- Squawk 통과 후 즉시 실행
- PostgreSQL 일반 DDL을 MigraGuard가 제시한 시간에 실행
- PostgreSQL 저잠금 방식을 즉시 실행
- PostgreSQL 저잠금 방식과 MigraGuard 시간대 판단을 함께 적용

`gh-ost`와 `pt-online-schema-change`는 MySQL 도구이므로 동일한 PostgreSQL 실험에서 직접 비교하지 않는다. PostgreSQL에서는 `CREATE INDEX CONCURRENTLY`, `NOT VALID` 후 별도 검증, 단계적 `NOT NULL` 적용과 같은 동일 목적의 저잠금 절차를 비교 대상으로 사용한다.

## 9. 기존 시뮬레이션과의 구분

기존 `022~041` DDL과 20개 시나리오 실험은 다음 변화 방향을 확인하는 데 사용한다.

- 부하 증가 시 위험도가 상승하는가?
- 처리 여력 증가 시 위험도가 하락하는가?
- 정적 특성이 같은 DDL도 환경에 따라 등급이 달라지는가?

정답 데이터가 없으므로 기존 시뮬레이션만으로 실제 장애 예측 정확도를 주장하지 않는다.

Config에서 서버 처리 여력의 영향만 확인할 때는 `C_max`, `MuMax`, 디스크 입출력 처리량만 변경하고 등급 임계값과 계산 계수는 고정한다. 정책값까지 함께 변경한 결과는 처리 여력만의 효과가 아니라 환경 프로필 전체의 차이로 해석한다.

## 10. 예상 결과물

- 실험 환경과 운영 기준 정의표
- 예측값과 관측값 비교표 및 산점도
- Safe·Warning·Danger 혼동행렬
- Squawk 통과 여부와 실제 장애 여부 비교표
- 시간대별 예측 등급과 실제 영향 히트맵
- 즉시 실행, 저잠금 방식, 추천 시간 실행 비교 그래프
- 오판 사례와 원인 분석표

실험의 핵심 성공 조건은 Danger가 많이 산출되는 것이 아니다. False Safe가 낮고, 추천 시간 실행이 실제 운영 영향을 줄이며, 각 중간 지표가 관측값을 설명할 수 있어야 한다. 결과가 좋지 않더라도 어느 계산 단계에서 오차가 커졌는지 확인하여 보정 방향을 제시할 수 있다.
