# Forecast 시간대 추천 최적성 검토 실험 결과 - 2026-06-21

## 1. 실험 목적

본 실험의 목적은 MigraGuard가 forecast로 추천한 시간대가 실제 DDL 실행 결과에서도 가장 적합한 시간대인지 확인하는 것이다. 이전 forecast 결과는 각 시간대의 Safe, Warning, Danger 분포를 보여주었지만, 추천 시간이 실제 실행 결과 기준으로 최적인지는 설명하지 못했다. 따라서 본 실험에서는 24개 시간대의 작업 부하를 각각 짧은 벤치마크 조건으로 압축 재현하고, 각 시간대에서 DDL을 실제 실행하여 시간대별 실측 순위를 계산하였다.

검증 질문은 다음과 같다.

> MigraGuard가 추천한 시간대는 실제 DDL 실행 중 P99 응답 지연, 처리량 유지율, DDL 완료 시간, 실패 트랜잭션, 잠금 대기 수를 종합했을 때 최적 또는 상위권 시간대인가?

## 2. 실험 대상 DDL

실험에는 PostgreSQL에서 운영 중 영향을 줄이거나 단계적으로 적용할 수 있는 DDL 유형을 사용하였다. `DROP INDEX CONCURRENTLY`와 `REINDEX CONCURRENTLY`도 후보로 검토하였으나, 현재 MigraGuard parser가 해당 DDL에서 forecast CSV를 생성하지 못해 시간대 추천 정확도 비교 대상에서는 제외하였다.

| ID | 유형 | SQL 특성 | Forecast 추천 |
|---|---|---|---|
| ONLINE-1 | 동시 인덱스 생성 | `CREATE INDEX CONCURRENTLY` | 02:00 Safe |
| ONLINE-2 | 동시 유니크 인덱스 생성 | `CREATE UNIQUE INDEX CONCURRENTLY` | 02:00 Safe |
| ONLINE-3 | 제약조건 단계적 추가 | `ADD CONSTRAINT ... NOT VALID` | 02:00 Safe |
| ONLINE-4 | 지연된 제약조건 검증 | `VALIDATE CONSTRAINT` | 02:00 Safe |

## 3. 실험 방법

실험은 실제 24시간 동안 진행하지 않고, forecast에 포함된 24개 시간대의 예상 TPS를 각각 독립된 부하 조건으로 재현하였다. 각 시간대마다 먼저 DDL 없이 기준선을 측정하고, 동일한 부하 조건에서 DDL을 실행하여 기준선 대비 변화를 계산하였다.

측정 지표는 다음과 같다.

| 지표 | 의미 |
|---|---|
| DDL 실행 중 P99 응답 지연 | 해당 시간대에서 사용자 요청 지연이 얼마나 커졌는지 확인 |
| P99 Ratio | DDL 실행 중 P99를 기준선 P99와 비교 |
| TPS Ratio | DDL 실행 중 처리량이 기준선 대비 유지되었는지 확인 |
| DDL 완료 시간 | DDL 자체가 얼마나 빨리 완료되었는지 확인 |
| 실패 트랜잭션 수 | 실제 요청 실패 여부 확인 |
| 최대 활성 커넥션 및 잠금 대기 수 | 커넥션 압력과 잠금 대기 발생 여부 확인 |

실제 최적 시간대는 다음 기준으로 계산하였다.

> 실제 최적 시간대는 DDL 실행 중 절대 P99 응답 지연이 낮고, 기준선 대비 P99 증가가 작으며, TPS 하락이 작고, DDL 완료 시간이 짧고, 실패 트랜잭션과 잠금 대기가 적은 시간대로 정의하였다.

결과 CSV는 다음 경로에 저장하였다.

- `experiments/benchmark/results/forecast_hourly_optimality_20260621/hourly_optimality_summary.csv`
- `experiments/benchmark/results/forecast_hourly_optimality_20260621/hourly_optimality_operation_ranking.csv`

## 4. 추천 시간대와 실제 순위

MigraGuard는 네 DDL 모두에서 02:00을 Safe 추천 시간으로 제시하였다. 그러나 실측 지표를 종합한 실제 순위에서는 02:00이 최적 시간대와 일치하지 않았다.

| DDL | MigraGuard 추천 시간 | 실제 순위 | Top-3 포함 여부 | P99 | P99 Ratio | DDL 시간 | 해석 |
|---|---|---:|---|---:|---:|---:|---|
| ONLINE-1 | 02:00 | 8위 | X | 4.87ms | 0.96 | 805.28ms | 최적 시간은 아니지만 낮은 위험 후보 |
| ONLINE-2 | 02:00 | 8위 | X | 5.59ms | 1.11 | 1142.92ms | 최적 시간은 아니지만 낮은 위험 후보 |
| ONLINE-3 | 02:00 | 8위 | X | 5.54ms | 1.10 | 338.05ms | 최적 시간은 아니지만 낮은 위험 후보 |
| ONLINE-4 | 02:00 | 6위 | X | 4.48ms | 0.89 | 382.20ms | 최적 시간은 아니지만 낮은 위험 후보 |

따라서 본 실험에서는 MigraGuard가 추천한 02:00이 실제 최적 시간대라고 볼 수 없었다. 특히 04:00, 00:00, 01:00, 05:00 등 인접한 저부하 시간대가 더 좋은 실측 순위를 보인 경우가 많았다. 이는 현재 forecast가 낮은 위험 구간 중 하나를 고르는 데에는 의미가 있지만, 저부하 후보들 사이의 세밀한 우선순위를 정확히 구분하는 수준에는 도달하지 못했음을 보여준다.

## 5. 실제 상위 시간대

각 DDL별 실제 상위 3개 시간대는 다음과 같다.

| DDL | 실제 1위 | 실제 2위 | 실제 3위 |
|---|---|---|---|
| ONLINE-1 | 04:00 | 05:00 | 00:00 |
| ONLINE-2 | 04:00 | 07:00 | 00:00 |
| ONLINE-3 | 00:00 | 04:00 | 01:00 |
| ONLINE-4 | 04:00 | 01:00 | 05:00 |

상위 시간대는 대체로 새벽 또는 이른 오전의 낮은 부하 구간에 분포하였다. 다만 모든 DDL에서 02:00이 1위로 나타나지는 않았다. 이는 1 TPS로 예측된 02:00을 실제 벤치마크에서는 측정 안정성을 위해 최소 10 TPS로 재현한 점, 20초 단위의 짧은 실행에서 발생하는 측정 변동, DB 캐시 및 내부 실행 상태 차이의 영향을 받은 것으로 해석할 수 있다.

## 6. 실제 최악 시간대

각 DDL별 실제 최악 시간대는 주로 forecast에서 높은 부하로 분류한 주간 또는 저녁 피크 구간에 분포하였다.

| DDL | 실제 최악 시간대 | Target TPS | P99 | P99 Ratio | 해석 |
|---|---|---:|---:|---:|---|
| ONLINE-1 | 20:00 | 4361 | 29.38ms | 2.92 | 동시 인덱스 생성도 피크 부하에서는 지연 증가 |
| ONLINE-2 | 21:00 | 3944 | 24.99ms | 4.11 | 동시 유니크 인덱스 생성도 고부하에서 지연 증가 |
| ONLINE-3 | 16:00 | 3330 | 17.10ms | 3.35 | NOT VALID 추가는 빠르지만 피크에서 지연 증가 |
| ONLINE-4 | 11:00 | 4186 | 37.26ms | 5.87 | 검증 단계는 고부하 시간대에서 지연 증가 |

이 결과는 MigraGuard가 최적 시간대를 정확히 맞히지는 못했지만, 실제로 지표가 나쁜 시간대는 대체로 forecast상 위험도가 높은 고부하 구간에 위치했음을 보여준다. 즉 현재 prototype은 최적 시간대 추천보다는 최악 시간대 회피에 더 가까운 성능을 보였다.

## 7. 종합 해석

본 실험 결과를 기준으로 보면 MigraGuard의 forecast 기능은 아직 "최적 시간대를 정확히 맞히는 도구"라고 보기 어렵다. 네 가지 DDL 모두에서 MigraGuard가 추천한 02:00은 실제 순위 6~8위에 머물렀고, Top-3에도 포함되지 않았다. 따라서 추천 시간의 정확도 측면에서는 개선이 필요하다.

다만 실험 결과가 forecast 기능의 의미를 완전히 부정하는 것은 아니다. 실제 상위 시간대는 대부분 낮은 부하 구간에 분포하였고, 실제 최악 시간대는 주간 또는 저녁의 높은 부하 구간에 집중되었다. 따라서 현재 MigraGuard는 정밀한 최적 시간대 선택보다는, 배포 전 단계에서 고위험 시간대를 피하고 낮은 위험 후보군을 좁히는 데 의미가 있다고 해석하는 것이 적절하다.

즉 본 실험의 결론은 다음과 같다.

> MigraGuard의 궁극적인 목표는 최적 실행 시간 추천이지만, 현재 prototype은 최적 시간대를 정확히 맞히는 수준에는 도달하지 못했다. 그러나 시간대별 작업 부하와 DDL 특성을 결합하여 실제로 지표가 악화되기 쉬운 고부하 시간대를 피하고, 상대적으로 낮은 위험 후보 시간대를 제시하는 단계까지는 확인하였다.

## 8. 한계와 개선 방향

- 24개 시간대를 모두 실행했지만 각 조건은 1회씩만 수행하였다. 따라서 반복 실험을 통한 통계적 안정성 검증이 필요하다.
- 실제 24시간 운영 데이터를 사용한 것이 아니라, forecast 시간대별 TPS를 짧은 `pgbench` 실행으로 압축 재현하였다.
- 02:00의 forecast TPS는 1 TPS였지만, 실험에서는 P99 측정 안정성을 위해 최소 10 TPS로 재현하였다.
- 실제 최적 시간대 점수는 본 실험에서 정의한 휴리스틱 기준이며, 서비스별로 P99, TPS, DDL 시간, 잠금 대기 중 어떤 값을 더 중요하게 볼지에 따라 달라질 수 있다.
- `DROP INDEX CONCURRENTLY`와 `REINDEX CONCURRENTLY`는 PostgreSQL 기능으로는 유효하지만 현재 MigraGuard parser가 forecast 결과를 생성하지 못해 이번 정확도 비교에서는 제외하였다.
- 향후에는 시간대별 예상 P99, 부하 변동성, 예상 DDL 수행 시간이 실행 후보 구간 안에 들어가는지 여부, 연속된 안전 구간 길이 등을 반영하여 추천 알고리즘을 개선해야 한다.
