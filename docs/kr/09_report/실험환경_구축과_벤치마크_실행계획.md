# MigraGuard 실험 환경 구축과 벤치마크 실행 계획

## 1. 이 문서에서 확정하는 사항

본 실험은 Windows 데스크탑에서 Docker Desktop을 이용해 격리된 PostgreSQL 환경을 구성하고, `pgbench`로 실제 SQL 트래픽을 발생시키는 방식으로 수행한다.

도구 선택은 다음과 같이 고정한다.

| 역할 | 사용할 도구 | 선택 이유 |
|---|---|---|
| 데이터베이스 | Docker의 PostgreSQL 15 | 현재 `docker-compose.yml` 및 초기 스키마와 동일한 버전이며 반복 초기화가 쉬움 |
| 트래픽 벤치마크 | `pgbench` 사용자 정의 스크립트 | 목표 TPS, 동시 접속 수, 실행 시간, 트랜잭션 로그를 통제할 수 있음 |
| 정적 분석 | Squawk CLI | DDL의 배포 전 정적 검사 기준선 |
| 동적 위험 분석 | MigraGuard CLI 및 Agent | 현재 상태 분석과 시간대별 위험 예측 수행 |
| DB 지표 수집 | PostgreSQL 통계 뷰를 조회하는 SQL 수집 스크립트 | 별도 모니터링 서버 없이 1초 단위 CSV 생성 가능 |
| 요청 지표 수집 | `pgbench` 진행 출력 및 트랜잭션 로그 | 실제 TPS, 지연 시간, 실패 여부 계산 가능 |
| 결과 분석·시각화 | Python, pandas, matplotlib, seaborn | 혼동행렬, 히트맵, 시간대별 그래프 생성 |
| 실험 자동화 | PowerShell | Windows 데스크탑에서 컨테이너 제어, DB 초기화 및 반복 실행 자동화 |

현재 저장소의 자체 LoadGen은 시연과 수동 부하 확인에는 사용할 수 있지만 정식 정확도 실험의 주 부하 발생기로 사용하지 않는다. 현재 LoadGen은 목표 TPS와 종료 시간을 직접 지정할 수 없고, 실제 PC 시각에 따라 부하 강도가 변하며, 요청별 지연 로그를 남기지 않아 동일 조건의 반복과 P99 계산이 어렵기 때문이다.

## 2. 필요한 데스크탑 사양

### 최소 권장 사양

- 운영체제: Windows 10 또는 Windows 11 64비트
- CPU: 4코어 이상
- 메모리: 16GB 이상
- 여유 디스크: 30GB 이상
- 가상화: BIOS에서 CPU 가상화 활성화

### 권장 사양

- CPU: 8코어 이상
- 메모리: 32GB 이상
- 여유 디스크: SSD 50GB 이상
- Docker Desktop 메모리 할당: 8GB 이상

실험 결과에는 CPU 모델, 코어 수, 메모리, 저장장치 종류, Windows 버전 및 Docker Desktop 버전을 기록한다. 실험 중에는 대규모 다운로드, 게임, 영상 인코딩 등 CPU와 디스크를 많이 사용하는 프로그램을 종료한다.

cmd /c npx --yes squawk-cli@2.58.0 experiments\ddl\021_comparison_linter_pass_dynamic_danger.sql

   - 프로젝트와 실험 결과 버전 관리에 사용한다.

## 4. 기존 저장소에서 재사용할 구성

현재 `docker-compose.yml`에는 다음 서비스가 존재한다.

- `db`: PostgreSQL 15와 `pg_stat_statements`
- `agent`: MigraGuard 지표 수집기
- `load-generator`: 기존 자체 LoadGen
- `analyze`: MigraGuard 분석 CLI

`build/postgres/init-db.sql`에는 `users`, `account_balances`, `products`, `inventory_stocks`, `orders`, `order_event_logs` 테이블과 초기 데이터가 정의되어 있다. 실험 DDL도 이 테이블을 대상으로 작성되어 있으므로 기존 스키마를 그대로 사용한다.

기존 초기 데이터는 약 10만 건의 주문과 20만 건의 이벤트 로그를 생성한다. 예비 실험에는 사용할 수 있지만 테이블 재작성과 인덱스 생성의 영향을 관찰하기에는 작을 수 있다. 본 실험 전에는 실제 `pg_total_relation_size`를 측정한 뒤 데이터 크기를 확정하며, 문서에 100GB라고 가정해서 적지 않는다.

## 5. 추가할 벤치마크 컨테이너

`pgbench`가 DB와 같은 컨테이너의 CPU를 직접 사용하면 DB 성능 측정에 영향을 줄 수 있으므로 별도의 벤치마크 컨테이너를 사용한다. `docker-compose.yml`에는 다음과 같은 서비스를 추가할 예정이다.

```yaml
benchmark:
  image: postgres:15
  environment:
    PGPASSWORD: pass
  depends_on:
    db:
      condition: service_healthy
  volumes:
    - ./experiments/benchmark:/work
  entrypoint: ["sleep", "infinity"]
```

이 컨테이너는 PostgreSQL 서버를 실행하지 않고 `psql`과 `pgbench` 클라이언트만 제공한다.

실행 확인 명령은 다음과 같다.

```powershell
docker compose up -d db benchmark
docker compose exec benchmark pgbench --version
docker compose exec benchmark psql -h db -U user -d target_db -c "SELECT version();"
```

## 6. pgbench를 선택한 이유

`pgbench`는 다음 값을 명시적으로 통제할 수 있다.

- `-c`: 동시 클라이언트 수
- `-j`: 작업 스레드 수
- `-T`: 실행 시간
- `-R`: 목표 TPS
- `-f`: 사용자 정의 SQL 트랜잭션 파일
- `-P`: 진행 상황 출력 주기
- `-l`: 요청별 지연 로그 저장
- `--latency-limit`: 허용 지연 시간을 넘긴 트랜잭션 집계

예시 명령은 다음과 같다.

```powershell
docker compose exec -w /work benchmark pgbench `
  -h db -U user -d benchmark_run `
  -n -c 20 -j 4 -T 60 -R 300 -P 1 -l -r `
  -f /work/sql/orders_mixed.sql
```

이 명령은 20개의 동시 클라이언트와 4개의 스레드로 60초 동안 초당 300건을 목표로 사용자 정의 주문 트랜잭션을 실행한다.

### pgbench가 담당하는 역할

`pgbench`는 DDL을 분석하거나 위험 등급을 계산하지 않는다. 여러 가상 사용자가 서비스 쿼리를 반복 실행하는 역할만 담당한다. 실험에서는 다음 세 구성요소를 분리한다.

- MigraGuard: DDL 실행 전 위험과 추천 시간을 예측
- pgbench: 실제 읽기·쓰기 요청을 PostgreSQL에 지속적으로 전송
- psql: pgbench 요청이 실행되는 도중 별도로 DDL 실행

즉 `pgbench` 요청이 정상적으로 처리되던 상태에서 DDL을 실행하고, 그 순간 요청 지연·오류·커넥션이 어떻게 달라지는지를 관찰한다.

### 기본 옵션의 의미

`-R 300`은 초당 정확히 300건이 완료된다는 뜻이 아니라 초당 300건의 트랜잭션 시작을 시도한다는 뜻이다. DB가 요청을 감당하지 못하면 실제 완료 TPS는 낮아지고 지연과 대기 요청이 증가한다. 이 차이가 실험에서 관찰할 과부하 현상이다.

`-c 20`은 동시에 요청을 보낼 수 있는 가상 클라이언트 수이다. 목표 TPS가 높아도 클라이언트 수가 너무 작으면 요청을 충분히 발생시키지 못한다. 반대로 클라이언트 수가 지나치게 크면 실험 시작부터 커넥션이 포화되므로 계단식 부하 시험으로 값을 정한다.

`-j 4`는 부하 발생기 내부에서 클라이언트들을 처리하는 작업 스레드 수이다. `-T 60`은 60초 동안 실행한다는 뜻이며, `-P 1`은 1초마다 진행 상황을 출력한다. `-l`은 각 트랜잭션의 지연 로그를 남기고, `-r`은 사용자 정의 스크립트에 포함된 명령별 지연을 요약한다.

`-n`은 pgbench 기본 테이블을 정리하는 사전 작업을 생략한다. 본 실험은 pgbench 기본 스키마가 아니라 MigraGuard의 `orders`, `order_event_logs`, `inventory_stocks` 등을 사용하므로 반드시 사용자 정의 스크립트와 `-n`을 사용한다. 본 실험에서는 `pgbench -i`로 기본 pgbench 테이블을 생성하지 않는다.

### 한 번의 수동 예비 실험

처음에는 자동화하지 않고 PowerShell 창 세 개를 사용하여 흐름을 확인한다.

1. 첫 번째 창: PostgreSQL과 벤치마크 컨테이너를 실행한다.

```powershell
docker compose up -d db benchmark
```

2. 두 번째 창: 180초 동안 주문 트래픽을 발생시킨다. 180초는 워밍업, DDL 실행 및 회복 관찰 시간을 포함하기 위한 예비 값이다.

```powershell
docker compose exec -w /work benchmark pgbench `
  -h db -U user -d benchmark_run `
  -n -c 20 -j 4 -T 180 -R 300 -P 1 -l -r `
  -f /work/sql/orders_mixed.sql
```

3. 트래픽 시작 후 약 30초 동안 기준 상태를 확인한다.

4. 세 번째 창: MigraGuard의 실행 전 결과를 저장한 뒤 동일한 DB에 DDL을 실행한다.

```powershell
Get-Content -LiteralPath experiments\ddl\대상_DDL.sql -Raw |
  docker compose exec -T db psql -U user -d benchmark_run -v ON_ERROR_STOP=1
```

5. 두 번째 창의 1초 단위 출력에서 DDL 실행 전후의 TPS와 지연 변화를 확인한다.

6. DDL이 끝나도 pgbench를 즉시 종료하지 않고 요청 지연과 처리량이 기준 상태로 돌아오는지 관찰한다.

7. 수동 예비 실험이 성공하면 PowerShell 스크립트가 pgbench 시작, 30초 워밍업, DDL 실행, 회복 관찰 및 CSV 저장을 자동으로 수행하도록 변경한다.

### 시간대 부하 재현 방법

시간대별 실험에서는 SQL 스크립트는 동일하게 유지하고 `-R`과 `-c`를 변경한다.

| 시간대 예시 | 목표 TPS | 클라이언트 | 의미 |
|---|---:|---:|---|
| 02시 | 60 | 8 | 저부하 |
| 10시 | 250 | 20 | 정상 부하 |
| 12시 | 400 | 35 | 점심 피크 |
| 20시 | 500 | 45 | 이벤트 피크 |

각 시간대는 별도의 초기 DB에서 실행한다. 02시 실험이 끝난 뒤 같은 DB에서 바로 10시 실험을 수행하면 앞선 DDL과 데이터 변경의 영향이 남으므로 시간대마다 DB를 복원해야 한다.

## 7. 사용자 정의 트래픽 스크립트

DDL의 대상 테이블과 작업 부하의 대상 테이블이 다르면 잠금과 쿼리 대기를 제대로 관찰할 수 없다. 따라서 실험 DDL이 변경하는 테이블에 실제로 접근하는 트랜잭션을 준비해야 한다.

최소한 다음 스크립트를 작성한다.

| 스크립트 | 주요 대상 | 실행 내용 | 사용하는 DDL 예시 |
|---|---|---|---|
| `orders_mixed.sql` | `orders` | 주문 조회, 상태 갱신, 주문 삽입 | 주문 컬럼 추가, 타입 변경, 인덱스, 제약조건 |
| `logs_write.sql` | `order_event_logs` | 이벤트 로그 삽입과 시간 범위 조회 | 로그 인덱스, 컬럼 변경, `NOT NULL` |
| `stock_update.sql` | `inventory_stocks` | 재고 조회와 수량 갱신 | 재고 인덱스, CHECK, 컬럼 변경 |
| `balance_update.sql` | `account_balances` | 잔액 조회와 갱신 | 잔액 인덱스, 컬럼 및 기본값 변경 |

예를 들어 `orders_mixed.sql`은 다음 구조를 가진다.

```sql
\set user_id random(1, 1000)
\set order_id random(1, 100000)
BEGIN;
SELECT status, total_amount FROM orders WHERE id = :order_id;
UPDATE orders SET status = status WHERE id = :order_id;
COMMIT;
```

실제 스크립트에서는 대상 DDL과 충돌하는 읽기 또는 쓰기 쿼리가 반드시 포함되어야 한다.

## 8. 부하 수준 결정 방법

저부하, 정상 부하 및 피크 부하의 TPS를 임의로 100, 500, 1000처럼 정하지 않는다. 먼저 DDL을 실행하지 않은 상태에서 계단식 부하 시험을 수행한다.

예시:

1. 목표 TPS 50으로 60초 실행
2. 목표 TPS 100으로 60초 실행
3. 목표 TPS 200으로 60초 실행
4. 목표 TPS 300, 400, 500 순서로 증가
5. 각 단계의 실제 TPS, P99, 오류율과 커넥션 사용량 기록

서비스 운영 기준을 유지할 수 있는 최대 처리량을 실험 환경의 `MuMax` 후보로 정한다. 이후 부하 수준은 다음처럼 결정한다.

- 저부하: 측정된 `MuMax`의 약 20~30%
- 정상 부하: 측정된 `MuMax`의 약 50~60%
- 피크 부하: 측정된 `MuMax`의 약 80~90%
- 초과 부하: 필요할 때만 `MuMax`의 100% 이상

이 비율은 실험 시작점이며, 실제 P99와 오류 발생 여부를 확인한 뒤 실험 전에 최종 고정한다.

## 9. 시간대별 작업 부하 구성

시간 추천 검증에는 이전 7일과 검증 대상 1일을 분리한 홀드아웃 방식을 사용한다.

- 이전 7일: MigraGuard가 24시간 위험도를 계산하기 위한 이력
- 검증일 1일: MigraGuard에 미리 보여주지 않고 실제 `pgbench`로 재현할 작업 부하

시간대별 프로필은 CSV로 관리한다.

```csv
hour,target_tps,clients,workload_script,expected_pattern
0,80,10,orders_mixed.sql,low
1,60,8,orders_mixed.sql,low
8,300,25,orders_mixed.sql,commute_peak
12,400,35,orders_mixed.sql,lunch_peak
20,500,45,orders_mixed.sql,event_peak
23,150,15,orders_mixed.sql,normal
```

24시간 전체를 실제 시계에 맞춰 기다리지 않는다. 각 행의 작업 부하를 60초 측정 구간으로 재현한다. 24시간 프로필은 약 24분의 순수 측정 시간과 초기화·안정화 시간으로 압축된다.

시간 추천의 전체 정확도를 평가할 때는 검증일의 실제 TPS를 MigraGuard 예측 입력으로 직접 제공하지 않는다. 이전 7일의 이력만으로 추천 시간을 먼저 저장하고, 이후 검증일 작업 부하를 재현한다.

## 10. 데이터베이스 크기와 초기화

### 데이터 크기

예비 실험은 현재 초기 데이터로 수행한다. 예비 실험에서 모든 DDL이 너무 빨리 끝나 잠금과 지연을 관찰할 수 없다면 다음 단계로 데이터를 늘린다.

- `orders`: 100만 건 이상
- `order_event_logs`: 200만 건 이상
- 실제 크기 기록: `pg_total_relation_size`

행 개수보다 실제 테이블과 인덱스의 바이트 크기를 실험 결과에 기록한다.

### 반복 실행을 위한 초기화

DDL은 스키마를 변경하므로 같은 데이터베이스에서 반복하면 두 번째 실행부터 조건이 달라진다. 기준 DB와 실행 DB를 분리한다.

- `benchmark_base`: 초기 스키마와 데이터를 보관하며 작업 부하를 연결하지 않음
- `benchmark_run`: 각 실험 전에 `benchmark_base`에서 복제하여 생성

초기화 개념은 다음과 같다.

```sql
DROP DATABASE IF EXISTS benchmark_run WITH (FORCE);
CREATE DATABASE benchmark_run TEMPLATE benchmark_base;
```

각 반복 실행은 새로 생성한 `benchmark_run`만 사용한다. 데이터가 커져 DB 복제가 지나치게 오래 걸리면 Docker 볼륨 스냅샷 또는 파일 시스템 복제 방식으로 변경한다.

## 11. 지표 수집 방법

### 요청 지표

`pgbench -l` 로그에서 다음 값을 계산한다.

- 실제 성공 TPS
- 평균 응답 지연
- P95와 P99 응답 지연
- 지연 제한 초과 건수
- 실패 트랜잭션 수

### 데이터베이스 지표

별도 PowerShell 또는 SQL 수집기가 1초마다 다음 쿼리를 실행하고 CSV로 저장한다.

```sql
SELECT
    clock_timestamp() AS observed_at,
    COUNT(*) FILTER (WHERE state = 'active') AS active_connections,
    COUNT(*) FILTER (WHERE wait_event_type = 'Lock') AS lock_waiting_sessions
FROM pg_stat_activity
WHERE datname = 'benchmark_run';
```

추가로 다음을 수집한다.

- `pg_locks`의 미획득 잠금 수
- `pg_stat_database`의 커밋·롤백·충돌·데드락 증가량
- DDL 시작 시각과 종료 시각
- 작업 부하 종료 후 P99와 커넥션이 기준 상태로 돌아온 시각

1차 실험에서는 P99의 실제 정답을 `pgbench` 로그에서 계산한다. `pg_stat_statements` 값은 MigraGuard 입력 및 보조 관측값으로 사용하되 요청별 실제 P99 정답으로 사용하지 않는다.

## 12. 한 번의 실험 실행 순서

각 `DDL × 시간대 × 반복` 조건은 다음 순서로 실행한다.

1. `benchmark_run` DB를 초기 상태로 다시 생성한다.
2. Squawk 결과를 기록한다. 동일 DDL의 Squawk 결과는 최초 1회만 실행해 재사용할 수 있다.
3. MigraGuard가 이전 7일 이력으로 계산한 시간대 예측과 추천 시간을 저장한다.
4. 해당 시간대의 `pgbench` 작업 부하를 시작한다.
5. 30초 동안 워밍업하고 TPS, P99 및 커넥션이 안정되는지 확인한다.
6. 현재 상태를 이용한 MigraGuard 단일 시점 분석 결과를 저장한다.
7. DB 지표 수집을 시작한다.
8. DDL을 실제 실행한다.
9. DDL 실행 중 최소 60초 또는 DDL 종료 시점까지 작업 부하를 유지한다.
10. DDL 종료 후 30~60초 동안 회복 상태를 관찰한다.
11. `pgbench`와 DB 지표 수집을 종료한다.
12. 사전에 정한 운영 기준으로 실제 안전 또는 위험을 판정한다.
13. 결과 CSV를 저장하고 다음 조건으로 이동한다.

## 14. 설치와 구축 순서

실제 작업은 다음 순서로 진행한다.

7. 사용자 정의 SQL 스크립트 작성

10. 1초 단위 지표 수집기 작성
