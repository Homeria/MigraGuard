# 테스트 케이스 확장 실험 설계 - 2026-06-21

## 1. 목적

현재 주요 추진내용의 실측 비교는 대표 DDL 3개와 2개 부하 단계로 구성되어 있다. 이 구성은 MigraGuard의 동작 방향을 보여주는 예비 실험으로는 사용할 수 있지만, DDL 종류와 부하 수준이 제한적이므로 “터질 가능성이 있는 DDL을 얼마나 구별하는가”를 설명하기에는 부족하다.

따라서 테스트 케이스 확장 실험의 목적은 다음 네 가지이다.

1. 정적 위험이 낮은 DDL을 과도하게 위험으로 판단하지 않는지 확인한다.
2. Squawk가 경고하는 DDL을 MigraGuard도 Warning 또는 Danger로 판단하는지 확인한다.
3. 같은 DDL이라도 작업 부하가 커질수록 MigraGuard 위험도가 상승하는지 확인한다.
4. 시간 추천 기능에서 Safe 추천, Warning 조건부 추천, Danger 추천 불가를 구분하는지 확인한다.

이 실험은 통계적으로 완성된 정확도 검증이 아니라, 대표 DDL 유형과 부하 조건을 늘려 현재 모델의 장점과 한계를 더 명확히 보기 위한 확장 벤치마크이다.

## 2. 사용할 DDL

기존 `experiments/ddl` 디렉터리를 확인한 결과, 대부분의 대표 DDL은 이미 존재하였다. 다만 `orders` 테이블을 대상으로 NOT NULL을 직접 설정하는 DDL은 없어서 `042_linter_warning_set_orders_shipping_address_not_null.sql`을 추가하였다.

| ID | 파일명 | DDL 유형 | Squawk 예상 | MigraGuard 기대 | 실험 목적 |
|---|---|---|---|---|---|
| DDL-1 | `022_safe_add_orders_note.sql` | nullable 컬럼 추가 | Pass | Safe에 가까워야 함 | 낮은 위험 DDL의 오탐 확인 |
| DDL-2 | `026_safe_concurrent_orders_composite_index.sql` | 동시 인덱스 생성 | Pass | 부하에 따라 Safe 또는 Warning | Linter 통과 DDL의 동적 위험 확인 |
| DDL-3 | `037_linter_warning_standard_orders_index.sql` | 일반 인덱스 생성 | Warning | Warning 또는 Danger | 쓰기 차단 가능성이 있는 DDL 탐지 |
| DDL-4 | `038_linter_warning_change_order_number_type.sql` | 컬럼 타입 변경 | Warning | Danger | 테이블 재작성 위험 확인 |
| DDL-5 | `042_linter_warning_set_orders_shipping_address_not_null.sql` | NOT NULL 직접 설정 | Warning | Warning 또는 Danger | 기존 데이터 검증 또는 실행 실패 위험 확인 |
| DDL-6 | `040_linter_warning_add_valid_order_check.sql` | CHECK 제약조건 즉시 검증 | Warning | Warning 또는 Danger | 제약조건 검증으로 인한 스캔 위험 확인 |

DDL-1과 DDL-2는 Squawk를 통과하는 비교군이다. DDL-3부터 DDL-6은 Squawk에서 정적 경고가 발생할 수 있는 비교군이다. 모든 DDL은 `orders_mixed` 작업 부하의 중심 테이블인 `orders`를 대상으로 하도록 구성하였다.

## 3. 부하 단계

부하 단계는 Low, Normal, High 세 단계로 구성한다. 기존 실험에서 사용한 1000 TPS와 5000 TPS를 유지하고, 낮은 부하에서의 오탐 여부를 보기 위해 100 TPS를 추가한다.

| 부하 단계 | Target TPS | 목적 |
|---|---:|---|
| Low | 100 | 낮은 부하에서 과도한 경고가 발생하는지 확인 |
| Normal | 1000 | 일반적인 운영 조건에서 등급 변화 확인 |
| High | 5000 | 부하가 큰 조건에서 위험 상승 여부 확인 |

## 4. 반복 횟수와 우선순위

원칙적으로는 각 조건을 3회 반복한다.

`6 DDL × 3 부하 × 3회 = 54회`

시간이 부족하면 다음 순서로 축소한다.

| 우선순위 | 범위 | 이유 |
|---|---|---|
| 1순위 | DDL-1, DDL-2, DDL-3을 3개 부하에서 3회 반복 | 기존 핵심 실험과 직접 연결되는 대표 케이스 |
| 2순위 | DDL-4, DDL-5, DDL-6을 3개 부하에서 1회 실행 | 위험 DDL 유형 확장 확인 |
| 3순위 | DDL-4, DDL-5, DDL-6도 3회 반복 | 반복 측정으로 결과 안정성 확인 |

최소 실행안은 `3 DDL × 3 부하 × 3회 + 3 DDL × 3 부하 × 1회 = 36회`이다.

## 5. 측정 항목

각 실행마다 다음 값을 기록한다.

| 항목 | 의미 |
|---|---|
| Squawk 결과 | DDL 자체의 정적 검사 결과 |
| MigraGuard 사전 등급 | 실행 전 작업 부하 기반 위험 판단 |
| Target TPS | 목표 요청량 |
| Actual TPS | 실제 처리량 |
| Baseline P99 | DDL 없는 상태의 P99 응답 지연 |
| DDL 실행 중 P99 | DDL 실행 중 관측한 P99 응답 지연 |
| P99 Ratio | `DDL 실행 중 P99 / Baseline P99` |
| 실패 트랜잭션 수 | 명확한 사용자 요청 실패 신호 |
| DDL 실행 성공 여부 | DDL 자체의 성공, 실패 또는 timeout 여부 |
| 실측 판정 | 본 실험 기준의 Safe, Warning, Danger |

## 6. 실측 판정 기준

실측 판정은 보편적인 장애 정답 라벨이 아니라 본 실험을 위한 임시 기준이다.

| 실측 판정 | 기준 |
|---|---|
| Safe | DDL 성공, 실패 트랜잭션 없음, P99 Ratio 2 미만 |
| Warning | DDL 성공, 실패 트랜잭션 없음, P99 Ratio 2 이상 10 미만 |
| Danger | DDL 실패, timeout, 실패 트랜잭션 발생, 또는 P99 Ratio 10 이상 |

이 기준은 실제 서비스별 SLO를 반영한 절대 기준이 아니므로, 보고서에서는 “실험 판정 기준”으로 제한하여 사용한다.

## 7. 시간 추천 실험 확장

시간 추천은 별도 세트로 구성한다. 목표는 추천 시간이 Safe, Warning 조건부, Danger 추천 불가로 나뉘는지 확인하는 것이다.

| 케이스 | DDL | 기대 결과 | 확인할 내용 |
|---|---|---|---|
| Forecast-1 | DDL-2 | Safe 추천 시간 존재 | 동시 인덱스 생성은 낮은 부하 시간에서 일반 추천 가능한지 확인 |
| Forecast-2 | DDL-3 | Warning 조건부 추천 | 일반 인덱스 생성은 낮은 부하라도 안전하다고 단정하지 않는지 확인 |
| Forecast-3 | DDL-4 또는 DDL-5 | Danger만 존재하거나 추천 불가 | 강한 재작성·검증 DDL은 시간 변경만으로 해결되지 않는지 확인 |

## 8. 내일 실행 순서

1. benchmark DB를 초기화한다.
2. DDL 없는 기준선을 100, 1000, 5000 TPS에서 측정한다.
3. DDL-1부터 DDL-6까지 각 부하에서 1회씩 실행한다.
4. 실행 실패 또는 DDL 충돌이 있는 케이스를 확인한다.
5. DDL-1, DDL-2, DDL-3 핵심 케이스를 3회 반복한다.
6. 시간이 남으면 DDL-4, DDL-5, DDL-6도 3회 반복한다.
7. Forecast-1, Forecast-2, Forecast-3을 실행한다.
8. 결과 CSV와 Markdown을 정리한다.
9. 주요 추진내용의 표, 그래프, 해석 문단을 갱신한다.

## 9. 보고서에서 주장 가능한 수준

이 확장 실험으로 주장할 수 있는 내용은 다음 정도로 제한한다.

> 제한된 대표 DDL과 부하 조건에서 MigraGuard는 일반 인덱스 생성, 컬럼 타입 변경, NOT NULL 직접 설정, 제약조건 즉시 검증처럼 실제 P99 지연 또는 실행 실패 위험이 커질 수 있는 DDL을 Warning 또는 Danger로 분류하는 경향을 보였다. 반면 일부 단순 DDL에서는 보수적 오탐이 발생할 수 있어, 실제 운영 적용을 위해서는 임계값과 잠금 영향도의 보정이 필요하다.

반대로 다음과 같은 표현은 피한다.

- MigraGuard의 정확도가 검증되었다.
- MigraGuard가 장애를 예측한다.
- 모든 DDL 유형에서 기존 도구보다 우수하다.
