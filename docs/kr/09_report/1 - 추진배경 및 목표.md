가. DDL 마이그레이션 위험이 운영 장애로 확대되는 과정

서비스 기능과 데이터 구조가 변경되면 이를 데이터베이스에 반영하기 위한 데이터 정의 언어(Data Definition Language, DDL) 마이그레이션이 필요하다. 개발자, 데이터베이스 관리자(Database Administrator, DBA) 및 사이트 신뢰성 엔지니어(Site Reliability Engineer, SRE)는 새로운 DDL을 운영 데이터베이스에 적용하기 전에 해당 변경을 지금 실행할 수 있는지, 부하가 낮은 시간대로 연기해야 하는지, 서비스 중단 또는 온라인 변경 전략이 필요한지를 결정해야 한다. 이때 SQL 문법이 올바르고 테스트 데이터베이스에서 정상적으로 실행되었다는 사실은 데이터베이스 관리 시스템(Database Management System, DBMS)이 해당 변경을 처리할 수 있다는 의미이지만, 운영 중인 데이터베이스가 실행 과정에서 발생하는 잠금과 부하를 감당할 수 있다는 의미는 아니다.

DDL의 운영 위험은 작업 방식에서 시작된다. `ALTER TABLE`, 컬럼 타입 변경, 인덱스 생성, 제약조건 추가 등의 작업은 서로 다른 수준의 잠금, 테이블 재작성(Table Rewrite), 인덱스 구축 또는 기존 데이터 검증을 요구한다. 테이블 재작성과 인덱스 구축은 대상 테이블의 데이터를 읽거나 다시 기록하므로 데이터 규모가 클수록 작업 시간이 길어진다. 작업 시간이 길어지면 잠금과 자원 사용이 지속되는 시간도 증가하고, 같은 테이블에 접근하는 운영 쿼리가 영향을 받을 가능성이 커진다.

DDL과 충돌한 쿼리가 대기하면 애플리케이션 요청은 데이터베이스의 응답을 기다리는 동안 커넥션을 계속 점유한다. 이 상태에서 새로운 요청이 유입되면 활성 커넥션(Active Connection)에 대기 요청이 누적되고 커넥션 풀(Connection Pool)의 여유가 감소한다. 현재 점유된 커넥션에 새 요청이 더해지면서 전체 커넥션 수요가 최대 허용 범위에 가까워지는데, 이 정도를 커넥션 압력(Connection Pressure)이라고 한다. 커넥션 압력이 한계에 도달하면 새로운 요청은 커넥션을 얻지 못하고 대기하거나 실패한다. 결과적으로 하나의 DDL에서 시작된 잠금이 쿼리 응답 지연, 커넥션 풀 고갈, 타임아웃 및 사용자 요청 실패로 확대될 수 있다. 이러한 영향은 일부 느린 요청에서 먼저 나타날 수 있으므로, 전체 요청의 99%가 해당 시간 이내에 완료되는지를 나타내는 P99 응답 지연(P99 Latency)을 통해 확인할 수 있다.

DDL이 종료된 이후에도 이미 대기 중인 요청은 남아 있으므로 시스템이 즉시 정상 상태로 돌아오는 것은 아니다. 데이터베이스의 최대 처리량이 요청 유입량보다 충분히 크면 누적 요청을 처리하여 정상 상태로 회복할 수 있다. 반대로 요청 유입량이 처리량과 비슷하거나 이를 초과하면 DDL이 끝난 뒤에도 지연이 지속되거나 정상 상태로 회복하지 못할 수 있다. 또한 대규모 데이터 변경으로 디스크 입출력(Disk I/O)과 미리 쓰기 로그(Write-Ahead Logging, WAL) 처리량이 증가하면 복제 데이터베이스가 원본의 변경을 따라가지 못해 반영이 늦어지는 복제 지연(Replication Lag)이 커질 수 있다.

이러한 위험은 테스트 데이터베이스에서 충분히 드러나지 않을 수 있다. 테스트 환경은 운영 환경보다 데이터 규모가 작고 동시에 실행되는 요청과 커넥션 점유가 적으며, 실제 초당 처리 요청 수(Transactions Per Second, TPS), P99 응답 지연 및 복제 지연을 충분히 재현하지 못하는 경우가 많다. 따라서 테스트 환경에서 짧은 시간 안에 정상 종료된 DDL도 운영 환경에서는 더 큰 테이블과 동시 요청으로 인해 쿼리 대기와 커넥션 압력을 발생시킬 수 있다.

결국 DDL의 운영 위험은 SQL 자체에만 고정된 속성이 아니라 DDL의 작업 방식, 대상 테이블의 크기, 실행 시점의 요청량, 커넥션 여유 및 서버 처리 여력이 결합되어 결정된다. 운영자가 필요로 하는 것은 DDL이 일반적으로 위험한지를 알려주는 데서 끝나는 정보가 아니다. 현재 시점에 실행할 수 있는지, 실행하기 어렵다면 어느 시간대에 실행하는 것이 가장 적합한지, 적합한 시간대가 없다면 어떤 대체 전략을 검토해야 하는지를 결정할 수 있는 근거가 필요하다.

나. DDL 마이그레이션 전략과 선택 기준

DDL 마이그레이션 전략은 크게 중단 마이그레이션과 무중단 마이그레이션으로 나눌 수 있다. 중단 마이그레이션은 일정 시간 사용자 트래픽을 차단한 뒤 변경을 적용하는 방식이고, 무중단 마이그레이션은 서비스 요청을 계속 처리하면서 변경을 적용하는 방식이다.

다만 실제 운영 사례에서 무중단 마이그레이션은 하나의 단일한 절차라기보다 여러 제한적·단계적 패턴을 포함하는 상위 개념에 가깝다. 본 보고서에서는 서비스 요청을 유지한 채 변경을 수행하는 전체 전략을 무중단 마이그레이션으로, 그 내부에서 적용 범위·실행 시점·전환 단계를 나누어 위험을 줄이는 방식을 제한적·단계적 무중단 패턴으로 구분하였다.

1) 중단 마이그레이션: 단순하지만 항상 선택 가능한 방식은 아님

중단 마이그레이션은 점검 시간(Maintenance Window) 동안 사용자 트래픽을 차단한 뒤 DDL을 실행하는 방식이다. 운영 요청과 DDL이 동시에 실행되지 않으므로 잠금 경합과 요청 누적을 줄일 수 있고, 작업 절차와 실패 시 롤백(Rollback) 경로를 통제하기 쉽다. 대상 테이블이 작고 예상 작업 시간이 짧으며 비핵심 서비스처럼 일정 시간의 중단을 허용할 수 있다면, 복잡한 온라인 변경 절차를 도입하는 것보다 중단 방식이 단순하고 안전할 수 있다.

그러나 중단 방식의 기술적 단순성이 항상 실제 선택 가능성을 의미하지는 않는다. 핵심 조건은 예상 마이그레이션 시간이 서비스가 허용할 수 있는 중단 시간보다 긴지, 그리고 변경 작업 동안 사용자 요청을 실제로 차단할 수 있는지이다. 주문, 결제 및 예약처럼 중단이 거래 실패로 직접 이어지는 서비스, 대용량 테이블의 작업 시간이 점검 가능 시간을 초과하는 환경, 여러 지역에서 지속적인 요청이 발생하여 공통 점검 시간을 확보하기 어려운 서비스에서는 중단 마이그레이션만으로 요구사항을 만족시키기 어렵다. 이러한 조건에서는 서비스 요청을 유지한 채 변경을 적용하는 무중단 마이그레이션을 대안으로 검토해야 한다.

2) 무중단 마이그레이션: 중단 비용을 줄이지만 복잡성을 만든다

무중단 마이그레이션은 사용자 요청을 계속 처리하면서 데이터 구조를 변경하는 방식이다. 이는 항상 우선적으로 선택해야 하는 방식이라기보다, 점검 시간을 확보하기 어렵거나 허용 가능한 중단 시간이 예상 작업 시간보다 짧은 경우에 고려할 수 있는 전략이다. 즉 중단 마이그레이션이 기술적으로 단순하더라도, 서비스 특성상 공통 점검 시간을 확보할 수 없다면 운영자는 사용자 요청을 유지한 상태에서 변경을 수행하는 방식을 검토해야 한다.

이러한 무중단 마이그레이션의 필요성을 보여주는 사례로 Stripe의 「Online migrations at scale」을 들 수 있다. Stripe는 수억 개의 구독 객체를 변경해야 했지만 사용자의 거래가 지속해서 발생했기 때문에 계획된 점검 시간에 서비스를 중단하지 않고 모든 서비스를 운영한 상태에서 마이그레이션을 수행하였다. 또한 하나의 객체를 처리하는 데 1초가 걸린다고 가정하면 1억 개의 객체를 순차적으로 처리하는 데 3년 이상이 필요하다는 예를 제시하였다. 이 사례의 요지는 서비스 규모가 크면 무조건 무중단 방식을 사용해야 한다는 것이 아니다. 예상 작업 시간이 허용 가능한 중단 시간을 초과하고, 작업이 진행되는 동안 사용자 요청도 중단할 수 없다면 중단 방식은 실제 선택지가 될 수 없다는 것이다. 따라서 `예상 마이그레이션 시간 > 허용 가능한 중단 시간`이고 서비스를 계속 운영해야 하는 조건에서 무중단 마이그레이션은 기술적 선호가 아니라 운영 요구사항이 된다.

그러나 무중단 마이그레이션은 단순히 서비스를 켜 둔 상태에서 DDL을 실행하는 방식이 아니다. Stripe는 기존 구조와 신규 구조에 동시에 데이터를 기록하고, 기존 데이터를 백필(Backfill)한 뒤, 읽기와 쓰기 경로를 순차적으로 전환하고, 마지막에 기존 구조를 제거하는 네 단계의 절차를 사용하였다. 추가 쓰기가 운영 데이터베이스에 미칠 영향을 줄이기 위해 적용 비율을 점진적으로 높이고 운영 지표를 관찰하였다. 이 절차가 보여주는 요지는 무중단 방식이 위험을 제거하는 것이 아니라, 서비스 중단 위험을 구·신 구조의 동시 운영과 데이터 정합성 관리 위험으로 전환한다는 것이다. 따라서 점검 시간을 확보할 수 있고 중단에 따른 영향이 작다면 절차가 단순한 중단 방식을 우선할 수 있다. 반대로 서비스 중단으로 발생하는 거래 실패와 가용성 저하가 단계적 전환의 구현 및 운영 부담보다 크다면 무중단 방식을 선택하는 것이 타당하다.

3) 제한적·단계적 무중단 패턴: 한 번에 전환하기 어려울 때의 절충안

제한적·단계적 무중단 패턴은 무중단 마이그레이션을 수행할 때 전체 시스템을 한 번에 전환하지 않고 변경 범위, 적용 시점 또는 트래픽 전환 단계를 나누어 적용하는 방식이다. 이는 중단 마이그레이션과 무중단 마이그레이션에 병렬로 놓이는 별도의 제3 전략이라기보다, 무중단 마이그레이션 내부에서 위험을 줄이기 위해 사용하는 운영 패턴에 가깝다. 예를 들어 애플리케이션 배포와 DDL 실행 시점을 분리하는 방식, 일부 인스턴스나 일부 트래픽에 먼저 변경을 적용한 뒤 점진적으로 확대하는 방식, 새 컬럼 또는 새 테이블을 추가한 뒤 읽기·쓰기 경로를 단계적으로 전환하는 방식, 대용량 데이터 변경을 작은 단위로 나누어 처리하는 방식 등이 있다. 공통점은 전체 서비스를 한 번에 중단하거나 모든 요청을 즉시 신규 구조로 전환하지 않고, 변경의 적용 범위를 나누어 위험을 줄인다는 점이다.

이 중 애플리케이션 배포와 DDL 실행 시점을 분리하는 사례로 GitLab 공식 문서의 「Post Deployment Migrations」를 들 수 있다. 이 방식은 모든 DDL에 적용되는 일반적인 방법이라기보다, 애플리케이션 코드가 의존하던 컬럼이나 구조를 단계적으로 제거할 수 있는 변경에 적합하다. 예를 들어 기존 애플리케이션 코드가 특정 컬럼을 읽거나 쓰는 상태에서 해당 컬럼을 바로 삭제하면, 아직 이전 버전으로 동작 중인 인스턴스에서 오류가 발생할 수 있다. 이를 피하기 위해 먼저 해당 컬럼에 의존하지 않는 새 애플리케이션 버전을 배포하고, 모든 인스턴스가 새 버전으로 전환된 이후에 컬럼 삭제와 같은 데이터베이스 마이그레이션을 수행한다. 즉 애플리케이션 배포와 DDL 실행 시점을 분리하여, 구버전 코드가 더 이상 해당 컬럼에 의존하지 않는 상태를 만든 뒤 DB 구조를 변경하는 방식이다.

이 사례의 요지는 제한적·단계적 패턴이 모든 DDL을 안전하게 만드는 단일 방법이라는 뜻이 아니라, 변경의 종류에 따라 배포 순서와 적용 범위를 나누어 전체 중단 없이 호환성 위험을 줄일 수 있다는 점이다. 다만 이러한 방식도 단계별 완료 상태, 구버전과 신버전의 공존 가능성, 데이터 정합성 및 롤백 경로를 함께 관리해야 하므로 운영 복잡도가 증가한다.

4) DBMS 레벨 온라인 변경 기능: 차단을 줄이지만 부하를 제거하지는 않음

제한적·단계적 무중단 패턴을 애플리케이션 배포 절차로 구성하는 방법 외에도, 일부 DBMS는 특정 DDL의 차단을 줄이는 온라인 실행 기능을 제공한다. PostgreSQL의 `CREATE INDEX CONCURRENTLY`가 대표적인 예이다. 개발자나 DBA가 별도의 이중 쓰기, 백필, 트래픽 전환 절차를 직접 설계하는 방식은 아니지만, DBMS가 인덱스 생성 중 쓰기 차단을 줄여 제한적 무중단에 가까운 실행을 가능하게 한다. PostgreSQL 공식 문서 「CREATE INDEX」는 일반 인덱스 생성이 완료될 때까지 대상 테이블의 쓰기를 차단하지만, `CONCURRENTLY` 옵션은 인덱스 생성 중에도 `INSERT`, `UPDATE`, `DELETE`를 허용한다고 설명한다.

이 점에서 DBMS 레벨 온라인 변경 기능은 앞서 설명한 제한적·단계적 무중단 패턴과 같은 문제의식을 공유한다. 구현 방식은 다르지만, 두 방식 모두 운영 요청을 완전히 차단하지 않은 상태에서 변경 작업을 수행한다. 따라서 강한 차단을 줄일 수는 있어도 변경 작업이 사용하는 CPU, 디스크 입출력, 트랜잭션 대기 및 복제 지연 가능성까지 사라지는 것은 아니다.

실제로 `CONCURRENTLY`를 사용한다고 해서 인덱스 생성 비용이 사라지는 것은 아니다. 동시 인덱스 생성은 테이블을 두 번 스캔하고 관련된 기존 트랜잭션의 종료를 기다려야 하므로 더 많은 작업이 필요하고 완료 시간도 길어진다. 추가 CPU와 디스크 입출력 부하로 다른 쿼리가 느려질 수도 있다. 이 사례의 요지는 온라인 변경 기능이 마이그레이션 위험을 제거하는 것이 아니라, 짧고 강한 쓰기 차단을 더 긴 시간의 자원 사용과 운영 부하로 전환한다는 것이다.

5) 전략 선택의 공통 조건

전략 선택은 결국 서비스 중단 비용과 온라인 변경 위험의 비교로 정리할 수 있다. 대상 테이블이 작고 예상 작업 시간이 허용 중단 시간 안에 있으며 점검 시간을 확보할 수 있다면 중단 마이그레이션을 선택할 수 있다. 반대로 예상 작업 시간이 허용 중단 시간을 초과하거나, 주문·결제처럼 사용자 요청을 멈추기 어려운 서비스라면 무중단 마이그레이션을 검토해야 한다. Stripe 사례는 이러한 조건에서 중단 방식이 실제 선택지가 되기 어렵다는 점을 보여준다.

무중단 마이그레이션을 선택하더라도 모든 변경을 한 번에 적용할 필요는 없다. 구·신 구조를 함께 운영하거나, 애플리케이션 배포와 DDL 실행 시점을 분리하거나, 일부 트래픽부터 점진적으로 전환하는 방식처럼 제한적·단계적 패턴을 사용할 수 있다. GitLab 사례는 애플리케이션 배포와 데이터베이스 변경 시점을 분리하여 호환성 위험을 줄일 수 있음을 보여준다. 또한 PostgreSQL의 `CONCURRENTLY`처럼 DBMS가 일부 온라인 변경 기능을 제공하는 경우도 있다.

그러나 중단을 피하거나 차단을 줄이는 방법을 선택했다는 사실만으로 안전이 보장되지는 않는다. 제한적·단계적 패턴과 DBMS 레벨 온라인 변경 기능은 운영 요청을 유지한 채 변경 작업을 수행하므로, 쿼리 지연, 자원 경쟁, 트랜잭션 대기 및 복제 지연이 발생할 수 있다. 따라서 어떤 전략을 선택하더라도 DDL의 작업 방식, 예상 작업 시간, 실행 시점의 요청량, 커넥션 여유 및 서버 처리 여력을 함께 확인해야 한다는 공통 조건이 남는다.

이 공통 조건은 전략 선택을 단순히 “중단할 것인가, 무중단으로 할 것인가”의 문제로만 볼 수 없게 만든다. 운영자는 현재 실행해도 되는지, 더 낮은 부하 시간대로 연기해야 하는지, 일반 DDL로 충분한지 또는 온라인 변경 방법을 검토해야 하는지를 판단해야 한다. 이를 위해 기존 도구가 수행하는 역할과 실행 전 의사결정에 어떤 공백이 남아 있는지를 살펴볼 필요가 있다.

다. 기존 도구의 역할과 배포 전 동적 영향 판단의 공백

앞서 정리한 마이그레이션 전략을 선택하려면 DDL 자체의 위험, 실행 시점의 데이터베이스 상태 및 변경 작업 중의 부하를 함께 고려해야 한다. 이 정보는 DDL 린터(Linter), 애플리케이션 성능 관리(Application Performance Monitoring, APM) 및 모니터링 도구, 온라인 스키마 변경(Online Schema Change, OSC) 도구에서 서로 다른 시점과 목적으로 다루어진다.

DDL 린터는 배포 전에 마이그레이션 SQL을 검사한다. 문법 오류, 파괴적 명령어(Destructive Command), 안전하지 않은 인덱스 생성(Unsafe Index), 컬럼 및 제약조건 변경 등을 정적 규칙과 비교하여 위험한 DDL 패턴을 사전에 탐지한다. 실제 데이터베이스에 변경을 적용하지 않고도 빠르고 일관된 검사가 가능하지만, 분석 대상이 SQL의 구조와 사전에 정의된 규칙에 한정되므로 같은 DDL이 오전의 저부하 환경과 이벤트 시간대의 고부하 환경에서 서로 다른 영향을 발생시키는지는 판단하지 않는다.

APM 및 모니터링 도구는 운영 중인 시스템의 요청량, 응답 지연, 커넥션 수, 오류율 및 복제 지연을 지속적으로 관찰한다. 이를 통해 배포 전의 현재 상태를 확인하고 배포 중 또는 배포 이후에 발생한 성능 저하와 장애 징후를 탐지할 수 있다. 그러나 특정 DDL이 아직 실행되지 않은 상태에서는 해당 DDL로 인해 쿼리 대기와 커넥션 수요가 얼마나 증가할지를 실제 관측값만으로 확인할 수 없다. 즉 현재 데이터베이스가 얼마나 바쁜지는 알 수 있지만, 해당 변경을 적용했을 때의 상태는 별도의 사전 추정이 필요하다.

OSC 도구는 서비스 요청을 유지하면서 대용량 테이블의 구조를 변경하기 위한 실행 도구이다. 대표적인 테이블 복사 방식의 OSC 도구는 변경된 스키마를 가진 새 테이블을 만들고, 원본 테이블의 기존 데이터를 작은 단위로 복사하면서 복사 도중 발생하는 `INSERT`, `UPDATE`, `DELETE`도 새 테이블에 반영한다. 기존 데이터와 변경분의 동기화가 완료되면 원본 테이블을 새 테이블로 전환한다. 이 방식은 원본 테이블을 한 번에 다시 작성하는 대신 복사 작업을 장시간에 분산하여 읽기와 쓰기 차단을 줄인다. 일부 도구는 복제 지연이나 서버 부하가 커질 때 복사 속도를 낮추거나 작업을 일시 중지한다. 그러나 새 테이블을 위한 추가 저장 공간, 장시간의 디스크 입출력, 변경분 동기화 및 최종 전환 과정이 필요하므로 실행 위험이 완전히 사라지는 것은 아니다.

GitHub의 `gh-ost`는 MySQL을 위한 트리거 없는 OSC 도구이다. 일반적인 OSC 도구는 원본 테이블에 데이터가 추가되거나 수정될 때마다 트리거를 실행하여 같은 변경 내용을 새 테이블에도 반영한다. 반면 `gh-ost`는 원본 테이블에 트리거를 만들지 않고, MySQL이 기록해 둔 바이너리 로그를 읽어 새 테이블에 같은 변경 내용을 따라 적용한다. 따라서 원본 테이블에 직접 트리거를 추가하지 않고도, 기존 데이터 복사 중에 발생한 변경분을 새 테이블에 반영할 수 있다. 이 구조를 통해 데이터 복사와 변경분 반영을 실제 서비스의 쓰기 부하와 분리하여 제어하고, 필요하면 마이그레이션을 일시 중지하거나 실행 중 설정을 변경할 수 있다. 부하가 높을 때는 처리를 제한하고 최종 테이블 전환 시점도 연기할 수 있다. 또한 GitHub는 운영 적용 전에 복제본에서 동일한 변경 과정을 시험하고 원본과 결과를 비교하도록 권장한다. 따라서 `gh-ost`는 동적 지표를 활용해 실행 중인 마이그레이션의 영향을 완화할 수 있지만, 작업을 시작하기 전에 어느 시간대가 더 안전한지까지 직접 판단하는 도구는 아니다.

[표 1. 기존 도구와 MigraGuard의 판단 시점 비교]

| 구분 | 주로 사용하는 시점 | 주로 보는 정보 | 수행하는 역할 | 남는 판단 공백 |
|---|---|---|---|---|
| DDL 린터 | 배포 전 | SQL 구조, 정적 규칙, 위험한 DDL 패턴 | 문법 오류, 파괴적 명령어, 안전하지 않은 인덱스 생성 등 사전 탐지 | 현재 요청량, 커넥션 점유, 응답 지연 등 실행 시점 부하를 반영하기 어려움 |
| APM 및 모니터링 도구 | 배포 전 상태 확인, 배포 중·후 관찰 | 요청량, 응답 지연, 커넥션 수, 오류율, 복제 지연 | 현재 시스템 상태와 배포 이후 성능 저하 감지 | 아직 실행하지 않은 DDL이 만들 잠금, 대기, 커넥션 압력을 직접 예측하지 않음 |
| OSC 도구 | 배포 중 | 복제 지연, 서버 부하, 복사 진행 상태 | 온라인 변경 중 복사 속도 제한, 일시 중지, 전환 제어 | 작업 시작 전에 어느 시간대가 더 안전한지 판단하기 어려움 |
| MigraGuard | 배포 전 | DDL 정적 특성, 시간대별 요청량, 응답 지연, 커넥션 여유, 처리 여력 | 실행 전 위험도 계산과 실행 시간대 후보 제시 | 실제 실행 제어 도구는 아니며, 계산 결과는 실측 기반 보정이 필요함 |

정리하면 기존 도구들은 각 단계에서 필요한 정보를 제공하지만, DDL의 예상 영향과 실행 전의 동적 지표를 하나의 판단 과정에서 결합하지는 않는다. 그 결과 운영자는 정적 검사 결과와 여러 모니터링 지표를 직접 해석하여 현재 실행할지, 더 낮은 부하 시간대로 연기할지, 온라인 변경 전략을 사용할지를 경험적으로 결정해야 한다.

즉 기존 흐름에서 충분히 다루어지지 않는 부분은 다음과 같은 실행 전 판단이다.

- 현재 시간에 일반 방식으로 실행할 수 있는가?
- 이후 더 안전한 연속 시간 구간이 존재하는가?
- 일반 실행에 적합한 구간이 없다면 중단 또는 온라인 변경 방법이 필요한가?
- 추천 결과를 뒷받침한 위험 요인은 무엇인가?

따라서 본 프로젝트가 주목한 지점은 새로운 린터나 실행 도구 자체가 아니라, 위 질문에 답하기 위해 필요한 배포 전 판단 과정이다. DDL의 정적 특성과 시간대별 운영 지표를 함께 사용한다면, 실행 전 위험도를 계산하고 일반 실행이 가능한 시간대와 중단 또는 온라인 변경 전략을 검토해야 하는 상황을 구분할 수 있을 것이라고 보았다.

라. 프로젝트 목표와 범위

이러한 문제의식을 바탕으로 본 프로젝트는 DDL 마이그레이션을 실행하기 전에 해당 변경을 지금 적용해도 되는지, 더 낮은 부하 시간대로 미뤄야 하는지, 또는 중단·온라인 변경 전략을 검토해야 하는지를 판단하는 보조 도구를 목표로 설정하였다. 구체적으로는 DDL 자체의 작업 특성과 시간대별 데이터베이스 상태를 함께 반영하여 실행 전 위험도를 계산하고, 최적에 가까운 실행 시간대와 판단 근거를 제시할 수 있는지 확인하고자 하였다.

주요 사용자는 운영 데이터베이스에 DDL을 배포하는 개발자, 데이터베이스 관리자 및 사이트 신뢰성 엔지니어로 보았다. 이들이 정적 검사 결과와 모니터링 지표를 개별적으로 해석하는 데만 의존하지 않고, 실행, 연기, 중단 또는 온라인 변경 전략을 검토할 수 있도록 정량적인 판단 근거를 제공하는 것이 프로젝트의 핵심 목표이다.

본 프로젝트의 범위는 실제 마이그레이션을 시작하기 전의 위험 평가와 실행 시간대 추천까지로 한정하였다. 즉 DDL을 직접 실행하거나, OSC처럼 실행 중 복사 속도를 조절하거나 작업을 일시 중지하는 기능을 만드는 것이 아니라, 실행 전에 위험을 판단하고 적절한 실행 시점을 검토하는 의사결정 보조 기능에 초점을 두었다.
