본 프로젝트는 DDL 마이그레이션에서 사용자가 배포 전에 내려야 할 의사결정을 구체화하고, 그 판단에 필요한 지표와 계산 과정을 단계적으로 구성하는 방식으로 추진하였다. 먼저 DDL 실행 여부와 실행 시간대 선택이라는 문제를 정의한 뒤, DDL 위험이 운영 환경에서 어떻게 확산되는지 정리하였다. 이후 선행 연구와 공식 문서를 검토하여 정적·동적 지표를 선정하고, 이를 바탕으로 5단계 위험 지표 산출 과정, 위험 등급 해석 기준, 시간대별 실행 시간 추천 과정을 구성하였다. 마지막으로 제안한 판단 과정을 프로토타입으로 구현하고, PostgreSQL과 `pgbench` 기반 부하 시험을 통해 사전 판단을 실제 DDL 실행 결과와 비교하였다.

가. 문제 및 사용자 의사결정 정의

추진 배경에서 확인한 판단 공백을 바탕으로, 본 프로젝트는 DDL 마이그레이션의 배포 전 판단 대상을 “운영 중인 DB가 해당 변경의 영향을 감당할 수 있는가”로 설정하였다. SQL 실행 가능 여부는 기본 전제이며, 실제 배포 판단에는 DDL 자체의 작업 방식과 실행 시점의 작업 부하가 함께 반영되어야 한다. PostgreSQL에서 `ALTER TABLE`, 인덱스 생성, 컬럼 타입 변경, 제약조건 추가와 같은 DDL은 잠금, 테이블 재작성, 쿼리 대기, 커넥션 풀 고갈 및 복제 지연과 연결될 수 있다. 이때 DDL의 정적 특성은 변경이 어떤 방식으로 DB에 영향을 줄 수 있는지를 설명하고, 실행 시점의 요청량과 커넥션 여유는 현재 환경이 그 영향을 감당할 수 있는지를 설명한다.

따라서 본 프로젝트에서는 DDL의 정적 위험과 실행 시점의 DB 상태를 결합하여 다음 사항을 배포 전에 판단하는 것을 문제의 범위로 설정하였다.

- 해당 DDL을 현재 작업 부하에서 실행할 수 있는가?
- 현재 실행하기 어렵다면 어느 시간대에 실행하는 것이 가장 적합한가?
- 일반 실행에 적합한 시간대가 없다면 DDL 분할, 중단 또는 온라인 변경 전략을 검토해야 하는가?
- 최종 등급이 산출된 원인은 DDL 수행 시간, 쿼리 영향, 커넥션 부족 또는 회복 지연 중 무엇인가?

배포 전 동적 영향 판단은 현재 상태 또는 시간대별 예상 작업 부하에 DDL의 예상 영향을 적용하여, 실행 이후의 상태를 미리 가늠하는 과정으로 보았다. 이를 통해 MigraGuard는 배포 가능 여부를 자동으로 확정하기보다, 실행, 연기 또는 대체 전략 검토에 필요한 판단 근거를 제공하는 것을 목표로 하였다.

나. DDL 위험 전파 과정 정의

DDL의 작업 시간만으로는 배포 가능 여부를 결정할 수 없으므로, DDL의 영향이 쿼리 대기, 커넥션 누적 및 회복 지연으로 확산되는 과정을 계산 가능한 단계로 분해하였다.

먼저 DDL이 대상 테이블 또는 관련 객체에 잠금을 발생시키면 해당 객체를 사용하는 쿼리가 대기할 수 있다. 대기 중인 애플리케이션 요청은 DB 응답이 반환될 때까지 커넥션을 점유한다. 이 상태에서 새로운 요청이 계속 유입되면 사용할 수 있는 커넥션의 여유가 줄어들고, 최대 허용 커넥션 수에 가까워질수록 커넥션 획득 대기와 타임아웃의 가능성이 커진다.

DDL이 종료된 이후에도 이미 누적된 요청이 즉시 사라지는 것은 아니다. DB의 최대 처리량이 현재 요청 유입량보다 충분히 크면 남은 처리 여력으로 누적 요청을 해소할 수 있지만, 요청량이 최대 처리량에 가깝거나 이를 초과하면 지연이 지속될 수 있다. 이에 따라 DDL 위험을 `DDL 수행 시간 → 쿼리 영향 시간 → 예상 커넥션 수요 → 회복 가능성 → 최종 위험도`의 흐름으로 정의하였다.

이 과정은 DDL 자체에서 확인되는 영향이 실행 시점의 작업 부하와 결합될 때 커넥션 자원에 어떤 압력을 가하는지 설명하기 위한 계산 구조이다. 또한 동일한 DDL을 여러 시간대에 적용했을 때 위험도가 어떻게 달라지는지 비교하는 기준으로 사용하였다.

다. 입력 지표 도출을 위한 근거 조사

위험 전파 과정의 각 단계를 계산 가능한 지표로 구체화하기 위해 관련 선행 연구와 공식 문서를 검토하였다. 검토는 다음 세 질문을 중심으로 진행하였다.

1) DDL은 얼마나 큰 작업을 발생시키는가?

첫 번째 질문에서는 DDL 자체의 작업량과 동시 쿼리에 미치는 영향을 확인하였다. PostgreSQL 공식 문서 「ALTER TABLE」은 컬럼 타입 변경과 일부 컬럼 추가가 테이블과 인덱스 전체를 다시 작성할 수 있고, 제약조건 추가는 기존 행을 확인하기 위한 테이블 스캔을 수행할 수 있다고 설명한다. 반대로 기존 행을 다시 처리하지 않고 시스템 카탈로그의 정의만 갱신하는 작업은 메타데이터 변경으로 구분하였다. 「Explicit Locking」 문서는 `ALTER TABLE`의 세부 작업마다 서로 다른 잠금이 필요하며, 잠금 간 충돌 여부에 따라 동시에 실행되는 쿼리가 제한됨을 보여준다. 따라서 DDL 이름만 구분하는 것으로는 부족하고, 실제 데이터 전체를 처리하는지와 어떤 쿼리를 얼마나 제한하는지를 함께 구분해야 한다고 판단하였다. 여기서 작업 유형, 잠금 수준, 테이블 재작성 가능성 및 메타데이터 변경 여부를 입력 후보로 도출하였다.

인덱스 작업은 같은 목적이라도 실행 방식에 따라 영향이 달라지는 사례로 별도 검토하였다. PostgreSQL 공식 문서 「CREATE INDEX」에 따르면 일반 인덱스 생성은 테이블 전체를 한 번 스캔하면서 쓰기 작업을 차단한다. 반면 `CONCURRENTLY` 방식은 쓰기를 허용하지만 테이블을 두 번 스캔하고 기존 트랜잭션의 종료를 기다리며 추가 CPU와 디스크 입출력을 사용한다. 또한 문서는 대용량 테이블의 인덱스 생성이 여러 시간 지속될 수 있다고 설명한다. 이로부터 인덱스 관련 여부와 동시 생성 여부는 쓰기 차단 방식을, 대상 테이블 크기는 처리해야 할 데이터량을, 디스크 입출력 처리량은 해당 데이터량을 처리할 수 있는 속도를 반영하는 후보로 도출하였다.

종합하면 DDL이 발생시키는 작업의 크기는 명령의 종류만으로 결정되지 않으며, 기존 데이터 전체를 다시 처리하는지, 처리할 데이터가 얼마나 많은지, 해당 작업이 동시 쿼리를 어느 정도 제한하는지에 따라 달라진다. 이에 따라 본 프로젝트에서는 작업 유형, 잠금 수준, 테이블 재작성 가능성, 인덱스 및 동시 생성 여부로 작업 방식을 구분하고, 대상 테이블 크기와 디스크 입출력 처리량을 결합하여 DDL의 작업 부담과 예상 지속 시간을 판단하기로 하였다.

2) 실행 시점의 DB는 얼마나 바쁘고 자원 한계에 가까운가?

두 번째 질문에서는 DDL 실행 전 DB의 상태를 요청 수요, 자원 여유 및 응답 지연의 세 측면으로 나누어 살펴보았다.

요청 수요 측면에서는 DDL의 영향이 지속되는 동안 새로 유입될 요청의 속도를 반영하기 위해 TPS를 선정하였다. Google SRE의 「Monitoring Distributed Systems」는 사용자 대상 시스템의 주요 관찰 신호로 지연 시간, 트래픽, 오류 및 포화도를 제시하며, 트래픽을 시스템에 유입되는 수요로 설명한다. 웹 서비스와 저장소에서는 이를 초당 요청 또는 트랜잭션 수로 측정할 수 있으므로, 실행 시점의 요청 수요를 TPS로 나타내었다.

자원 여유 측면에서는 현재 점유량과 허용 상한의 차이를 반영하기 위해 활성 커넥션과 최대 허용 커넥션 수(C_max)를 선정하였다. 요청 수요가 같더라도 이미 사용 중인 자원이 많으면 DDL이 추가될 때 한계에 더 빠르게 도달할 수 있다. 「Monitoring Distributed Systems」는 포화도를 자원이 얼마나 가득 찼는지를 나타내는 값으로 설명하며, 자원 사용률이 100%에 도달하기 전부터 성능 저하가 시작될 수 있으므로 현재 사용량과 상한을 함께 관찰해야 한다고 제시한다. PostgreSQL 공식 문서 「Connections and Authentication」의 `max_connections`는 동시에 허용되는 최대 연결 수를 정의하고, 「Monitoring Database Activity」의 `pg_stat_activity`는 현재 세션과 처리 상태를 제공한다. 이를 바탕으로 현재 점유량은 활성 커넥션으로, 환경이 허용하는 상한은 최대 허용 커넥션 수(C_max)로 나타내었다.

응답 지연 측면에서는 실행 전부터 존재하는 느린 요청과 포화 징후를 반영하기 위해 P99 응답 지연을 선정하였다. P99는 느린 요청 99%의 평균이 아니라, 전체 요청을 응답 시간 순으로 정렬했을 때 99%가 해당 시간 이내에 완료되는 경계값이다. Google SRE 문서는 이러한 99번째 백분위 응답 시간의 증가가 시스템 포화를 조기에 보여줄 수 있다고 설명한다. Google의 「The Tail at Scale」은 전체 요청의 응답 시간을 모두 더해 요청 수로 나눈 산술평균만으로는 소수의 매우 느린 요청이 사용자 경험에 미치는 영향을 충분히 드러내기 어렵다는 점을 다룬다. 따라서 전체 요청의 평균 응답 시간보다 느린 요청 구간의 변화를 확인할 수 있는 P99 응답 지연을 입력 지표로 사용하였다.

위 선정 지표를 바탕으로 TPS와 활성 커넥션, P99 응답 지연이 높고 최대 허용 커넥션 수(C_max)까지 남은 여유가 작을수록 DDL의 추가 영향을 수용하기 어려운 상태로 해석하였다.

3) DDL 종료 이후 누적된 요청과 복제 작업을 해소할 수 있는가?

세 번째 질문에서는 DDL이 끝난 뒤 누적된 요청을 처리하고 복제 DB가 변경을 따라갈 수 있는지를 확인하였다. 대기행렬 이론의 「Little’s Law」는 시스템 내부에 머무르는 요청 수가 요청 유입률과 체류 시간의 곱으로 설명될 수 있음을 제시한다. 이에 따라 TPS와 DDL로 인한 영향 시간을 결합하면 그동안 새로 유입되어 대기할 수 있는 요청 수를 추정할 수 있다고 판단하였다. 다만 Little’s Law가 DB 커넥션 수를 직접 계산하는 것은 아니므로, 요청이 영향 시간 동안 커넥션을 점유한다는 가정을 적용해 커넥션 수요로 변환하였다.

누적 요청을 해소할 수 있는지는 요청 유입량뿐 아니라 DB가 처리할 수 있는 최대 처리량과의 차이에 따라 결정된다. Google SRE의 「Handling Overload」는 시스템에 처리 용량보다 많은 트래픽을 보내지 않아야 한다고 설명하는 한편, 요청마다 자원 비용이 달라 단순한 초당 요청 수만으로 용량을 일반화하면 부정확할 수 있다고 지적한다. 이에 따라 최대 처리량(MuMax)을 DB가 안정적으로 처리할 수 있는 환경별 처리 한계로 두되, 고정된 보편값이 아니라 대상 작업 부하를 이용한 부하 시험이나 운영 측정으로 정해야 하는 값으로 보았다.

복제 작업의 누적 상태를 반영하기 위한 지표로는 복제 지연을 선정하였다. GitHub의 「gh-ost」는 복제 지연과 서버 부하를 관찰하고, 설정한 기준을 초과하면 온라인 변경 작업의 진행 속도를 제한한다. 이 사례는 복제 지연이 현재 발생한 변경량을 복제 DB가 따라갈 수 있는지를 판단하는 운영 지표로 사용되고 있음을 보여준다. 이에 따라 MigraGuard에서도 복제 지연을 실행 전부터 누적된 복제 부담과 추가 변경을 수용할 여유를 반영하는 지표로 사용하였다.

종합하면 DDL 종료 이후 누적 요청의 해소 가능성은 TPS와 최대 처리량(MuMax)의 차이로 남은 처리 여력을 판단하고, 복제 작업의 누적 상태는 복제 지연으로 판단하기로 하였다. TPS가 최대 처리량(MuMax)보다 충분히 낮고 복제 지연이 작을수록 누적된 요청과 변경을 해소할 여유가 크다. 반대로 TPS가 최대 처리량(MuMax)에 가깝거나 이를 초과한 경우, 또는 복제 지연이 큰 경우에는 정상 상태로 회복하는 데 더 긴 시간이 필요한 것으로 해석하였다.

라. 정적·동적 입력 지표 선정과 반영 대상

근거 조사에서 확인한 운영 현상을 바탕으로 최종 입력 지표를 선정하였다. 선정 결과는 각 입력값이 실행 전 상태의 어떤 측면을 표현하고, 어디에서 수집하거나 설정하는지를 기준으로 정리하였다.

[표 2. 정적·동적 입력 지표와 반영 대상]

| 구분 | 선정 지표 | 지표가 반영하는 대상 | 수집 또는 설정 방법 |
|---|---|---|---|
| DDL 정적 특성 | 작업 유형 | 메타데이터 변경, 데이터 검증, 재작성, 인덱스 구축 등 DDL이 발생시키는 작업의 종류 | 입력 DDL 정적 분석 |
| DDL 정적 특성 | 잠금 수준 | DDL과 동시에 실행될 수 없는 읽기·쓰기 쿼리의 범위와 제한 강도 | 입력 DDL 정적 분석 |
| DDL 정적 특성 | 테이블 재작성 가능성 | 기존 행과 인덱스 전체를 다시 처리해야 하는지 여부 | 입력 DDL 정적 분석 |
| DDL 정적 특성 | 메타데이터 변경 여부 | 기존 행을 다시 처리하지 않고 시스템 카탈로그의 정의만 변경하는지 여부 | 입력 DDL 정적 분석 |
| DDL 정적 특성 | 인덱스 및 동시 생성 여부 | 쓰기 차단을 선택하는지, 추가 스캔과 장시간 자원 사용을 선택하는지의 차이 | 입력 DDL 정적 분석 |
| 대상 작업량 | 테이블 크기 | 재작성·검증·인덱스 구축에서 읽거나 기록해야 할 데이터의 양 | DB 메타데이터 조회 또는 실험 환경 설정 |
| 환경 처리 속도 | 디스크 입출력 처리량 | 전체 데이터 작업을 단위 시간에 처리할 수 있는 속도 | 저장장치 측정 또는 환경 설정 |
| 실행 시점 수요 | TPS | DDL의 영향이 지속되는 동안 새로 유입될 요청의 속도 | 모니터링 값, 시간대별 이력 또는 부하 시험 측정값 |
| 실행 시점 지연 | P99 응답 지연 | 실행 전부터 존재하는 느린 요청과 포화 징후의 정도 | 모니터링 값, 시간대별 이력 또는 부하 시험 측정값 |
| 커넥션 포화도 | 활성 커넥션 | 현재 이미 점유된 동시 처리 자원의 양 | `pg_stat_activity` 또는 모니터링 도구에서 수집 |
| 커넥션 처리 한계 | 최대 허용 커넥션 수(C_max) | 환경이 허용하는 동시 연결 상한 | `max_connections`, 커넥션 풀 및 운영 기준 반영 |
| 요청 처리 한계 | 최대 처리량(MuMax) | DB가 안정적으로 처리할 수 있는 환경별 최대 요청 처리량 | 부하 시험 또는 운영 측정으로 설정 |
| 복제 상태 | 복제 지연 | 원본 DB의 변경량을 복제 DB가 따라가지 못하고 누적한 정도 | PostgreSQL 복제 통계 또는 모니터링 도구에서 수집 |

이 가운데 작업 유형, 잠금 수준, 테이블 재작성 가능성, 메타데이터 변경 여부 및 인덱스 관련 여부는 DDL 자체에서 얻는 정적 입력이다. 테이블 크기, TPS, P99 응답 지연, 활성 커넥션 및 복제 지연은 배포 대상과 실행 시점에서 관측하는 환경 입력이다. 최대 허용 커넥션 수(C_max), 최대 처리량(MuMax), 디스크 입출력 처리량은 현재 사용량이 아니라 해당 환경이 수용할 수 있는 한계를 나타내므로 별도의 환경 처리 한계로 구분하였다.

위 표의 값은 DDL, 실행 시점 및 대상 환경에서 얻는 입력값이다. 이 입력값을 계산에 적용하기 위해서는 DDL 특성의 차이를 수치로 변환하는 계산 계수가 추가로 필요하다. 잠금 영향도는 다번에서 확인한 잠금 수준별 쿼리 제한 차이를 환산하며, 정적 기본 위험도는 작업 유형, 테이블 재작성 및 메타데이터 변경 여부에서 확인되는 DDL 자체의 위험을 최종 결과에 반영한다. 두 계수가 5단계 계산에 적용되는 위치와 방식은 마번에서 설명한다.

계산 결과에는 Safe, Warning, Danger를 일관된 의미로 해석할 수 있도록 고정 판정 기준을 적용하였다. 구체적인 판정 경계와 각 등급의 운영상 의미는 5단계 계산 과정을 설명한 뒤 바번에서 다룬다. 서비스 환경의 차이는 판정 기준을 변경하는 방식이 아니라, 해당 환경의 최대 허용 커넥션 수(C_max)와 최대 처리량(MuMax)에 반영하도록 하였다.

위 입력값과 계산 계수를 실제 판단 결과로 변환하기 위해 DDL의 작업량과 잠금 특성을 먼저 시간의 형태로 바꾸고, 그 시간 동안 유입되는 요청을 커넥션 수요로 변환한 뒤, 환경의 처리 한계와 비교하여 회복 가능성을 판단하였다. 이에 다음 절에서는 원시 입력을 `예상 DDL 수행 시간 → 쿼리 영향 시간 → 예상 최대 커넥션 수요 → 예상 회복 시간 → 최종 위험도`로 순차적으로 변환하는 5단계 위험 지표 산출 과정을 설명한다.

마. 5단계 위험 지표 산출 과정

앞서 선정한 입력 지표를 실제 배포 판단에 활용하기 위해 DDL의 영향이 확산되는 순서에 따라 5단계 위험 지표 산출 과정을 구성하였다. 먼저 DDL의 작업 부담을 예상 수행 시간으로 환산하고, 잠금 특성과 실행 시점의 상태를 결합하여 쿼리 영향 시간을 계산한다. 이어서 영향 시간 동안 누적될 커넥션 수요와 이를 해소하는 데 필요한 회복 시간을 산출한 뒤, 최종 위험도와 Safe, Warning, Danger 등급을 결정한다.

각 단계의 산출값은 다음 단계의 입력으로 사용되거나 최종 등급의 원인을 설명하는 판단 근거가 된다. 5개 지표의 사용 위치와 각 지표로 판단할 수 있는 내용은 다음과 같다.

[표 3. 5단계 위험 지표의 사용 위치와 판단 의미]

| 단계 | 산출 지표 | 실제 사용 위치 | 판단할 수 있는 내용 |
|---|---|---|---|
| 1단계 | 예상 DDL 수행 시간(T_ddl) | 쿼리 영향 시간(T_block) 계산의 입력 | DDL 자체의 작업 부담이 큰지 판단 |
| 2단계 | 쿼리 영향 시간(T_block) | 예상 최대 커넥션 수요(C_peak) 계산의 입력 | DDL 영향으로 운영 쿼리가 영향을 받을 수 있는 시간이 긴지 판단 |
| 3단계 | 예상 최대 커넥션 수요(C_peak) | `최종 위험도(RiskScore) = 예상 최대 커넥션 수요(C_peak) / 최대 허용 커넥션 수(C_max) × 100`의 핵심 입력 | 예상 커넥션 수요가 허용 한계에 얼마나 가까운지 판단 |
| 4단계 | 예상 회복 시간(T_rec) 및 회복 불가 조건 | 최종 등급 판단 보조 | 커넥션 한계 초과 후 누적 요청을 처리 여력으로 해소할 수 있는지 판단 |
| 5단계 | 최종 위험도(RiskScore) | Safe, Warning, Danger 등급 분류 및 시간대별 forecast 비교 기준 | 현재 또는 특정 시간대가 일반 실행 후보인지, 조건부 후보인지, 실행 보류 대상인지 판단 |

1) 예상 DDL 수행 시간(T_ddl)

첫 번째 지표인 예상 DDL 수행 시간(T_ddl)은 DDL 자체가 완료되기까지 걸릴 것으로 예상되는 시간을 의미한다. 이 값을 먼저 추정한 이유는 DDL 수행 시간이 길어질수록 잠금 유지 시간과 디스크 입출력 부하가 지속되고, 이후 쿼리 대기와 커넥션 압력으로 영향이 확산될 가능성이 커지기 때문이다.

현재 구현은 테이블 재작성이 필요한 경우 `대상 테이블 크기 ÷ 디스크 입출력 처리량`으로 데이터 처리 시간을 계산한다. 테이블 재작성은 기존 행을 새로운 스키마 구조나 타입 조건에 맞게 다시 기록하는 작업이므로 대상 테이블이 클수록 읽고 써야 할 데이터량이 증가한다. 인덱스 생성은 테이블 재작성은 아니지만 대상 테이블을 스캔하여 새로운 인덱스 구조를 구축해야 하므로, 테이블 크기와 디스크 입출력 처리량의 영향을 받는 작업으로 반영하였다. 반대로 실제 행 데이터를 다시 쓰지 않고 PostgreSQL 카탈로그의 스키마 정의만 변경하는 작업에는 고정된 메타데이터 처리 시간을 적용한다.

이 계산은 작업 유형별 실제 실행 계획, 캐시, CPU 및 동시 입출력의 차이를 모두 반영하지 않는다. 따라서 예상 DDL 수행 시간(T_ddl)은 실제 완료 시간을 정확히 예측하는 값이라기보다, 테이블 재작성 여부, 인덱스 구축 여부 및 데이터 규모에 따른 상대적인 작업 부담을 추정하는 값으로 해석하였다. `CREATE INDEX CONCURRENTLY`도 작업 수행 시간은 테이블 크기의 영향을 받지만, 일반 인덱스 생성과의 차이는 이후 잠금 영향도에서 구분하였다.

2) 쿼리 영향 시간(T_block)

두 번째 지표인 쿼리 영향 시간(T_block)은 DDL 수행 중 운영 쿼리가 영향을 받을 수 있는 시간을 위험 계산에 반영한 값이다. DDL 수행 시간이 길더라도 모든 시간이 사용자 요청을 동일하게 차단하는 것은 아니므로 DDL이 요구하는 잠금 수준과 실행 시점의 지연 상태를 함께 고려하였다.

현재 구현은 예상 DDL 수행 시간(T_ddl), P99 응답 지연 및 복제 지연을 합산한 뒤 잠금 수준에 따른 영향도를 적용한다. P99 응답 지연은 이미 느린 요청이 존재하는 상태를 반영하고, 잠금 영향도는 같은 수행 시간이라도 강한 잠금을 요구하는 DDL과 동시 실행을 고려한 DDL의 영향이 다르다는 점을 구분한다. 복제 지연은 원본 DB의 변경을 복제 DB가 따라가는 데 어려움이 존재하는 상태를 보수적으로 반영한다.

복제 지연이 실제 잠금 시간을 직접 증가시키는 것은 아니다. 따라서 쿼리 영향 시간(T_block)은 실제 쿼리 차단 시간을 그대로 예측한 값이 아니라, DDL 수행 시간에 실행 시점의 지연 상태와 잠금 강도를 결합한 쿼리 영향 시간 또는 차단 위험 환산값으로 해석하였다.

3) 예상 최대 커넥션 수요(C_peak)

세 번째 지표인 예상 최대 커넥션 수요(C_peak)는 쿼리 영향 시간(T_block) 동안 발생할 것으로 예상되는 최대 커넥션 수요를 의미한다. 쿼리 대기가 단순한 응답 지연에서 끝나지 않고, 커넥션을 점유한 요청이 누적되면서 애플리케이션 장애로 확대될 수 있기 때문에 이 단계를 두었다.

현재 구현은 `현재 활성 커넥션 + TPS × 쿼리 영향 시간(T_block)`으로 예상 커넥션 수요를 계산하며, 밀리초 단위의 쿼리 영향 시간(T_block)은 초 단위로 변환한다. 같은 쿼리 영향 시간이라도 TPS가 높으면 더 많은 요청이 유입되고, 현재 활성 커넥션이 많으면 새로운 요청을 수용할 여유가 작다.

예상 최대 커넥션 수요(C_peak)는 실제로 관측한 최대 커넥션 수가 아니다. 모든 신규 요청이 영향 시간 동안 커넥션을 필요로 한다는 단순화된 가정에 따라 추정한 수요이다. 이 값이 최대 허용 커넥션 수(C_max)에 가까워질수록 커넥션 풀 고갈 위험이 커지고, 이를 초과하면 커넥션 획득 대기와 타임아웃 가능성이 커지는 것으로 해석하였다.

4) 예상 회복 시간(T_rec)

네 번째 지표인 예상 회복 시간(T_rec)은 DDL의 영향으로 최대 허용 커넥션 수(C_max)를 초과한 요청 수요를 DB의 잔여 처리량으로 해소하는 데 필요한 시간을 의미한다. DDL이 종료되어 잠금이 해제되더라도 이미 누적된 요청을 처리하지 못하면 지연과 타임아웃이 지속될 수 있기 때문이다.

현재 구현은 예상 최대 커넥션 수요(C_peak)가 최대 허용 커넥션 수(C_max)를 초과한 경우 초과 수요를 `최대 처리량(MuMax) - TPS`로 계산한 잔여 처리량으로 나누어 예상 회복 시간(T_rec)을 산출한다. TPS가 최대 처리량(MuMax)보다 작으면 새로 유입되는 요청을 처리하고 남은 용량으로 누적 요청을 해소할 수 있다고 본다. 반대로 TPS가 최대 처리량(MuMax) 이상이면 누적 요청을 처리할 잔여 용량이 없으므로 예상 회복 시간(T_rec)을 산출하지 않고 회복 불가 조건으로 판단한다. 이 조건은 다음 단계의 최종 위험도 계산에서 Danger를 결정하는 근거로 사용한다.

5) 최종 위험도(RiskScore)

다섯 번째 지표인 최종 위험도(RiskScore)는 예상 커넥션 수요가 환경의 최대 허용 커넥션 수에 얼마나 접근하는지를 백분율로 나타내고, DDL 자체의 정적 위험을 함께 반영한 최종 위험도이다.

현재 구현은 `예상 최대 커넥션 수요(C_peak) / 최대 허용 커넥션 수(C_max) × 100`으로 커넥션 위험도를 계산한다. 이후 작업 유형, 잠금 수준, 테이블 재작성 및 메타데이터 변경 여부에서 도출한 정적 기본 위험도를 최솟값으로 적용한다. 이를 통해 실행 시점의 부하가 낮더라도 DDL 자체의 강한 잠금이나 재작성 위험이 결과에서 사라지지 않도록 하였다. 또한 TPS가 최대 처리량(MuMax) 이상인 회복 불가 조건은 커넥션 비율과 관계없이 Danger로 판단한다.

예상 DDL 수행 시간(T_ddl)과 쿼리 영향 시간(T_block)은 예상 최대 커넥션 수요(C_peak)를 계산하는 과정에 반영되고, 예상 회복 시간(T_rec)은 누적 요청의 회복 가능성을 별도로 설명한다. 즉 최종 위험도(RiskScore)는 예상 DDL 수행 시간(T_ddl), 쿼리 영향 시간(T_block), 예상 최대 커넥션 수요(C_peak), 예상 회복 시간(T_rec)을 각각 별도의 가중치로 더한 값이 아니라, 앞 단계에서 계산된 커넥션 압력을 중심으로 정적 기본 위험도와 회복 불가 여부를 결합한 결과이다.

이처럼 최종 위험도(RiskScore)는 최종 등급과 시간대 추천에 직접 사용되는 지표이며, 예상 DDL 수행 시간(T_ddl), 쿼리 영향 시간(T_block), 예상 최대 커넥션 수요(C_peak), 예상 회복 시간(T_rec)은 최종 위험도(RiskScore)가 어떤 원인으로 증가했는지 설명하는 진단 지표로 사용한다. 따라서 네 지표는 독립적인 합격·불합격 기준이라기보다, DDL 분할, 저부하 시간대 실행, 커넥션 여력 확보, 처리량 증설과 같은 후속 조치를 결정하기 위한 원인 분석 지표로 해석하였다.

각 지표의 운영상 해석 기준은 다음과 같다.

[표 4. 5단계 위험 지표별 값의 해석과 활용]

| 지표 | 값이 낮을 때의 의미 | 값이 높을 때의 의미 | 사용자가 판단할 수 있는 내용 |
|---|---|---|---|
| 예상 DDL 수행 시간(T_ddl) | DDL 자체의 작업 부담이 작고, 메타데이터 변경 또는 작은 데이터 작업에 가까움 | 대용량 테이블 스캔, 인덱스 구축, 테이블 재작성 또는 데이터 검증 부담이 큼 | DDL 분할, 점검 시간 확보 또는 온라인 변경 방식 검토 필요 여부 |
| 쿼리 영향 시간(T_block) | 운영 쿼리가 영향을 받을 가능 시간이 짧음 | 잠금 경합이나 쿼리 대기가 길게 지속될 가능성이 큼 | 현재 실행 가능 여부, 저부하 시간대 실행 필요 여부 |
| 예상 최대 커넥션 수요(C_peak) | 예상 커넥션 수요가 최대 허용 커넥션 수(C_max)보다 충분히 낮아 커넥션 여유가 있음 | 예상 커넥션 수요가 최대 허용 커넥션 수(C_max)에 접근하거나 초과할 수 있음 | 커넥션 풀 고갈, 타임아웃 위험 및 커넥션 여력 확보 필요 여부 |
| 예상 회복 시간(T_rec) | 누적 요청을 빠르게 해소할 수 있거나 초과 수요가 거의 없음 | DDL 종료 이후에도 누적 요청 해소가 지연되거나, 회복 불가 조건에 가까움 | 처리량 증설, 배포 보류 또는 작업 부하 감소 필요 여부 |
| 최종 위험도(RiskScore) | 전체적으로 실행 여유가 비교적 있음 | 커넥션 압력 또는 정적 위험이 커서 추가 검토가 필요함 | Safe, Warning, Danger 최종 등급과 시간대별 추천 판단 |

바. 위험 등급의 의미와 대응 기준

5단계 계산 결과가 실제 의사결정에 사용될 수 있도록 Safe, Warning, Danger의 의미와 후속 조치를 구분하고, 다음의 판정 기준을 MigraGuard에 고정하여 적용하였다.

판정 경계를 정하기 위해 커넥션 포화도와 응답 지연의 관계를 다룬 자료를 검토하였다. Victoria University of Wellington의 강의 자료 「Queueing Systems M/M/1 and M/M/c」는 M/M/1 대기행렬을 통해 요청 유입량과 시스템 처리량이 대기 시간에 미치는 영향을 설명한다. 이 자료에서 다루는 M/M/1은 일정하지 않은 간격으로 들어오는 요청을 하나의 처리 자원이 순서대로 처리한다고 가정하는 모델이다. 처리 중인 요청이 있으면 새 요청은 대기열에 머물며, 시스템 활용률은 단위 시간당 요청 유입률을 단위 시간당 처리율로 나눈 값으로 계산한다. 활용률이 1에 가까워질수록 요청 유입 속도와 처리 속도의 차이가 줄어들고 대기열이 누적되므로, 대기 시간과 평균 응답 시간이 급격히 증가한다. 이 관계는 현재 수요가 처리 한계에 얼마나 접근했는지를 나타내는 비율을 단순한 사용량이 아니라, 지연 가능성이 커지는 정도를 나타내는 위험도로 해석할 수 있는 근거가 되었다.

위험도가 어느 수준에 도달했을 때 실행을 보류해야 하는지를 정하기 위해 González-Horta 등의 「Mathematical Model for the Optimal Utilization Percentile in M/M/1 Systems」를 참고하였다. 이 연구는 M/M/1 성능 곡선에서 응답 시간과 활용률 사이의 균형점인 무릎 지점을 수학적으로 찾으려는 접근을 제시한다. 활용률이 낮을 때는 추가 요청의 영향이 상대적으로 제한적이지만, 처리 한계에 가까워질수록 작은 요청 증가도 응답 시간 증가로 크게 이어질 수 있다. 다만 이 연구는 특정 활용률을 모든 시스템에 적용 가능한 보편 기준으로 제시하지 않고, 무릎 위치가 시스템 조건에 따라 달라질 수 있음을 함께 설명한다. Google SRE의 「Monitoring Distributed Systems」도 많은 시스템에서 자원 사용률이 100%에 도달하기 전에 성능 저하가 시작된다고 설명한다. 이에 따라 본 프로젝트에서는 80%를 실측으로 검증된 보편 임계값이 아니라, 처리 한계에 도달하기 전에 실행을 보류하기 위한 프로토타입의 보수적 정책값으로 선택하였다.

MigraGuard에서는 이러한 활용률 개념을 커넥션 자원에 적용하여, 예상 최대 커넥션 수요(C_peak)를 최대 허용 커넥션 수(C_max)로 나눈 비율을 최종 위험도(RiskScore)로 정의하였다. 최종 위험도(RiskScore)가 50% 미만이면 예상 수요보다 더 많은 커넥션 여유가 남아 있으므로 Safe로 구분하였다. 50% 이상에서는 남은 커넥션 여유가 예상 수요와 같거나 더 작아지고, 추가 부하에 따라 무릎 구간으로 이동할 수 있으므로 Warning으로 구분하였다. 앞서 도출한 80%부터는 지연과 타임아웃 위험이 급격히 커질 수 있는 구간으로 보고 Danger로 구분하였다. 이에 따라 최종 위험도(RiskScore) 50% 미만은 Safe, 50% 이상 80% 미만은 Warning, 80% 이상은 Danger로 고정하였다. TPS가 최대 처리량(MuMax) 이상인 경우에는 누적 요청을 해소할 처리 여력이 없으므로 최종 위험도(RiskScore)와 관계없이 Danger로 판정하였다.

[표 5. Safe, Warning, Danger 판정 기준과 권장 조치]

| 결과 | 계산 기준 | 운영상 의미 | 권장 조치 |
|---|---|---|---|
| Safe | 최종 위험도(RiskScore) 50% 미만 | 예상 커넥션 수요가 처리 한계에서 비교적 여유가 있음 | 일반 배포 후보로 검토하고 기본 모니터링과 롤백 준비 수행 |
| Warning | 최종 위험도(RiskScore) 50% 이상 80% 미만 | 부하가 추가되면 커넥션 한계에 접근할 수 있음 | 저부하 시간대 실행, DBA 승인, 모니터링 강화 또는 DDL 분할 검토 |
| Danger | 최종 위험도(RiskScore) 80% 이상 또는 TPS가 최대 처리량(MuMax) 이상 | 커넥션 한계 접근·초과 또는 누적 요청 회복 곤란 | 즉시 배포 보류, 처리 여력 확보, 중단 또는 온라인 변경 전략 검토 |

Safe는 장애가 발생하지 않음을 보증하는 등급이 아니라 현재 입력과 계산 가정에서 커넥션 여유가 비교적 충분하므로 일반 배포 후보로 검토할 수 있다는 의미이다. Warning은 실행 자체가 불가능하다는 뜻이 아니라 부하 변동이나 DDL 대기 시간이 추가될 경우 한계에 접근할 수 있으므로 실행 시점 변경과 추가 승인이 필요하다는 의미이다. Danger는 커넥션 한계에 접근했거나 회복 불가 조건에 해당하므로 현재 조건에서 즉시 실행하기보다 DDL과 환경을 변경한 뒤 다시 평가해야 한다는 의미이다.

서비스별 처리 능력의 차이는 판정 경계를 바꾸지 않고 실제 환경에서 측정한 최대 허용 커넥션 수(C_max)와 최대 처리량(MuMax)에 반영한다. 이에 따라 Safe, Warning, Danger는 서로 다른 환경에서도 각각 일반 배포 후보, 조건부 실행 후보, 현재 조건에서의 배포 보류라는 동일한 의미를 유지한다.

사. 시간대별 위험 평가와 실행 시간 추천

실행 시간대를 추천하기 위해서는 동일한 DDL이 시간대별 작업 부하에서 어떤 위험도를 가지는지 비교해야 한다. 이에 지표 수집기(Collector)가 주기적으로 수집한 대상 테이블의 TPS와 P99 응답 지연을 이력 저장소에 기록하고, 이를 시간대별로 집계하여 24시간 작업 부하 프로필을 생성하도록 구성하였다.

작업 부하 프로필은 같은 시간대에 수집된 TPS의 평균을 예상 TPS로, 최소값과 최대값을 관측 변동 범위로, P99 응답 지연의 평균을 예상 P99로 사용한다. 예를 들어 여러 날짜의 02시 데이터가 존재하면 해당 데이터의 평균 TPS와 평균 P99를 02시의 대표 작업 부하로 사용하고, 최소·최대 TPS를 함께 기록하여 그 시간대에서 관측된 트래픽 범위를 제시한다.

현재 구현은 시간대별 평균 TPS와 평균 P99를 입력하고 동일한 5단계 계산 과정을 반복하여 각 시간의 최종 위험도(RiskScore)와 등급을 산출한다. 이후 각 시간대를 Safe, Warning, Danger로 구분하고, DDL 잠금으로 인한 P99 응답 지연 영향 가능성도 함께 확인한다. 여기서 P99 영향 가능성은 DDL의 쿼리 영향 시간이 해당 시간대의 일반적인 느린 요청보다 충분히 길고, 그 시간 동안 실제 요청이 잠금의 영향을 받을 수 있는지를 함께 보는 기준이다. 즉 시간 추천은 단순히 TPS가 가장 낮은 시간을 고르는 것이 아니라, 해당 시간대의 평균 요청량, 평균 P99 응답 지연, DDL 잠금 수준 및 쿼리 영향 시간(T_block)을 함께 반영한다.

추천 시간은 Safe 시간대를 가장 우선한다. Safe 시간대가 존재하면 그중 최종 위험도(RiskScore)가 가장 낮은 시간을 일반 추천 시간으로 제시하고, 위험도가 같으면 TPS가 더 낮은 시간을 우선한다. Safe 시간대가 하나도 없더라도 Warning 시간대가 존재하면 가장 위험도가 낮은 Warning 시간대를 조건부 추천으로 제시한다. 이 경우 결과는 “안전한 시간”이 아니라 “현재 후보 중 상대적으로 위험이 낮지만 추가 승인과 모니터링이 필요한 시간”으로 해석한다. 반대로 모든 시간대가 Danger라면 실행 시간 추천을 제공하지 않고, DDL 분할, 처리 여력 확보 또는 다른 마이그레이션 전략 검토를 제시한다.

다만 현재 추천 기능에는 다음과 같은 한계가 있다.

- 연속된 안전 구간이 아니라 한 시간 단위의 후보만 선택한다.
- 예상 DDL 수행 시간(T_ddl)이 해당 시간 구간 안에 완료되는지 검사하지 않는다.
- 시간대별 활성 커넥션과 복제 지연 예측값이 없으면 현재 관측값을 공통으로 사용한다.
- 이력이 없는 시간대를 0으로 보완하면 실제보다 안전한 시간으로 계산될 가능성이 있다.

따라서 시간대별 추천 기능의 목표는 마이그레이션을 실행하기에 가장 적합한 시간대를 제시하는 데 있다. 다만 현 단계의 추천은 최종 위험도(RiskScore)와 등급을 기준으로 한 휴리스틱이므로, 실행 시각을 자동 확정하는 완성된 최적화 결과가 아니라 최적 실행 시간 후보를 제안하는 기능으로 해석하였다. Safe 추천은 일반 배포 후보를 의미하고, Warning 추천은 조건부 실행 후보를 의미한다. Danger만 존재하는 경우에는 추천 가능한 시간대가 없다고 판단한다. 향후에는 누락된 시간대의 입력 검증, 예상 수행 시간과 회복 시간을 포함하는 연속 구간 탐색, 서비스별 P99 허용 기준, 실제 시간대별 실행 결과를 이용한 추천 점수 보정을 보완할 필요가 있다.

아. 프로토타입 구현

프로토타입은 앞서 정의한 판단 과정을 실제 입력과 출력으로 연결하기 위한 수단으로 구현하였다. 사용 흐름은 `DDL 입력 → 정적 특성 추출 → 현재 또는 시간대별 작업 부하 입력 → 5단계 위험 지표 계산 → 등급과 위험 원인 제시 → 최적 배포 시간 후보와 대응 전략 제시`의 순서로 구성하였다.

핵심 분석 로직은 소프트웨어 개발 키트(Software Development Kit, SDK) 형태로 분리하고, 명령줄 인터페이스(Command-Line Interface, CLI)는 이를 호출하는 실행 인터페이스로 구성하였다. 이를 통해 동일한 분석 기능을 향후 CI/CD 파이프라인이나 API 환경에서도 재사용할 수 있도록 하였다.

자. pgbench 기반 실행 결과 및 민감도 검토

MigraGuard의 사전 판단을 실제 DDL 실행 결과와 비교하기 위해 로컬 PostgreSQL과 부하 시험 도구인 `pgbench`를 이용한 검토 환경을 구성하였다. 각 DDL을 실행하기 전에 데이터베이스를 동일한 상태로 초기화하고, `pgbench`의 목표 TPS와 동시 클라이언트 수를 조절하여 낮은 부하부터 높은 부하까지 작업 부하를 재현하였다.

먼저 DDL을 실행하지 않은 기준 구간과 동일한 부하에서 DDL을 실행한 구간을 각각 측정하였다. 두 구간의 P99 응답 지연, TPS 유지율, DDL 완료 시간, 실패 트랜잭션 수, 최대 활성 커넥션 수 및 잠금 대기 수를 비교하여 MigraGuard가 Warning 또는 Danger로 판단한 조건에서 실제 지연이나 실행 실패가 나타나는지 확인하였다. 이를 통해 정적 검사만으로 구분하기 어려운 실행 시점의 영향을 MigraGuard가 사전에 탐지할 수 있는지를 검토하였다.

시간대 추천 기능은 지표 수집 이력으로 생성한 24시간 작업 부하 프로필의 TPS를 `pgbench` 목표 TPS로 변환하여 압축 재현하였다. 여기서 압축 재현은 실제로 24시간 동안 부하를 실행하는 대신, 각 시간대를 독립된 20초 부하 시험으로 바꾸어 순차적으로 실행하는 방식이다. 시간대별 예상 TPS를 반올림하여 `pgbench`의 초당 목표 트랜잭션 수로 설정하고, 부하 크기에 따라 동시 클라이언트 수를 조절하였다.

각 시간대에서는 먼저 DDL을 실행하지 않은 기준 구간을 측정하였다. 이후 데이터베이스를 같은 초기 상태로 되돌리고 동일한 TPS와 클라이언트 조건으로 `pgbench`를 실행한 뒤, 5초의 준비 구간이 지나면 DDL을 적용하였다. 이 과정을 24개 시간대와 온라인·단계적 DDL 4종에 반복하여 총 96개의 DDL 실행 조건을 구성하였다. 각 조건에서 기준선 대비 P99 응답 지연 증가, TPS 하락, DDL 완료 시간, 실패 트랜잭션 수, 활성 커넥션 및 잠금 대기를 비교하여 MigraGuard가 추천한 시간이 실제 실행 결과에서도 상대적으로 유리한지 확인하였다.

Low Capacity, Default, High Capacity 비교에서는 MigraGuard의 고정 판정 기준과 계산 계수를 동일하게 적용하고, 최대 허용 커넥션 수(C_max), 최대 처리량(MuMax), 디스크 입출력 처리량만 변경하였다. 이를 통해 등급 변화가 판정 기준의 차이가 아니라 서버 처리 여력의 차이에서 발생하도록 실험 조건을 통제하였다.

이 검토는 DDL별 사전 판단과 실측 영향의 일치 여부, 추천 시간과 실제 실행에 유리한 시간의 일치 여부, 서버 처리 여력 변화에 대한 위험도 민감도를 확인하는 세 실험으로 구성하였다. 구체적인 실험 조건과 결과는 주요 추진내용에서 제시한다.
