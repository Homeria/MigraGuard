앞 절에서는 DDL 마이그레이션 위험을 배포 전에 판단하기 위해 필요한 정적 지표와 동적 지표를 선정하고, 이를 예상 DDL 수행 시간, 쿼리 영향 시간, 예상 최대 커넥션 수요, 예상 회복 시간 및 최종 위험도로 변환하는 5단계 위험 지표 산출 과정을 구성하였다. 본 절에서는 이 과정을 적용한 MigraGuard 프로토타입의 분석 흐름을 설명하고, 실제 PostgreSQL 작업 부하에서 DDL 실행 전 위험 판단, 실행 시간 추천, Config 변화에 따른 민감도를 실험적으로 확인한다.

가. MigraGuard 프로토타입의 분석 구조

본 프로젝트의 주요 결과물은 DDL 자체의 정적 위험과 실행 시점의 데이터베이스 상태를 결합하여 마이그레이션 위험도를 판단하는 MigraGuard 프로토타입이다. MigraGuard는 입력된 DDL에서 작업 유형, 잠금 수준, 테이블 재작성 가능성 및 인덱스 관련 여부를 추출한다. 이후 배포 전에 수집한 대상 테이블 크기, TPS, P99 응답 지연, 활성 커넥션 및 복제 지연을 결합하여 위험 지표를 계산한다.

프로토타입의 사용자 흐름은 다음과 같다.

> DDL 입력 → 정적 특성 추출 → 현재 또는 예상 작업 부하 입력 → 5단계 위험 지표 산출 → Safe, Warning, Danger 등급 출력 → 실행·연기·대체 전략 검토

Safe는 현재 입력 조건에서 일반 배포 후보로 검토할 수 있음을 의미한다. Warning은 저부하 시간대 실행, 추가 승인 또는 DDL 분할을 검토해야 함을 의미한다. Danger는 즉시 실행을 보류하고 처리 여력 확보, 중단 마이그레이션 또는 온라인 변경 방식을 검토해야 함을 의미한다. 이 등급은 실제 장애 발생을 보증하거나 단정하는 결과가 아니라, 배포 전에 필요한 검토 수준을 구분하기 위한 판단 정보이다.

나. 실험 목적과 구성

프로토타입이 실제로 의미 있는지 확인하기 위해서는 단순히 DDL 파일에 Safe, Warning, Danger라는 의도 등급을 붙이고 MigraGuard 결과와 비교하는 것만으로는 부족하다. 해당 등급은 실험자가 부여한 기준일 뿐이며, 실제 운영 위험은 실행 시점의 작업 부하와 데이터베이스 상태에 따라 달라지기 때문이다. 따라서 본 프로젝트에서는 실제 PostgreSQL 환경에서 작업 부하를 발생시킨 상태로 DDL을 실행하고, 관측된 P99 응답 지연, 처리 TPS, 실패 트랜잭션 수 및 DDL 실행 결과를 기준으로 MigraGuard의 사전 판단을 해석하였다.

비교 대상에는 PostgreSQL DDL 린터인 Squawk를 함께 사용하였다. Squawk는 DDL 자체의 정적 위험을 배포 전에 검사한다. 반면 MigraGuard는 DDL의 정적 특성에 실행 시점의 작업 부하를 결합하여 위험도를 계산한다. 따라서 두 도구의 비교 목적은 어느 하나가 절대적으로 더 우수하다는 결론을 내리기 위한 것이 아니라, 정적 검사만으로는 드러나기 어려운 작업 부하 기반 위험을 MigraGuard가 추가로 포착할 수 있는지 확인하는 데 있다.

라. 실험 1: DDL별 사전 판단과 실제 실행 결과

첫 번째 실험의 목적은 MigraGuard가 실제 지연 또는 실행 실패 위험이 나타나는 DDL을 배포 전에 경고할 수 있는지 확인하는 것이다. 실험은 DDL을 실행하지 않은 기준선과 DDL을 실행한 조건을 비교하는 방식으로 구성하였다. DDL 실행 조건에서는 작업 부하가 유지되는 중간 시점에 DDL을 실행하였다. 각 DDL 실행 전에는 benchmark DB를 초기화하여 이전 DDL의 인덱스, 컬럼 변경 또는 제약조건이 다음 실험에 영향을 주지 않도록 하였다.

실측 해석은 보편적인 장애 정답 라벨이 아니라 본 실험을 위한 임시 기준이다. DDL 실행 실패, 실패 트랜잭션 발생, 또는 동일 TPS 기준선 대비 P99 응답 지연이 크게 증가한 경우를 위험 신호로 해석하였다. 반대로 기준선 대비 P99 증가가 작고 실패가 없었던 경우는 영향이 작았던 조건으로 보았다. 따라서 이 실험은 MigraGuard의 완성된 정확도 검증이 아니라, 배포 전 위험 판단 방향과 현재 모델의 한계를 확인하기 위한 예비 벤치마크로 보아야 한다.

일반 인덱스 생성 DDL인 DDL-3은 세 부하 단계 모두에서 실제 P99 응답 지연을 증가시켰다. 특히 100 TPS 조건에서는 기준선 P99 2.8ms가 38.1ms로 증가하였고, 1000 TPS 조건에서는 3.0ms가 226.5ms로 증가하였다. Squawk는 해당 DDL을 일반 인덱스 생성으로 경고하였고, MigraGuard도 모든 부하 단계에서 Danger로 판단하였다.

DDL-5는 P99 응답 지연보다 DDL 실행 결과 자체에서 위험이 확인되었다. `orders.shipping_address`에는 NULL 값이 존재하므로 NOT NULL 제약을 직접 설정하는 DDL은 세 부하 단계 모두에서 실패하였다. MigraGuard가 기존 NULL 값의 존재 여부를 직접 검증한 것은 아니지만, NOT NULL 직접 설정이라는 정적 위험을 Danger로 판단하였고 실제 실행에서도 데이터 검증 계열 DDL의 배포 실패 위험이 드러났다. 이는 DDL 위험이 성능 저하뿐 아니라 기존 데이터 상태와의 불일치로 인한 실행 실패로도 나타날 수 있음을 보여준다.

반면 DDL-1, DDL-2, DDL-4, DDL-6은 이번 실측 기준에서는 영향이 작게 나타났다. DDL-1은 nullable 컬럼을 추가하는 단순 변경이고, DDL-2는 동시 인덱스 생성을 사용하여 쓰기 차단을 줄인 사례이다. DDL-4의 `VARCHAR(50)`에서 `TEXT`로의 타입 변경은 PostgreSQL에서 실제 테이블 재작성이 발생하지 않을 수 있는 유형이며, DDL-6의 CHECK 제약조건 즉시 검증도 이번 100만 행 규모와 30초 작업 부하 조건에서는 P99 응답 지연을 크게 증가시키지 않았다.

이 실험에서 가장 중요한 한계는 MigraGuard의 보수적 오탐이다. MigraGuard는 DDL-3과 DDL-5처럼 실제 위험 신호가 나타난 조건을 Danger로 판단했지만, 실측 영향이 작았던 DDL-1, DDL-2, DDL-4, DDL-6의 다수 조건도 Danger로 판단하였다. 이번 18개 조건 중 MigraGuard가 Danger로 판단한 조건은 16개였고, 이 중 10개는 실제 실행에서 P99 증가나 실패가 거의 나타나지 않았다. 이는 현재 설정에서 최대 허용 커넥션 수와 커넥션 압력 계산, 잠금 영향도 및 DDL 유형별 기본 위험도가 보수적으로 작동했기 때문으로 해석된다.

마. 실험 2: 시간대 추천 최적성 검토

두 번째 실험의 목적은 MigraGuard가 forecast로 추천한 시간대가 실제 DDL 실행 결과에서도 가장 적합한 시간대인지 확인하는 것이다. 단순히 24개 시간대의 Safe, Warning, Danger 분포를 나열하는 것만으로는 시간 추천의 의미를 설명하기 어렵다. 따라서 본 실험에서는 PostgreSQL에서 운영 중 영향을 줄이거나 단계적으로 적용할 수 있는 DDL을 대상으로, 24개 시간대별 작업 부하를 각각 짧은 벤치마크 조건으로 압축 재현하고 실제 실행 결과 기준의 시간대 순위를 계산하였다.

실험 대상은 PostgreSQL의 온라인 또는 단계적 변경 패턴을 대표하는 네 가지 DDL로 구성하였다. `DROP INDEX CONCURRENTLY`와 `REINDEX CONCURRENTLY`도 후보로 검토하였으나, 현재 MigraGuard SQL parser가 해당 DDL에서 forecast CSV를 생성하지 못해 시간 추천 정확도 비교 대상에서는 제외하였다.

[표 12. 시간대 추천 최적성 검토에 사용한 PostgreSQL 온라인·단계적 DDL]

| ID | 유형 | SQL 특성 | MigraGuard 추천 |
|---|---|---|---|
| ONLINE-1 | 동시 인덱스 생성 | `CREATE INDEX CONCURRENTLY` | 02:00 Safe |
| ONLINE-2 | 동시 유니크 인덱스 생성 | `CREATE UNIQUE INDEX CONCURRENTLY` | 02:00 Safe |
| ONLINE-3 | 제약조건 단계적 추가 | `ADD CONSTRAINT ... NOT VALID` | 02:00 Safe |
| ONLINE-4 | 지연된 제약조건 검증 | `VALIDATE CONSTRAINT` | 02:00 Safe |

각 DDL에 대해 먼저 MigraGuard forecast를 수행하여 24개 시간대의 최종 위험도(RiskScore)와 추천 시간을 기록하였다. 이후 각 시간대의 예상 TPS를 `pgbench` 목표 TPS로 사용해 부하를 압축 재현하고, 해당 부하 중 DDL을 실제 실행하였다. 각 시간대마다 DDL 없는 기준선을 먼저 측정한 뒤, 동일한 부하 조건에서 DDL 실행 중 P99 응답 지연, TPS 유지율, DDL 완료 시간, 실패 트랜잭션 수, 최대 활성 커넥션 수 및 잠금 대기 수를 측정하였다.

시간대별 실행 결과를 동일한 기준으로 비교하기 위해 각 측정값을 실측 종합점수로 환산하였다. 기준선 대비 P99 배율은 DDL 실행 구간의 P99 응답 지연을 동일 시간대 기준선의 P99 응답 지연으로 나누어 계산하였다. TPS 하락률은 기준선 대비 DDL 실행 구간에서 감소한 TPS의 비율이며, DDL 실행 구간의 TPS가 기준선보다 높으면 0으로 처리하였다.

실측 종합점수는 다음과 같이 계산하였다.

`실측 종합점수 = 절대 P99 응답 지연 + (기준선 대비 P99 배율 × 2) + (TPS 하락률 × 50) + DDL 수행 시간(초) + (실패 트랜잭션 수 × 100) + (잠금 대기 수 × 5)`

[표 13. 시간대별 실측 종합점수의 구성 지표와 가중치 설정 근거]

| 지표 | 점수 반영 방식 | 가중치 설정 근거 |
|---|---:|---|
| 절대 P99 응답 지연 | 측정값(ms) × 1 | 실험에서 수 ms에서 수십 ms 범위로 관측되므로 이를 점수의 기준 척도로 사용하였다. |
| 기준선 대비 P99 배율 | P99 배율 × 2 | 배율은 대부분 1~6 범위로 나타나 절대 P99보다 점수 기여도가 지나치게 작아질 수 있다. 2배를 적용하여 상대적 성능 저하가 순위에 반영되도록 하되 절대 지연보다 우선하지 않도록 하였다. |
| TPS 하락률 | TPS 하락률 × 50 | 하락률은 0~1 사이의 비율이므로 그대로 더하면 영향이 거의 사라진다. 50배를 적용하면 TPS가 10% 감소할 때 5점이 부과되어 중간 수준의 지연 증가와 유사한 크기로 반영된다. |
| DDL 수행 시간 | 수행 시간(초) × 1 | 실험에서 DDL 수행 시간은 대체로 1초 내외이므로 주요 위험 판정보다, 유사한 지연 조건에서 더 짧게 완료된 시간대를 우선하는 보조 지표로 사용하였다. |
| 실패 트랜잭션 수 | 실패 수 × 100 | 한 건의 요청 실패도 일반적인 P99 증가나 TPS 하락보다 심각하게 평가하기 위해 100점을 부과하였다. 이를 통해 실패가 발생한 시간대가 상위 후보로 선택되지 않도록 하였다. |
| 잠금 대기 수 | 대기 수 × 5 | 잠금 대기는 DDL이 운영 쿼리를 직접 차단한 현상이므로 별도 불이익을 부여하였다. 한 건의 잠금 대기는 TPS 10% 하락과 같은 5점으로 환산하되, 실제 요청 실패보다는 낮게 평가하였다. |

가중치는 각 지표의 관측 단위가 서로 달라 특정 지표가 단위 크기만으로 종합점수를 지배하는 문제를 줄이기 위해 설정하였다. 절대 P99 응답 지연을 기준 척도로 두고, P99 배율과 TPS 하락률은 실험에서 나타난 값의 범위를 고려하여 수 ms에서 수십 ms 수준의 점수로 환산하였다. 실패 트랜잭션은 가장 심각한 운영 영향으로, 잠금 대기는 그다음 수준의 직접적인 쿼리 차단으로 평가하였다.

다만 이 가중치는 실제 장애 데이터로 최적화된 보편 기준이 아니라 본 실험의 시간대별 결과를 동일한 기준으로 비교하기 위한 휴리스틱 값이다. 따라서 실측 종합점수는 MigraGuard의 정확도를 판정하는 절대적인 정답이 아니라, 본 실험에서 상대적으로 운영 영향이 작은 시간대를 정렬하기 위한 평가 기준으로 사용하였다. 실측 종합점수가 낮을수록 DDL 실행에 따른 운영 영향이 작은 시간대로 보고, 각 DDL에 대해 1위부터 24위까지 순위를 부여하였다.

[그림 5. 24개 시간대 forecast 수행, 시간대별 부하 압축 재현, DDL 실행 및 실측 순위 계산 절차]

MigraGuard는 네 가지 DDL 모두에서 02:00을 Safe 추천 시간으로 제시하였다. 그러나 실측 지표를 종합해 계산한 실제 순위에서는 02:00이 최적 시간대와 일치하지 않았다.

|---|---|---:|---|---:|---:|---:|---|
| ONLINE-1 | 02:00 | 8위 | X | 4.87ms | 0.96 | 805.28ms | 최적 시간은 아니지만 낮은 위험 후보 |

따라서 본 실험에서는 MigraGuard가 추천한 02:00이 실제 최적 시간대라고 볼 수 없었다. 네 가지 DDL 모두에서 추천 시간은 실제 순위 6~8위에 머물렀고, Top-3에도 포함되지 않았다. 특히 04:00, 00:00, 01:00, 05:00 등 인접한 저부하 시간대가 더 좋은 실측 순위를 보인 경우가 많았다. 이는 현재 forecast가 낮은 위험 구간 중 하나를 고르는 데에는 의미가 있지만, 저부하 후보들 사이의 세밀한 우선순위를 정확히 구분하는 수준에는 도달하지 못했음을 보여준다.

이 결과를 기준으로 보면 MigraGuard의 forecast 기능은 아직 “최적 시간대를 정확히 맞히는 도구”라고 보기 어렵다. 다만 실제 상위 시간대는 대부분 낮은 부하 구간에 분포하였고, 실제 최악 시간대는 주간 또는 저녁의 높은 부하 구간에 집중되었다. 따라서 현재 프로토타입은 정밀한 최적 시간대 선택보다는, 배포 전 단계에서 고위험 시간대를 피하고 낮은 위험 후보군을 좁히는 데 의미가 있다고 해석하는 것이 적절하다.

즉 MigraGuard의 궁극적인 목표는 최적 실행 시간 추천이지만, 현재 단계에서는 최적 시간대를 정확히 맞히는 수준에는 도달하지 못했다. 그러나 시간대별 작업 부하와 DDL 특성을 결합하여 실제로 지표가 악화되기 쉬운 고부하 시간대를 피하고, 상대적으로 낮은 위험 후보 시간대를 제시하는 단계까지는 확인하였다.

바. 실험 3: Config별 처리 여력 변화에 따른 위험도 민감도

세 번째 실험의 목적은 동일한 DDL과 동일한 작업 부하 조건에서도 서버 처리 여력 설정이 달라지면 MigraGuard의 위험도 판단이 달라지는지 확인하는 것이다. 이는 정확도 검증이 아니라, 계산 구조가 최대 허용 커넥션 수(C_max), 최대 처리량(MuMax), 디스크 입출력 처리량 변화에 반응하는지 확인하기 위한 민감도 실험이다.

이번 실험에서는 Safe·Warning·Danger의 고정 판정 기준과 계산 계수를 동일하게 적용하고, 최대 허용 커넥션 수(C_max), 최대 처리량(MuMax), 디스크 입출력 처리량만 변경하였다. 이를 통해 위험도 변화가 판정 기준이 아니라 서버 처리 여력의 차이에서 발생하도록 조건을 통제하였다.

[표 17. Config별 처리 여력 설정]

| Config | 최대 허용 커넥션 수(C_max) | 최대 처리량(MuMax) | DiskIO | 판정 기준·계수 |
|---|---:|---:|---:|---|
| Low | 100 | 1,200 TPS | 10MB/s | 고정 |
| Default | 500 | 5,000 TPS | 100MB/s | 고정 |

| DDL-2 | High | 3.05 | Safe | 471.08ms | 47.11ms | 61 | 처리 여력이 충분한 경우 위험 완화 |
| DDL-3 | Low | 15445.00 | Danger | 23542.97ms | 11771.48ms | 15445 | 처리 여력 부족으로 위험 |
| DDL-3 | Default | 308.80 | Danger | 2354.30ms | 1177.15ms | 1544 | 여전히 위험 |
| DDL-3 | High | 20.00 | Safe | 470.86ms | 235.43ms | 308 | 실제 위험을 과소평가할 가능성 |

DDL-2는 config 차이가 가장 잘 드러난 사례이다. Low Capacity에서는 최종 위험도(RiskScore)가 3090으로 Danger였지만, Default에서는 61.80으로 Warning, High Capacity에서는 3.05로 Safe가 되었다. 같은 DDL과 같은 작업 부하라도 서버 처리 여력과 디스크 처리량이 커지면 예상 DDL 수행 시간(T_ddl), 쿼리 영향 시간(T_block), 예상 최대 커넥션 수요(C_peak)가 함께 낮아져 위험도가 완화된다는 점을 보여준다.

주의할 점은 DDL-3이다. DDL-3은 실제 실행 실험에서 P99 응답 지연 증가가 확인된 일반 인덱스 생성 DDL이지만, High Capacity 설정에서는 Safe로 계산되었다. 이는 config 값을 지나치게 크게 설정하면 실제 위험을 과소평가할 수 있음을 보여준다. 따라서 최대 허용 커넥션 수(C_max), 최대 처리량(MuMax), 디스크 입출력 처리량은 임의로 크게 설정하는 값이 아니라, 실제 부하 시험과 운영 지표를 바탕으로 보정해야 한다.

사. 종합 해석과 한계

세 실험의 목적, 주요 결과 및 해석 가능한 주장은 다음과 같이 정리할 수 있다.

[표 19. 실험별 목적, 주요 결과 및 해석 가능한 주장]

| 실험 | 보고자 한 것 | 주요 결과 | 해석 가능한 주장 | 한계 및 주의점 |
|---|---|---|---|---|
| 실험 1. DDL별 사전 판단과 실제 실행 결과 | 실제 위험 DDL을 사전에 경고하는가 | DDL-3은 P99가 증가했고, DDL-5는 실행 실패하였다. MigraGuard는 둘 다 Danger로 판단하였다. | 실제 위험 신호가 나타난 DDL을 배포 전에 경고할 수 있었다. | Danger 16개 중 10개는 실제 영향이 작아 보수적 오탐이 있었다. |
| 실험 2. 시간대 추천 최적성 검토 | 추천 시간대가 실제 실행에서도 적합한가 | 추천 시간 02:00은 4종 DDL에서 6~8위였고, 최악 시간대는 고부하 구간에 집중되었다. | 최적 시간 예측보다는 고위험 시간 회피와 후보군 축소에 의미가 있었다. | 짧은 pgbench 조건으로 압축 재현했으며, 추천 점수 보정이 필요하다. |
| 실험 3. Config 민감도 | 서버 처리 여력에 따라 위험도가 달라지는가 | DDL-2는 처리 여력이 커질수록 Danger에서 Safe로 낮아졌고, DDL-3은 High에서 과소평가되었다. | 위험도는 DDL 고정값이 아니라 처리 여력과 함께 결정된다. | Config를 과도하게 크게 잡으면 실제 위험을 낮게 볼 수 있다. |

이를 종합하면 MigraGuard는 DDL 실행 전 동적 지표를 결합하여 실제 지연 또는 실행 실패 위험이 큰 조건을 사전에 경고하고, 시간대별 작업 부하와 DDL 잠금 특성을 결합하여 고위험 시간대를 피하는 데 활용될 수 있음을 보였다. 다만 시간대 추천 실험에서 확인했듯이 현재 forecast는 최적 시간대를 정확히 맞히기보다는 낮은 위험 후보군을 좁히는 수준에 가깝다. 또한 Config 민감도 실험을 통해 동일 DDL과 동일 작업 부하에서도 서버 처리 여력 설정에 따라 최종 위험도(RiskScore)가 달라지는 것을 확인하였다.

그러나 본 실험은 실제 운영 장애 데이터를 사용한 통계적 정확도 검증이 아니다. 실험 환경은 로컬 Docker 기반 PostgreSQL이며, 작업 부하는 pgbench로 재현하였다. 또한 실험 2의 실제 최적 시간대 순위는 절대 P99, 기준선 대비 P99 증가율, TPS 유지율, DDL 완료 시간, 실패 트랜잭션 및 잠금 대기를 조합한 본 실험의 휴리스틱 기준이다. 따라서 본 결과를 모든 서비스와 데이터베이스 환경에 일반화할 수는 없다.

특히 현재 실험은 실제 애플리케이션의 커넥션 풀 동작을 완전히 재현하지 못한다. MigraGuard는 커넥션 압력을 중심으로 위험도를 계산하지만, pgbench는 지정한 client 수만큼만 동시 요청을 만들기 때문에 모델이 가정한 커넥션 고갈 상황이 실제 측정에서 약하게 나타날 수 있다. 이 차이는 nullable 컬럼 추가나 동시 인덱스 생성에서 MigraGuard가 Danger를 산출했지만 실제 지연이 거의 없었던 원인 중 하나로 볼 수 있다.

또한 Config 민감도 실험에서 확인했듯이 처리 여력 값을 크게 설정하면 실제 위험이 있었던 DDL도 Safe로 낮아질 수 있다. 따라서 MigraGuard의 판단 결과가 의미를 가지려면 최대 허용 커넥션 수(C_max), 최대 처리량(MuMax), 디스크 입출력 처리량, 잠금 영향도, DDL 유형별 기본 위험도를 실제 부하 시험과 운영 관측에 기반해 보정해야 한다.
