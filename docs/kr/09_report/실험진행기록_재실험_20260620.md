# 실험 진행 기록 - 재실험 2026-06-20

## 재실험 원칙

이 문서는 이전에 환경 설정과 오류 수정 과정에서 생성된 실험 결과를 보고서 근거로 사용하지 않고, 새로 실행한 결과만 기록하기 위한 진행 로그이다.

이전 결과는 `experiments/benchmark/results`에 남아 있을 수 있으나, 본 재실험에서는 `RunTag`를 붙인 새 결과만 사용한다. 따라서 분석 및 표 작성 시 기존 `baseline_*`, `022_*` 결과는 제외한다.

## 이번 실험의 목적

실험의 핵심 질문은 다음과 같다.

1. 동일한 DDL이라도 실행 시점의 작업 부하가 커질수록 실제 PostgreSQL 성능 지표가 악화되는가.
2. MigraGuard의 배포 전 위험 등급이 실제 실행 중 관측된 지연, 실패, 처리량 저하와 같은 위험 신호를 어느 정도 구분하는가.
3. Squawk는 DDL 자체의 정적 경고를 제공하지만 작업 부하 차이를 반영하지 못한다는 점이 실험 결과에서도 드러나는가.

## 새 실험 태그

- RunTag: `rerun_20260620_exp1`
- 대상 workload: `orders_mixed`
- 기준선: DDL 없이 동일 workload 실행
- 비교군: 동일 workload 중 DDL 실행

## 현재 해석

이번 핵심 실험에서 일반 인덱스 생성은 Squawk와 MigraGuard 모두 위험 신호를 제시했고, 실제 pgbench 결과에서도 P99 응답 지연이 크게 증가하였다. 이 결과는 일반 인덱스 생성처럼 쓰기 차단 가능성이 있는 DDL이 실제 운영 부하에서 지연을 키울 수 있음을 보여준다.

반면 `022_safe_add_orders_note.sql`은 실제로는 안정적이었지만 MigraGuard가 Danger로 분류하였다. 이는 현재 설정에서 `C_max=100`이 보수적으로 적용되고, MigraGuard가 `TPS × 영향 시간`을 커넥션 압력으로 환산하기 때문에 발생한 false positive로 해석할 수 있다. 즉 현재 MigraGuard는 위험한 DDL을 놓치지 않는 방향으로는 동작하지만, 안전한 DDL을 과도하게 위험으로 분류할 수 있다.

따라서 보고서에는 이 실험을 “MigraGuard의 완성된 정확도 검증”이 아니라 “DDL 실행 전 동적 지표를 반영하면 실제 지연 위험을 사전에 경고할 수 있으나, 현재 프로토타입은 임계값과 커넥션 압력 계산을 보정해야 한다는 점을 확인한 실험”으로 쓰는 것이 안전하다.
